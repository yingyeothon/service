# Decisions (confirmed 2026-08-22)

Single source of truth for settled product/technical decisions. Change this file first, then the code.

## Purpose

- Shared contest-support services with near-zero traffic outside hackathon day.
- Goal: with tslib (`@yingyeothon/*`) plus these services, a team builds a casual MORPG (lobby HTTP API / party matching / instant dungeon) within a 7-hour contest, spending **2–3 hours on the server**.
- Therefore auth, matchmaking, and broadcast are pre-built services the game only calls.

## Console permission model

- Login: **GitHub OAuth only**. Session = httpOnly cookie (SPA) or Bearer API token (CLI).
- Roles `admin` / `member` / `pending`. New sign-ups are `pending` until an admin approves.
- Bootstrap admins: GitHub logins listed in `ADMIN_GITHUB_LOGINS` (comma-separated) become `admin` on their **first** login only (GitHub logins can be re-registered; later changes go through `/members/{id}/promote`).
- Channels (auth/topic/match/lobby/q) belong to a **project** (revised 2026-08-26, see _Teams and projects_; until then they belonged to their creator). Every team member may read and write them, secrets included. Admins can view/extend/delete any channel and see its config, but never read or change its secrets or config (the `secret_json` half and every write). topic/match/lobby/q channels must reference an auth channel **in the same project** (the earlier admin exception — any auth channel — is withdrawn).
- Channel expiry: 7 days, extendable by 7 (cap now+28). Expired → disabled (401/410) by the daily sweep; extending a disabled channel revives it; deleted (secrets wiped) 30 days after being disabled. A platform admin may grant a channel no expiry on request (_Limit requests_ #7).
- Channel secrets are shown once on creation and can be rotated; an encrypted asset bundle's key is re-readable by its team and never rotated (_Live and encrypted asset bundles_ #4, built 2026-09-28, live on dev and prod 2026-09-29).

## auth service

- Channel = `{ channelId, secret (HS256), audience, tokenTtlSec (default 86400), providers: { github?: {clientId, clientSecret}, google?: {clientId, clientSecret} } }`.
- Users register **their own OAuth app** and set its callback to `https://auth.yyt.life/c/{channelId}/{provider}/callback`.
- JWT: HS256, `iss = yyt-auth/{channelId}`, `aud = channel.audience`, `sub = userId`, `exp = iat + tokenTtlSec`. `userId` = first 32 hex of `hmacSha256(userSalt, channelId + ":" + provider + ":" + providerUserId)`, the salt per auth channel (_Player ids are salted per auth channel_, 2026-09-09); a channel whose `secret_json` holds no `userSalt` — every channel created before this shipped to its stage — keeps the unsalted form. No PII stored or claimed.
- Routes: `GET /c/{ch}/start?provider=&redirect=` → provider → `GET /c/{ch}/{provider}/callback` → `302 {redirect}#token=…&userId=…`. Manual: `POST /c/{ch}/token {provider, accessToken|idToken}` → `{jwt, userId, exp}`. `GET /c/{ch}/verify` (Bearer) → `{userId, exp}`.
- Games verify locally with the channel secret (tslib `createJwtRequestAuthorizer`; contract in `docs/auth-game-contract.md`).
- An auth channel may also carry a **doc apiKey** (`secret_json.apiKey`, added 2026-08-26), which the auth service itself never reads. It authenticates the server side of the state service and is issued, rotated and revoked on its own route so that neither it nor the signing secret can invalidate the other — see _state service_.
- **Debug seeding**: dev `POST /debug/channels` writes the console DB, so console's dev MySQL account is supplied separately as SSM `/yyt-service/dev/auth/debug-mysql-{user,password}` (copied by `bootstrap-ssm.sh dev`) and injected only when deployed with `--param debugHooks=1`. prod has neither the keys nor the routes. Since 2026-08-26 the seeded channel lands in the `debug` team's `smoke` project (found or created, fixed ids `team_debug`/`prj_debug`) unless the body names a `projectId`; smoke scripts pass their own so the topic/match channels they create can reference it from the same project. Move seeding to the console API/CLI once they exist, then remove the keys.

## topic service

- Channel (console) → `{ channelId, apiKey, authChannelId, wsUrl }`.
- `POST /t` (Bearer apiKey) `{ allowUserIds?, ttlSec? ≤ 1200 }` → `{ topicId, wsUrl, expiresAt }`. **Topic lifetime ≤ 20 min.**
- Connect: `wss://topic-ws.yyt.life/?topic={topicId}` (the `wsUrl` returned by `POST /t`; API Gateway cannot map an HTTP API and a WebSocket API onto one custom domain, so the HTTP control API lives on `topic.yyt.life` and sockets on `topic-ws.yyt.life`) + `Sec-WebSocket-Protocol: bearer, <auth JWT>`. Allowed if in `allowUserIds`, or (when empty) the JWT verifies against the linked auth channel.
- Clients send `{type:"msg", payload}` (`{type:"ping"}` → `{type:"pong"}`). Messages are wrapped as `{ type:"msg", from:userId, seq, payload }` and echoed to **everyone including the sender**; `{type:"join"|"leave", userId}` on membership changes (the joiner does not receive its own `join`). 16 KB cap (`{type:"error", code:"too_large"|"bad_message"}`). No history. `POST /t/{id}/publish {payload}` sends `from:"server"`; `GET /t/{id}` returns meta + connection count; `DELETE /t/{id}` broadcasts `{type:"closed"}` and drops every socket. An expired or deleted topic answers the next client message with `{type:"expired"}` and does not close the socket (clients close).
- State: `topic:{stage}:t:{topicId}` (meta), `:conns` (set), `:seq` (counter), `conn:{connId}` → `{topicId,userId,at}`; all with the topic's TTL.

## match service

- Channel = `{ channelId, apiKey, authChannelId, partySize (2–16), waitTimeoutSec (60), onTimeout: "partial"|"fail", callbackUrl?, wsUrl }`. `callbackUrl` is **optional** (added 2026-09-08, _Serverless clients_ #8); an empty string is stored as absent.
- Connecting = submitting a ticket: `wss://match.yyt.life/?channel={channelId}` + `bearer, <auth JWT>`. Invalid JWT → rejected. Reconnecting with the same userId replaces the ticket; disconnect removes it.
- Algorithm: FIFO only. Every connect triggers a match attempt (run by an async worker invocation, because a socket cannot be posted to from inside its own `$connect`); disconnect only removes the ticket. An EventBridge 1-minute schedule handles timeouts and acts as the backstop (documented as "handled within ~2 min").
- Match → `POST callbackUrl` `{ matchId, channelId, members:[{userId}], partial }` with `X-Yyt-Signature: hmac-sha256(channel.apiKey, body)`. The 2xx JSON response (≤8 KB, empty body → `null`) is forwarded verbatim to each client as `{type:"matched", matchId, partial, result, members:[{userId}]}` — `members` is the party in ticket order and is sent in **both** modes. **Without a `callbackUrl` nothing is posted anywhere**: no request, no signature, no `failed reason:"callback"`, and `result` is `null`. Callback failure (network, non-2xx, non-JSON; one retry on 5xx/network) → `{type:"failed", reason:"callback"}`. The server never closes the socket after a terminal message (closing right after `PostToConnection` loses the frame); clients close, idle sockets expire.
- Reconnect with the same userId: the old socket receives `{type:"replaced"}`. `{type:"ping"}` → `{type:"pong", position, waited}`.
- Timeout: `partial` → match with whoever is present, possibly a single player (`partial:true`); `fail` → `{type:"failed", reason:"timeout"}`. A disabled/expired channel (seen within the 60s config cache) or a ping from a socket without a ticket → `{type:"failed", reason:"closed"}`.
- Callback target may be the topic service (`POST /t`) or a tslib dungeon server (creates `GameActorStartEvent`, returns `{wsUrl, gameId, token}`).

## Realtime gateway (`lobby` / `q`) — added 2026-08-25

Design in full: `docs/realtime-gateway-design.md`. Game-side blueprint: [`sample-morpg/docs/blueprint.md`](https://github.com/yingyeothon/examples/blob/main/sample-morpg/docs/blueprint.md) in `yingyeothon/examples`.

- Two channel kinds join auth/topic/match. **`lobby`** is a client-authoritative position relay plus chat and a party primitive; **`q`** bridges client sockets to a tslib actor Lambda (inbound over a Redis list, outbound over pub/sub). Both are served by one platform-operated process whose strategy is chosen per channel.
- **Deployment**: a single Go Docker container on the `yyt-stateful` box, 256 MB cap, design ceiling **10 concurrent players**. Not per team, not on Lambda. One process means the peer index is trivially global and no cross-instance replication is ever built; it also means a deploy or restart disconnects everyone, so clients must reconnect and the SDK's backoff must not stampede.
- **Endpoint**: `wss://gw.yyt.life/?channel={channelId}`, token in `Sec-WebSocket-Protocol: bearer, <jwt>` (never the query string), selected subprotocol echoed back. The console renders this URL only once the host is actually configured; until then a `lobby`/`q` channel view carries no `wsUrl` at all, because a copyable URL for a name that does not resolve reads as "working".
- **Identity**: the gateway holds no channel secrets. It verifies every token by calling auth `GET /c/{authChannelId}/verify` and caches the result keyed by a hash of the token until the JWT's `exp`. auth's `reservedConcurrency` is 10 and a dungeon start bursts 8 connects, so the cache is mandatory, not an optimisation. `authChannelId` is the gateway channel's config, which is why one token works for both the lobby and the dungeon socket.
- **Channel config comes over HTTP** (settled 2026-08-25): the gateway reads it from `GET /gw/channels/{id}`, never from MariaDB. A shared secret from SSM authenticates it (it is a process, not a person, and may read any owner's `lobby`/`q` channel — and only those: every other kind answers 404). `GET /gw/health` exists so the gateway can tell "wrong console, or one older than this route" from "the channel is gone"; both would otherwise be a bare 404. It stays out of the 57/60 connection budget and adds no second schema consumer; the cost is one HTTP hop per cache miss (60 s cache, the existing platform rule).
- **`lobby` and `q` channels carry no apiKey** (settled 2026-08-25). `buildChannel` mints one for every non-auth kind today; these two get a secretless branch, since neither has a server-to-server caller. That also lifts `rules/data.md`'s ban on caching a secret-bearing row. Adding a server-initiated push later (`POST /lobby/{channelId}/publish`, mirroring topic) would reintroduce one deliberately.
- **The gateway routes scopes, never semantics.** `pos` goes to a zone, `say` to a zone/party/user, `event` to a scope with its payload unread. Only `pos` and the party operations have gateway-side meaning; dungeon-entry negotiation, emotes and trades are all `event`.
- **`mapUrl` is pinned to the asset CDN**, not merely required to be https: it is announced to every client and fetched server-side by the game, which makes a free-form URL both an SSRF primitive and a way to point every player's browser at someone else's origin (the same reasoning already applied to stored webhook URLs). Since 2026-09-28 (`todo/46` P2) it must also name a committed file of a versioned bundle of the channel's own team (unencrypted, once encrypted bundles exist), checked whenever the value is set or changed, resolved through the stored `object_key` (_Live and encrypted asset bundles_ #2) — a live bundle can change under a running game, an encrypted one is ciphertext, a URL that names no file could later land in either, and a pin into another team's bundle would stop that team from deleting it.
- **`hello` is the first frame**: `{ userId, connectionId, tick, mapUrl, capabilities, zone, partyId?, aoi }`. The client learns its map and its feature set from the server and holds no configuration of its own. All of it is channel metadata edited in console; the gateway forwards, never computes.
- **Capability flags per `lobby` channel** (`pos`, permitted `say` scopes, `party`, `event`, `debug`). A message whose capability is off is refused with a typed error, never ignored — silence during a contest is expensive to debug. Invalid combinations (`say: ["party"]` without `party`, `say: ["zone"]` without `pos`) are rejected at channel creation, not at connect.
- **Area-of-interest filtering (revised 2026-09-01, settled 2026-09-02).** `pos` carries `(x,y)` so that the gateway can filter by interest: zones are the coarse partition, AOI the fine one. A `lobby` channel may set `aoi: { range }` (`range` 1–256 tiles; requires `capabilities.pos`); the peer cap is the top-level `maxPeers` (1–256, default 64, next item). A peer is **in view** when both `|dx|` and `|dy|` are within `range` of the viewer (a box, not a circle: the owner's "10 tiles up/down/left/right"), nearest first up to `maxPeers`. **Views are receiver-owned**: each connection's view is the set of peers it has been told about, every `enter`/`leave` is a diff of that set, and `snapshot`, `pos` batches and `say`/`event` with `scope:"zone"` all follow the _receiver's_ view ("you hear who can see you"), so a `maxPeers` cut can be asymmetric. A peer that leaves your view without leaving your zone produces a `leave` — the frozen-character bug those frames exist to prevent must not come back — which makes this a wire-contract change (`gateway/README.md`). Views are re-derived on entry, on departure, at every flush, and when the config changes; no hysteresis, because a flush is the only place a move can flip a view, so a boundary peer flaps at most once per tick. Without `aoi` the range is the whole zone; the `maxPeers` cut applies to every lobby channel (revised 2026-09-02, next item). The earlier wording — "grid bucketing and radius config are explicitly not built at this scale" — deferred the work and was then misread as a standing decision against it. Two neighbours settled with it: retained positions are persisted at most once a second (one pipelined write for every mover) plus immediately on zone change and disconnect, since they exist for reconnect recovery, not for relay; and an outbound frame over the 32 KB cap is answered with `error frame_too_large` and a log line instead of being dropped in silence.
- **View invariant and peer cap (settled 2026-09-02, `todo/28`).** For every lobby socket and every peer `P`, each zone-scoped frame naming `P` — a `pos` entry, a zone `say`/`event` — is delivered after the `snapshot`/`enter` that introduced `P` and before the `leave` that removed it; `enter` is never sent for a peer already in view, `leave` never for one that is not, and the frame's `zone` is the zone of the receiver's last `snapshot`. A replaced socket (`4000`) produces a `leave` for its viewers and the successor's zone entry a fresh `enter` — a view is a diff of frames, never a silent swap, so the rule has no exception a checker must know about. Party frames and `say`/`event` with `scope:"party"|"user"` are routed by `userId` across zones and are outside the rule. Three mechanisms make it hold rather than usually hold: (1) every peer frame is enqueued while the hub lock is held, so the lock is the one order all of them share (a batch decided under the lock but sent after it landed behind a `leave` for the same peer); (2) control frames — `hello`, `snapshot`, `enter`, `leave`, `say`, `event`, `party*`, `error` — are never dropped for room; the outbound queue drops the oldest `pos` batch, and a queue holding nothing but control frames closes the socket with **`4005` (reason `too_slow`)** so the client resyncs by reconnecting (a dropped `leave` is a ghost forever, a dropped `enter` a peer that never moves); (3) **`maxPeers` (default 64, max 256) caps every view, with or without an `aoi.range`** — without a box the view is the nearest `maxPeers` peers of the zone, ties by `userId` — so a `snapshot` or a `pos` batch always fits the 32 KB frame cap, and a view change of more than 32 entries (a config change, a crowd) is sent as one fresh `snapshot` instead of a burst of `enter`/`leave` that could fill the control queue. `maxPeers` is a top-level lobby field (the console folds a legacy `aoi.maxPeers` into it); a zone within the cap behaves exactly as before the cap existed. The invariant is enforced in tests by a checker built into every recorder socket plus a randomized model of players, replacements, zone changes and config changes under `-race`; the reference client traces a frame that breaks it (`view_violation`) instead of silently ignoring it.
- **Zone changes are decided by the game's HTTP API**, not the gateway — a rule-free relay cannot own them. The client re-announces and the gateway emits leave-from-old / enter-to-new from its retained state.
- **Sessions** (settled 2026-08-25): one player may hold a lobby socket and a dungeon socket at once; a second socket of the _same_ kind for the same `(channel, userId)` replaces and closes the first. Enforced through Redis `session:{channelId}:{userId} -> connectionId` with compare-and-delete on release, so the game's HTTP API can also see who is online. Two tabs writing one character record is the duplication path this closes.
- **Actor death is the gateway's to detect.** `RPUSH` returns the new list length, so queue depth is free — never poll `LLEN`. An absolute cap (~200) plus a no-progress timeout (~5 s) triggers an abort: close every connection for that `gameId` with a dedicated 4000-range close code **distinguishable from a normal finish**, `DEL` the queue key, `UNSUBSCRIBE`, alarm. A retry must allocate a **new `gameId`**, because the dead actor's lock outlives it. The queue key still needs a TTL as the backstop for the case where the gateway is the thing that died.
- Channel expiry is unchanged by default (7 d, extend +7, cap now+28): games are not left running for days unless a platform admin grants that channel no expiry on request (_Limit requests_ #7).
- **Implemented 2026-08-27 as `gateway/`** (Go module outside the pnpm workspace; wire spec in `gateway/README.md`, which is the client SDK's contract). Deviations from the 2026-08-25 sketch, deliberate: `hello.capabilities` is the config **object** (`{pos, say:[…], party, event, debug}`) rather than a flat list, so the client keeps the `say` scopes; `hello` also carries `connectionId` and, on reconnect, `partyId`. A player has **no zone until their first `pos`** — `hello.zone` is the default the game starts in — and entering a zone answers the newcomer with one `snapshot` frame (every retained peer) rather than one `enter` per peer. A party survives a disconnect (roster marks the member `online:false`, Redis TTL 30 min sliding) and dissolves only on explicit `party.leave` of the last member or the TTL; the leader's seat passes to the next member. The session key is per **kind** (`gateway:{stage}:session:{lobby|q}:{channelId}:{userId}`) so the lobby and dungeon sockets of one player coexist. Handshake refusals are HTTP statuses before upgrade (400/401/403/404/410/502/503), and the application close codes are `4000` replaced, `4001` actor-unavailable, `4002` idle, `4003` policy, `4004` channel gone, `1001` restarting. Channel config is re-read once per TTL for every channel with a socket, so an expired or disabled channel closes its sockets with `4004` within a minute. **Binary frames on `q`, added 2026-09-10** (`todo/34`, from `todo/27` §2): a `GatewayCommand` may carry `{"binary": true, "message": "<base64>"}`, and only then does the gateway write a WebSocket binary frame instead of a text one. The reason is arithmetic — bytes inside a JSON text frame cost +34 % as base64 plus a decode step in every client — and the shape is chosen so that nothing changes for anyone who does not ask: it is per message, there is no negotiation, a malformed `binary` command is dropped rather than written as text, and **inbound binary is still refused** with `1003` (the actor envelope is JSON and has nowhere to put bytes). `lobby` gets no equivalent: its protocol routes by JSON scope, so there is no whole-frame payload to convert; a game's own bytes go in `event.payload`. Not built: `debug` capability commands, the `POST /lobby/{id}/publish` push, and `yyt smoke gateway` (`scripts/smoke/gateway.mjs` covers the lobby protocol against a running gateway instead). **Added 2026-08-27:** `GET /parties/{partyId}?channel={lobbyId}` with a member's bearer JWT returns the mirrored roster (404 for unknown party _and_ non-member) — the read a game's dungeon-entry API needs, since a participant's Redis credential cannot see `gateway:*` keys; `sample-morpg` (`yingyeothon/examples`) is the reference game built on it.
- **Monitoring (settled 2026-08-27)**: the gateway is watched by a scheduled console Lambda (`gatewayProbe`, every 5 minutes, prod schedule only) that GETs `https://gw.yyt.life/livez` and publishes to the stage's existing SNS alarm topic **only on the down and recovered edges**, and only after **two consecutive** failed ticks (≈10 min blind spot; one failed tick is a cold Lambda or a planned restart, not an outage). The edge and the failure count live in the console's Redis, so an outage is one message, not one per tick; when Redis is unreachable as well — the two share the box — the probe sends one "state unavailable" message per container instead of staying silent. No CloudWatch alarm is added — the 10-alarm free tier stays full — and the probe never throws, so it has no Errors alarm either. `/livez` is the target, not `/healthz`: the latter answers 503 for a moment on every console redeploy while sessions keep running. Memory (`/metrics` `runtime.sysBytes` against the container cap) is watched from the host (`docker stats`), not from here. **Usage digest (settled 2026-08-28)**: the other unalarmed numbers — Redis `used_memory`/`maxmemory`, growth of `evicted_keys` since the previous day, per-channel key counts, artifact-bucket size growth (S3 `BucketSizeBytes`) and CDN bytes per day per distribution (CloudFront `BytesDownloaded` of the artifact CDN, the static-site path host, the per-site host and the console's own distribution, labelled `artifact`/`path-host`/`site-host`/`console`, read from `us-east-1`; widened from the artifact CDN alone on 2026-09-27) — are gathered once a day by the console `expire` sweep (`runUsageDigest`), logged in full, and published to the same alarm topic as **one message**: level conditions (80 % of `maxmemory`, a channel above 5000 keys, 20 GiB/day CDN) are announced once when they appear, not daily while they persist; delta events (any eviction, 5 GiB/day bucket growth) every day they occur. CloudWatch or SNS failures are logged, never thrown — the sweep's Errors alarm is for the sweep. Yesterday's readings live in console Redis (`usage:*`, 3-day TTL). CloudWatch is only read (`GetMetricStatistics`); no alarm and no custom metric is created. The hand-made distributions' ids are plain SSM Strings (`cdn-distribution-id`, `site-distribution-id`), set by hand like `gateway-ws-url`; the stack's own two come from `!Ref`. Minute-scale cost protection for the same distributions is the CDN cost guard (_CDN cost guard and emergency stops_ below), whose last completed run the digest also checks (`cdn:guard:stale` after an hour).

## Storage shapes (settled 2026-08-25)

The platform generalises **storage shapes**, never game logic. Every game datum belongs to exactly one of three, and yyt never interprets a game's schema — it lives opaquely inside the value. The direction of travel is that a participant writes only a game Lambda and everything under it is the platform's.

- **asset** — public files on S3 + CDN (`d.yyt.life` / `dev-d.yyt.life`), immutable unless a live bundle marks one mutable (live bundles built 2026-09-28), and served as ciphertext when the bundle is encrypted (_Live and encrypted asset bundles_, live on dev and prod 2026-09-29): the map, with its NPC definitions inlined. The client GETs it directly, like a web page, and does local collision only; the dungeon Lambda fetches the same URL server-side because it is the authority. Format spec: `sample-morpg/docs/blueprint.md` §4.6 in `yingyeothon/examples`.
- **doc** — MariaDB, per-`(channel, ownerId)` versioned JSON with **enforced CAS** (`If-Match` → 409 on mismatch): character, inventory, quest progress. Written only with a channel apiKey, read by the owner alone (`sub != ownerId` → 403) or by the server. Deliberately not Redis: `allkeys-lru` plus the mandatory-TTL rule would evaporate a player's level. Body size and per-channel document caps are required. Served by its own Lambda stack on `doc{-dev}.yyt.life` — see _state service_ below.
- **ephemeral** — Redis, TTL mandatory: party rosters, retained positions, dungeon queues and start events. Gateway-owned. A party survives a _reconnect_ (sliding TTL, mirrored to Redis so the game's entry API reads a roster it can trust rather than believing a client) but not a logout; a party that outlives a session would be a guild, which is out of scope.
- **kv** — MariaDB, added 2026-09-03: per-project **collections** of JSON values addressed by key, each with a read and a write scope (`team` = console/CLI only, `server` = the doc apiKey and the console, `project` = any player of the project, `user` = the entry's owner), optional per-entry TTL, optional CAS, optional AES-256-GCM encryption whose key only the state stack holds. Announcements, per-player progress, public profiles, inboxes. Served by the state stack under `/kv/*` — see _Key-value store_.

Consequences settled with them:

- **Assets get a dedicated resource** (decided 2026-08-25, implemented 2026-08-25 as `asset_bundles`/`asset_files`/`asset_pending_uploads`, migration `3_assets`), not an extra `platform` enum value on `catalog_apps`. Object read is public and unauthenticated — a game client holds no GitHub account and fetches straight from the CDN; the management API is member-gated, and writes need team membership of the bundle's project (revised 2026-08-26; formerly the bundle owner or an admin). That flat membership rule _is_ the model: reproducing the catalog's per-app/per-group grid is exactly what a separate resource exists to avoid. Object keys are versioned (`assets/{bundle}/{version}/{path}`, the path relative inside the bundle so a map's own references keep resolving) and served `Cache-Control: public, max-age=31536000, immutable`, set with `MetadataDirective: REPLACE` when commit copies staging to the final key. Versions and paths are stored `utf8mb4_bin` (migration `4_assets_binary_paths`): they are S3 key segments and S3 keys are case-sensitive, so the database index has to agree with the storage it names — under the inherited `_ci` collation `v1/map.json` and `V1/map.json` were one row addressing two objects. Bundle **names** stay case-insensitive on purpose. Because the object is immutable, a `(bundle, version, path)` triple is **write-once** — a second commit under a different upload id gets 409 (re-committing the _same_ upload is idempotent and returns its file) — and a bundle that holds files **could not be renamed** while its name was a live key segment; since 2026-08-26 new object keys are id-based (`assets/{bundleId}/{version}/{path}`) and renaming is allowed — rows created before that keep their stored `url`/`object_key`. Commit **inserts the row before copying the object**: the row is the claim, so a lost race cannot overwrite a live `immutable` object, and a failed copy rolls the claim back only once `HeadObject` answers 404 (revised and built 2026-09-28: a lost copy response can mean a published object — _Large asset uploads_ #2); every copy onto a new key also carries `If-None-Match: *`. Deleting a version or a bundle is **refused while a lobby channel's `mapUrl` still points into it** (only a channel of the same team since 2026-09-28: _Live and encrypted asset bundles_ #2), and a failed object delete keeps its row so the retry can finish — `assets/` is outside every sweep, so a stranded object is unreclaimable. The "current version" pointer lives in **channel config, not the CDN** — publishing a map is a config edit, so no invalidation ever happens. `Content-Type` is set at presign time from an extension allowlist (json/png/jpg/jpeg/webp/gif/bmp/ogg/mp3/wav/txt/csv, and since 2026-09-28 db/sqlite/bin as `application/octet-stream` and zip as `application/zip`; since 2026-09-28 every object of an encrypted bundle as `application/octet-stream`; no `text/html`, no `image/svg+xml`, which scripts): letting a caller choose it would put attacker-controlled markup on our own CDN origin. Staging lives under `asset-uploads/`, swept exactly like the catalog's `uploads/`, and **no retention policy touches `assets/`** — a 404 there is not a degraded game but one that cannot load at all. `uploads`, `assets` and `asset-uploads` are reserved catalog app names, since an app name is the first key segment. Caps: 2 MiB per file, 20 MiB per bundle, 200 files per version, 50 versions per bundle, 20 bundles per project (revised 2026-08-26; formerly per member, admins exempt; since 2026-09-28 these are the soft values of _Limit requests_, which a platform admin may raise per bundle or project up to a hard ceiling, joined by 10,000 files per bundle and 400 MiB per project); every one of them counts presigns still in flight, because a grant is a reservation and a caller that pipelines them would otherwise see an empty bundle each time. Staging objects are reachable on the CDN by their random id until the sweep takes them, exactly like the catalog's `uploads/`; they carry the same allowlisted type, so this is not a new exposure.
- **The client is a browser.** It holds no content and no rules, receives its map URL and capability set in `hello`, and performs only the predefined actions of the protocol plus local collision. This is a constraint, not a description — it is what makes a shared client SDK possible later.
- **Participant credentials.** A game Lambda runs in the participant's own AWS account and talks to yyt Redis directly, so each `q` channel is issued a Redis ACL user scoped to `~game:{stage}:{channelId}:*` / `&game:out:{stage}:{channelId}:*` — a wrong prefix fails `NOPERM` instead of reading another game's queue. The `{stage}` segment matters: one Redis instance serves both stages, so without it a dev credential would match prod keys. Since the store became Valkey 8 (2026-08-28) the issuer may add a read-only selector such as `(%R~gateway:{stage}:party:{lobbyId}:* +get +mget)` when a `q` channel names a lobby, so a game can read a roster without the gateway HTTP hop (deferred, `todo/34-backlog.md`; not implemented yet). That credential is issued once and never logged, the same discipline as `rotate-secret` — but the `q` **channel** itself has no secret and `rotate-secret` refuses it; the two are separate things. **Both surfaces print it as one copyable block** — connection plus the five tslib prefixes, one `key`/`value` per line (the console matched the CLI's shape on 2026-09-10; it used to show host, port and username as three separate fields). The account is scoped to exactly those prefixes, so a value a participant retypes lands outside the ACL and fails `NOPERM`, or differs from the gateway's by one character and silently relays nothing; a block that is copied whole cannot do either. The two differ in one place, on purpose: `yyt` prints the password **inside** the block on the issue that mints it, because a terminal is where that credential is delivered and the operator copies the card whole; the console keeps it on a separate one-render surface, because a browser page is read many times and re-rendered from cache.
- **The console mints them itself** (decided 2026-08-26, implemented the same day: `POST|GET|DELETE /channels/{id}/redis-user`). Redis has no way to delegate "may create users below this prefix", so anything holding `ACL SETUSER` can widen itself — the credential the console carries for this is root-equivalent in Redis terms, and that is accepted rather than worked around. The reasoning: console already holds every auth channel's signing secret, so its blast radius does not change class; the alternatives each buy less than they cost (routing issuance through the not-yet-written Go gateway inverts `todo/14`'s order and adds a console→gateway auth path, and issuing by hand puts a manual step between a team and their first working Lambda, which is the friction this platform exists to remove). What the design does buy is that **no accidental path reads data**: the issuer is a _second_ account per stage (its name lives in `yyt-stateful`, never here) with `-@all`, four `acl|…` subcommands and **no key or channel patterns at all**, used by one module that never runs a data command, while the console's own user keeps `-@dangerous` and no ACL rights. The username is derived like the prefixes (`game_{stage}_{channelId}`) and the issuer refuses every name outside `game_` — `ACL SETUSER` is an upsert, so one miscomputed id would otherwise rewrite one of the platform's own service accounts and lock a whole service out of Redis. Issue is idempotent-by-replacement (`reset` first, so a re-issue rotates rather than stacking a second password) and always `ACL SAVE`s, or the credential would work until the next Redis restart and then fail on contest day. The account is revoked when the channel is **deleted** (by hand or by the daily sweep) but deliberately **not when it merely expires**: extending revives a channel, and stripping a credential the owner still holds would be a silent trap. The participant grant also removes `scan`, `randomkey`, `dbsize`, `pubsub` and `memory` on top of `-@dangerous`: Redis does not filter `SCAN` by ACL key patterns, so without that a credential could enumerate every key name on the instance — both stages, every service — while being refused every read (measured, and fixed, 2026-08-26). The same fact is why every key that names a secret stores its digest instead. **Redis has no per-account memory quota** and `allkeys-lru` means an abuser evicts other services' data rather than their own, so the platform's answer is observation plus revocation, not a limit: the daily cron reports instance memory and per-channel key counts. Splitting participants onto their own Redis instance with its own `maxmemory` is the only real isolation and is deliberately deferred.
  A stage without a state stack is a valid state too: `POST`/`DELETE /channels/{id}/doc-key` answer 503 with `reason: state_not_configured` rather than minting a credential with nowhere to spend it, while the **read** still returns the block with `configured: false`, because that read backs every auth channel's detail page.
  A stage without an issuer account is a valid state — `POST`/`DELETE` answer 503 with `reason: redis_acl_not_configured`, while the **read** still returns the derived block with `configured: false` rather than failing, because that read backs every `q` channel's detail page and a 503 there would paint an error over a perfectly healthy channel.
- **The Redis prefixes are derived, not configured.** All four keys tslib's actor needs plus the pub/sub channel are computed from the channel id — `game:{stage}:{id}:{event,queue,lock,awaiter}:` and `game:out:{stage}:{id}:` — and are never stored or typed in. Deriving three of the four would be worse than deriving none: the fourth would be invented outside the participant's ACL scope and fail `NOPERM` at actor start. They have to agree on three sides at once — the gateway, tslib, and the participant's own Lambda — and a mismatch is a silent no-op rather than an error, so exactly one place computes them and the console, CLI and SPA present the result as one copyable block. The block is passed to tslib's prefix options directly: helpers that append a segment of their own turn `…:queue:` into `…:queue:queue:`, which stays inside the ACL and therefore fails silently rather than loudly. Abuse is handled in person; what is not optional is per-prefix key-count and memory observability before the shared 256 MB ceiling evicts someone else's state.

## state service (`doc.yyt.life`) — added 2026-08-26

Serves the **doc** shape from _Storage shapes_ (and, since 2026-09-03, the **kv** shape under `/kv/*` — _Key-value store_ below; this section describes the doc routes): one versioned JSON blob per `(auth channel, ownerId)` in `state_docs` (migration `5_state_docs`).

- **Its own Lambda stack, not a process on the box.** The `yyt-stateful` host exists for the two things that must hold a socket or the data itself — Redis and MariaDB — and a REST reader/writer holds neither, so the _Stack_ table's rule puts it on Lambda. The obvious name was in any case unavailable — `state` is already taken by an existing record for that box (see the private ops repo) — which is why the API is `doc{-dev}.yyt.life`. (Until 2026-08-26 the `doc` bullet above said "served under the existing `yyt-stateful` hostname"; that sentence read the _storage_ location as the _serving_ one and contradicted the _Stack_ table two screens earlier.)
- **Scoped to the auth channel, not to the game channel.** `ownerId` is `deriveUserId(userSalt, authChannelId, provider, providerUserId)` — it means nothing outside the auth channel that produced it, so any other scope needs a mapping and a channel segment in every path. A team has exactly one auth channel and therefore exactly one document namespace, whether it runs a `q` channel, a `lobby` channel, or both. `q`/`lobby` keep their empty `secret_json`.
- **The client reads only its own row.** `GET /s/{ownerId}` with the same channel JWT the gateway takes: `iss` names the channel, `sub` must equal `ownerId`, otherwise 403. There is no list route — enumerating a channel's owners is a server capability, and a route that a client can reach with its own token would hand it one.
- **Only a server writes**, holding a channel apiKey as `Authorization: Bearer`. Auth channels had none; they get one now, deliberately and _separately_ from the signing secret, issued and rotated by `POST /channels/{id}/doc-key` and revoked by `DELETE`. A second secret rather than a reuse of `secret`, because the two have different holders — the signing secret never leaves the platform, this one is pasted into a participant's Lambda — and rotating either must not invalidate the other. The key is **self-identifying** (`yds.{channelId}.{random}`, the `.` being outside the channel-id charset): the routes carry no channel segment, and the alternative to reading the id out of the credential is scanning `secret_json` across every row.
- **Every write is conditional.** `PUT /s/{ownerId}` requires `If-Match`; `"0"` means "no row yet" and creates. A missing `If-Match` is **428**, a stale one is **409** carrying the current `ETag`. This is the entire point of the shape — two dungeon results landing on one inventory is the failure it exists to prevent, and an unconditional whole-blob write is that bug restated. `DELETE` accepts `If-Match` but does not demand it.
- Caps: **64 KB** per document, **10000** documents per channel, both refused rather than trimmed. `owner_id` is `utf8mb4_bin`: it is an identity the authorization check compares byte-exactly, so a case-insensitive index would let two identities share one row — the same bug migration `4_assets_binary_paths` fixed for S3 key segments.
- **No Redis and no cache.** Rows carry secrets, and `rules/data.md` forbids caching those; one `SELECT` per request is the cost of correctness here. That `SELECT` runs for **any** bearer, before a body limit or an authorization check, so unauthenticated junk is what actually competes for the stack's `reservedConcurrency` — which is why the stack sets an API Gateway throttle rather than leaning on the reservation alone.
- **The document is stored as sent, byte for byte.** The request is parsed only to prove it is JSON; re-encoding it would be interpreting it, and `JSON.stringify(JSON.parse(x))` silently rewrites an integer past 2^53 (a snowflake id), collapses duplicate keys and reorders integer-like ones. The size cap is therefore measured on those same bytes.
- **A browser is a first-class caller**, so the routes carry CORS with `*` — the credential is an explicit `Authorization` header, never an ambient cookie — and, critically, `Access-Control-Expose-Headers: ETag`. `ETag` is not CORS-safelisted, so without it a browser client cannot read the version it is then required to send back in `If-Match`, and the whole conditional-write contract is unusable from the client the design assumes.
- **This is the first writer of the database that is not console**, so the ownership rule is narrowed rather than broken: console still owns the schema and every migration, and the state account's grant is `SELECT` on `channels` plus `SELECT, INSERT, UPDATE, DELETE` on `state_docs` alone. That grant is table-level, so it does include every channel's `secret_json` — the same reach auth/topic/match already have, and the honest claim is "cannot touch members or api_tokens", not "sees only what it needs". A stage whose account has not been created yet simply has no state stack deployed.
- Documents die with their channel: the console sweep drops a channel's documents when the channel is deleted, the same lifecycle point at which a `q` channel's Redis credential is revoked, and for the same reason — expiry is reversible by extending, deletion is not.

## Teams and projects — added 2026-08-26

- **Terminology (2026-08-26): the grouping is a _team_, never an "organization".** Code, API paths (`/teams`), Redis keys, history events, the CLI (`--team`, `YYT_TEAM`, `.yyt.json {team}`), documents and the database all say `team`. The expand migration keeps its historical name `6_org_project`; `7_team_rename` renames every table, column, index and foreign key it created.

Plan and migration detail: `docs/team-project.md`. Every resource — channel, catalog app, asset bundle, and through the channel `state_docs` — belongs to a **project**, and every project to an **team**. The single `owner_id` model (creator owns; admin sees all) is withdrawn for resources; it survives only as `created_by` for display.

- **Hierarchy**: platform `members` (roles `admin|member|pending`, unchanged) → `teams` (name globally unique, case-insensitive; markdown description; `admin_locked` flag) → `team_members` (`owner|member|pending`, plus `declined|kicked` state for a re-request cooldown) and `team_history` (append-only, written in the same transaction as the change it records) → `projects` (name unique within the team) → resources, `project_versions`, `issues` (per-project sequence number), and team-level `discussions`. Comments hang off issues and discussions.
- **Permission is team membership, nothing finer.** `pending` sees the team's name and its own state. `member` reads and writes every project, resource, discussion and issue of the team — including channel secrets, `rotate-secret`, Redis credential and doc-key issue, Slack/retention settings. `owner` adds member management, team settings and team/project deletion. The blast radius (one member can rotate a teammate's credential) is accepted: a team is a team building one game together, not a tenancy boundary.
- **Platform admin** may list every team, delete a team, set or clear `admin_locked` (owners cannot; the flag is the installer's trust anchor and is refused in the team PATCH body), and appoint an owner — any existing platform member (`admin` or `member`, including themselves; `pending` is refused); the appointee need not be seated yet, so a team whose owners all left can be rescued. (Revised 2026-08-29: the earlier "non-admin other than self" restriction was never a product decision; an admin who wants to operate a team seats themselves as owner and is then judged by that membership.) Admin may also delete a project, because deleting a team requires its projects gone first and an ownerless team has nobody else. Admin still never reads or writes secrets/config; a resource helper called with `secret: true` refuses admins with **403** (the team is already visible to them), whereas a member of another team gets **404** (the resource is not revealed). Appointments are written to both `team_history` and the global audit log. Platform `pending` cannot create or join teams.
- **Joining**: a member asks by exact team name (`POST /teams/join {name}`; unknown names are 404, indistinguishable from "not allowed"), or an owner adds a GitHub login that is already a platform member. **There is no global team listing** — the migration seeds teams named after GitHub logins, so a listing would publish the member roster. Kicked or declined members wait out a cooldown before asking again, and withdrawing one's own request counts as declined (otherwise join→withdraw is a free loop that writes history on the target team).
- **Last owner**: demote/leave/kick run in one transaction that locks the team row (`SELECT … FOR UPDATE`), counts owners, then writes; the same lock serialises issue numbering.
- **Leaving does not revoke anything.** A kicked or departed member still knows every secret they ever saw; the response and the UIs list the channels whose credentials should be rotated and — since 2026-09-28 — the team's encrypted asset bundles, whose keys any member could read and whose remedy is a new bundle (_Live and encrypted asset bundles_ #4). Automatic revocation would kill a running game.
- **Names**: unique within the team across all kinds — `(team_id, name)` on `catalog_apps`, `asset_bundles` and `channels` (channels had no uniqueness at all before). A name may not look like an id (`team_`, `prj_`, `ca_`, `ab_`, `auth_` … prefixes), because the CLI treats prefixed strings as ids. `team_id` is denormalised onto resource rows (a project never changes team) so the index is local.
- **Object keys are id-based** for new rows (`apps/{appId}/…`, `assets/{bundleId}/…`); existing `url`/`object_key` values are immutable and stay valid. Catalog commit inserts the artifact row before copying (claim-first, the assets rule). `apps` joins the reserved catalog names while legacy `{name}/…` objects exist.
- **`authChannelId`** of a topic/match/lobby/q channel must name an auth channel **in the same project**. Migrated cross-team pairs are fixed by the mapping script, not tolerated.
- **Migration is explicit, not inferred**: `6_org_project` only adds tables and nullable `team_id`/`project_id` columns (expand); a machine-local mapping file (`local/team-project-map.<stage>.json`) declares every existing resource's destination or deletion and `scripts/apply-team-project-map.mjs` applies it, refusing to run while any resource is unmapped. The contract migration (`NOT NULL`, team-scoped unique indexes, dropping the catalog permission tables and columns) is a **separate later commit**, applied only once every stage runs the new bundle, because `deploy.sh` applies every pending migration and MariaDB DDL cannot roll back. Its SQL starts with the line `-- contract`; `scripts/migrate.sh` refuses such a pending file unless `--allow-contract` is passed **and** `scripts/contract-preflight.mjs` (the same checks `apply-team-project-map.mjs` verifies with: no unmapped rows, no duplicate `(team_id, name)` including soft-deleted channels, no app named `apps`) passes — `deploy.sh` never passes the flag, so a contract migration is always applied by hand first.
- **Team-scoped unique names include soft-deleted channels** (2026-08-26): the contract index `(team_id, name)` on `channels` has no `deleted_at` filter, so a deleted channel's name stays taken until the daily sweep purges the row (`purgeChannels`, 30 days after the soft-delete; the sweep's soft-delete itself follows 30 days of `disabled`). Simpler than a partial index MariaDB does not have, and the pre-flight counts the same way.
- **Migration directory names sort lexically** (`prisma migrate deploy` and `testDb.ts` both order by name), and the applied `0_`…`7_` names cannot be renamed. Decided 2026-08-26: the contract migration and everything after it use `m{NNNN}_{slug}` (`m0008_team_project_contract`, `m0009_…`) — `m` sorts after every digit, so the new series always follows the old one, and the zero-padded number keeps its own order.
- **Installer trust**: `platform_settings.installer_app_id` names the app `GET /catalog/installer/downloads` serves; its team must be `admin_locked`. The compatibility read routes for the installed installer were **removed 2026-09-10** (`todo/17` P10, at the owner's word that backward compatibility is not a consideration before launch): `/catalog/apps/{app}` and its artifact routes take an id and only an id, the name resolution is gone. Two of the three named here were **not** removed and are permanent: `GET /catalog/apps` (the flattened cross-team list, `GET /channels`'s shape and the CLI's no-context listing — it was compatibility only by association) and the downloads route.
- **Versions**: free strings per project, unique (`utf8mb4_bin`); `bump patch|minor|major` parses the strictly-semver subset, takes the greatest, and refuses when none parses. A version links to artifacts and asset versions (`project_version_links`), cascading on deletion of the target. **A committed catalog artifact is linked automatically (2026-09-02)**: its `version` tag with any `+build` suffix stripped (`1.0.7+8` → `1.0.7`; the build number is the artifact's own tag — the rule the backfill script used) names the project version, which is created when missing (`note` empty, creator = the committer; the commit response carries `version: {id, name, linkId, created} | null`). A repeated commit of the same upload only reports the link the first one made and never writes, so a version an owner deleted (or a link they removed) stays that way. The bookkeeping is skipped — never failing an already-copied artifact — when the tag is not a version name, when a cap (versions per project, links per version) is hit, or when the team write fails; it takes no per-member write slot, since commits are bounded by presigns, and the cap is checked before the write rather than under the team lock (the same shape as `POST …/versions`; a parallel burst can overshoot it by a few rows, accepted). `yyt project issue create|update --version <name>` creates a missing version from the client (`+build` stripped by the same rule, list → `POST …/versions` → on 409 re-list), so an issue filed against pubspec `1.0.7+8` meets the deploy's artifact on `1.0.7`. The SPA shows a version as a detail page (`/teams/{team}/projects/{prj}/versions/{ver}`) with its links, each naming its target, and the issues that reference it (`GET /projects/{prj}/issues?versionId=`).
- **Issues** are numbered per project, may reference a version, can only be closed and reopened (never deleted); comments may be deleted by their author or an owner. Discussions are the team-level equivalent (article + comments).
- **Markdown** (description, discussion, issue, comment, and the existing event/proposal `bodyMd`) is stored raw and rendered by the SPA through `react-markdown` + `remark-gfm` + `rehype-sanitize`: no raw HTML, no images, `http(s)` links only, `rel="noopener noreferrer nofollow ugc"`. The SPA distribution adds a CSP response header. This supersedes the plain-text rule in _Console SPA frontend stack_ and `rules/security.md`.
- **Caps**: markdown body 20 KB, comment 10 KB; per member 5 teams; per team 20 projects (the soft value of `team.projects` since 2026-09-29, hard 1000, _Limit requests_ #1–#2), 50 pending requests, 500 discussions; per project 20 bundles (the soft value of _Limit requests_ since 2026-09-28), 50 apps, 50 channels, 500 versions, 2000 issues; per issue 500 comments. Every recorded team write — markdown or not, including join requests — is rate-limited per member (2/s, Redis `nx`); Redis credential issue is rate-limited per member **and** per channel (10 s), since every issue is an `ACL SAVE`.
- **CLI** is team/project-aware (see _CLI_); `catalog group|permission` commands are removed. The Flutter console app probes tokens with `GET /me`, lists apps with **one request** (`GET /catalog/apps?artifacts=summary&platform=android`, 2026-09-27 — the flattened list embeds the newest artifact per app, so a client never walks `/artifacts` per app, and carries the caller's seats; the per-team requests it replaced put a cold Lambda container on the launch path for each concurrent one), checks for its own update only after that first load, and has no permission screen. Since 2026-09-26 it also lists, views, creates, edits and deletes a project's **sites** (name, description, domain; no deploy upload) and **channels** (per-kind config, extend; no rotate-secret, Redis user or doc key), gated like the SPA: writes need a seat (`owner`/`member`), except channel extend and delete, which the server also allows a platform admin.

## Hackathon workflow (console)

Redesigned 2026-08-29, superseding the proposal/winner model (an admin-driven `draft → proposing → voting → decided → published → closed` chain with free-text proposals and one vote per member; dropped with migration `m0009_event_redesign`).

- **An event is a date vote plus a page.** A draft carries everything at once: title, markdown body, poster, place (free text) with an optional map `placeUrl`, `durationHours`, the candidate start times (`options`, each a timestamp) and `voteUntil`. There is no proposal; the round number ("36회") is part of the title.
- **State machine** `draft → voting → waiting → opened → closed`, plus `cancelled`. `publish` (owner or admin) moves `draft → voting`. The rest is time-driven and **derived lazily**: every read computes the effective status from `voteUntil`, the decided start and `durationHours`, and persists it opportunistically on the next write or the daily sweep. No scheduler; an event nobody reads need not transition.
- **Vote**: any non-`pending` member, **multiple options** per person, changeable while `voting`; tallies are hidden from voters until the vote closes. At `voteUntil` the option with the most votes wins, ties (including zero votes everywhere) go to the **earliest** start time. No extension, and `voteUntil` and the options are immutable once `voting`; `place`/`placeUrl` stay editable because they are not part of the vote.
- **Early close (platform admin only)** — added 2026-09-01, superseding the original "no early decision": `POST /events/{id}/close-vote` ends a running vote immediately. It moves `voteUntil` to now and decides the start in one conditional update — by the standing tally rule, or by an `optionId` the admin names outright, which may be an option that lost. A **reason is required** even when the admin owns the event, and the actor, the time and the reason are stored on the event row (`vote_closed_by`/`vote_closed_at`/`vote_closed_reason`) and shown on the event page to everyone, not only in the admin audit log: a forced decision participants cannot see would defeat the revision history this redesign exists for. The decision only narrows the calendar days this event holds, so no new one-event-per-date check is needed. Two consequences follow from the state machine and are intended: the event becomes visible to anonymous visitors and its tally is revealed exactly as the natural deadline would do, and `POST /events/{id}/show` (gated on "visible to the world") becomes available — closing a vote early also unlocks the gallery.
- **One event per date**: a candidate start time whose calendar day (`Asia/Seoul`) is already taken by another event's options or decided start (in `voting`, `waiting` or `opened`) is rejected — when the option is added to the draft and again at `publish`, since the draft may predate the conflict.
- **Ownership**: any non-`pending` member creates drafts, at most **3 drafts per member** (`429`, `code: draft_limit`). A draft is visible only to its owner and admins. Owner and admin edit title/body/poster/place until `closed` and may `cancel` before `closed`; only a platform admin deletes (hard delete of the row, revisions, comments, votes and the poster object) — the deleted event is copied in full into `audit_log.detail_json` first.
- **Every edit is a revision.** `event_revisions` stores the full page (title, body, poster key, place, placeUrl, durationHours) with the editor and time, including admin edits of someone else's draft; the API serves the list and any revision, the SPA and the CLI compute the diff between two revisions. The event page shows the history; the old proposal panel is gone.
- **Poster**: allowed in every status before `closed`; each upload is recorded (`event_posters`: uploader, time, key, size), and a replacement deletes the previous S3 object immediately (one poster per event, no GC; a failed delete is retried by the daily sweep). Delivery stays the presigned-GET redirect.
- **Comments** (`event_comments`, markdown, same caps as team comments) by non-`pending` members on non-draft events; **edited by the author alone, deleted by the author or an admin** (revised 2026-09-10; edit used to allow an admin too). Everywhere else in the console an edit is the author's own — issues and discussions have said "only the author may edit" since they were written — and deletion is the moderation tool. Editing another member's words leaves their name on text they did not write, which is worse than removing it and cannot be told apart from the author's own edit. A show's comment is the one exception: a show **admin** may edit one, and decision 12 below makes them give a `reason` that goes to the audit log. A show's own owner may edit a comment on their show without one — moderating your own wall is not the same act as reaching into someone else's. Anonymous visitors see only `waiting`, `opened` and `closed` events; members see every non-draft status including `voting` and `cancelled`.
- **Migration is destructive**: `proposals`/`votes` are dropped and the `events` status enum is replaced. Both stages hold only test data (confirmed 2026-08-29), so no data is carried over.
- No Slack notification in this iteration. Everything the SPA can do here the CLI can do too (`yyt events …`).
- **Past events stay off the console (decided 2026-09-06).** The model accepts future-dated votes only; rounds 26–35 (and anything older) are represented by yingyeothon.github.io, which remains the canonical archive. No admin "archive import" shortcut is built.
- Implementation notes (2026-08-29): `cancel` is allowed from `draft` too (a member cannot delete their own draft, so this is how a spare draft is retired; a cancelled draft no longer counts against the cap). `durationHours` is frozen with the vote at `publish` because it fixes when `opened` becomes `closed`. A due vote is decided by the first read that finds it (one conditional update), so the tally is frozen the moment `voteUntil` passes even before the sweep runs. Comments are part of the event detail response (no separate list route). Page edits are capped at 200 revisions per event (409 beyond).
- Posters live in a private bucket owned by the console stack (`yyt-console-posters-{stage}`, retained on stack removal), uploaded through a presigned PUT (png/jpeg ≤ 5 MB, content headers signed) and attached only after a `commit` step re-checks the object. Poster visibility follows the event's visibility and is enforced by the API, so CloudFront does not front the poster bucket: `GET /events/{id}/poster` redirects to a 10-minute presigned GET (browsers may cache it, so a replaced poster can lag up to 10 minutes).

- Console app (`apps/console-app`, shown as "잉여톤"): applicationId **`life.yyt.console`** (pre-release ids `life.yyt.catalog` and the legacy vendor id are abandoned without compatibility, 2026-08-27) with its own signing key. It signs in by scanning the SPA's _App login_ QR (see the auth bullet above) or through the web → app handoff, and talks only to the console API; it is distributed through the catalog itself.
- **Web → app handoff** (decided 2026-09-29, `todo/49`; console API live on dev and prod the same day with the fingerprint in SSM, app 1.6.0+26 in both catalogs, SPA on dev and prod): the Home installer card and the _App login_ page show an **Open app** button on Android browsers for approved members. `POST /auth/app-handoff` (cookie session only — a bearer gets 403 — Origin-checked, the member write slot, the 20-token cap) issues a `hoff_` code — 128 bits random, Redis `handoff:{sha256}` for **120 s**, single use — and the SPA navigates to a Chrome `intent://<console host>/app-open?code=…#Intent;scheme=https;package=life.yyt.console;S.browser_fallback_url=…/ui/installer?app=missing;end`. The intent form is deliberate: Chrome never hands a same-origin https link to an App Link, and the pinned package means no chooser and no custom scheme to hijack; a phone without a handoff-capable app (none, or older than 1.6.0) lands on the Installer page (whose URL carries no code). The app (`app_links`, a `VIEW`/`BROWSABLE` filter for the two console hosts on `/app-open`, `autoVerify`) re-checks the URL itself — `https`, an allowlisted host, the exact path, no userinfo or explicit port, the code grammar — because the exported activity receives whatever VIEW intent any app sends it; then calls `POST /auth/app-handoff/exchange` (no auth; the code is the credential) **before** asking, so the confirm can name the account it would add (a stranger's own code in a mailed link is the threat) — declining revokes the just-minted token with itself as bearer; the exchange consumes the code, re-reads the member (gone → the same 410 as an unknown code; `pending` → 403 with nothing minted), mints a `yyt_` token named `app handoff <time>` (`token.create`, `via: "handoff"`) and answers 201 `no-store`; the app then adds the profile exactly as a scanned QR would (the `/me` probe, the pending refusal, the same server + login replaced). The handoff code is the one secret allowed in a URL (`rules/security.md`): it is a claim on a token, not the token, and it is spent or dead within two minutes. Rollout order is console API → the app in the catalog → SPA, because a browser with the new button and an old app lands every tap on the Installer notice. The button is hidden in in-app WebViews (`; wv)`), which cannot follow `intent://`. Accepted residuals: an adb-attached logcat sees the intent URL, and a phone that never had the genuine app could carry an impostor of the same package name (App Links verification does not gate `intent://` with an explicit package). `GET /.well-known/assetlinks.json` is served by the console API (CloudFront sends root paths there, not to the SPA bucket) from the stage's `android-cert-sha256` SSM parameter (the release keystore's SHA-256; empty → 404, links stay unverified but the intent path works regardless), and `GET /app-open` redirects a browser to the Installer page. The one-time credential a channel create returns (`secret` for auth, `apiKey` for topic/match; lobby/q return none) is shown once on a screen that sets Android `FLAG_SECURE`, copied as a sensitive clip, and never stored. It updates itself: at launch it compares its own version with the newest Android entry of `GET /catalog/installer/downloads` and offers a banner-with-button update (2026-08-27); the CLI likewise has `yyt self version|update` (newest `cli/v*` GitHub release, checksum-verified, in-place binary swap). Which app is "the installer" is `platform_settings.installer_app_id`, set by an admin, and that app's team must be `admin_locked` (every owner/member is a platform admin) — otherwise `GET /catalog/installer/downloads` answers 503 `installer_untrusted` rather than serve a member-pushed APK to every device.

## Static sites (`site` resource, `g.yyt.life/{slug}/`) — added 2026-08-30

A third project resource beside channels, catalog apps and asset bundles: a **site** is a static web build (a game's browser client, a landing page) served at `https://g.yyt.life/{slug}/` (dev: `https://dev-g.yyt.life/{slug}/`). Assets (`d.yyt.life`) stay for game data and keep refusing `html`/`js`/`css` (decision 2026-08-25); sites get their own host. The execution notes were retired 2026-09-06 (`local/todo-archive/23-static-site-assets.md`); later-version ideas live in `todo/34-backlog.md`.

1. **One shared origin, path-based.** Every site of every team lives under one origin. Accepted with a standing rule that the console (site page and create form) and `yyt site` help repeat verbatim: _"Every site on this host shares one origin: another site here can read this page, its storage and its in-memory state (same-origin frames). Never keep a credential (JWT, API token) in localStorage, sessionStorage or IndexedDB; use short-lived tokens minted per session and treat this host as untrusted."_ A same-origin frame can read another site's page, so "in memory" is no defence either — the rule buys short-lived, per-session tokens and nothing more. Per-site origins are the real fix; since 2026-09-26 every site also has one (see _Site domains_ below), and the path URL keeps this rule.
2. **Slug**: nine random `[a-z0-9]` characters minted at creation, unique, opaque, never chosen by the caller and never changed — except that a claimed name replaces it (_Site domains_ §2, 2026-09-26). A site also has a team-unique `name` (same rule as bundles) for humans and the CLI.
3. **Mutability: one live tree per site, no history.** A deploy uploads the new file set over `{slug}/`, deletes every object under the prefix that the new set does not contain, then invalidates `/{slug}/*` on CloudFront. No per-deploy paths, no rollback: redeploy the previous build. Every deploy is recorded (`site_deploys`: actor, zip bytes, extracted bytes, file count, status, timestamps) so usage per team/project/member is one query; the number of sites per project is unlimited until that query says otherwise.
4. **Upload: one zip per deploy, ≤ 5 MiB**, presigned PUT with the size and `application/zip` signed in, then `commit`. Extraction runs in a separate console Lambda (`siteDeploy`, async invoke, one at a time) because it can exceed API Gateway's window; `commit` answers **202** and the client polls the deploy. Worker limits: ≤ 2000 entries, ≤ 50 MB extracted, stored/deflate only, zip-slip guard (no `..`, no absolute paths, no backslash, no symlinks); `__MACOSX/` and dot-files are dropped; a zip that wraps everything in one directory (no root `index.html`) is unwrapped. Content types come from a site allowlist by extension (html, js/mjs, css, map, json, wasm, data, ico, svg, png/jpg/webp/gif, woff2/woff/ttf, mp3/ogg/wav, txt, unityweb; `.br`/`.gz` set `Content-Encoding` with the inner type); unknown extensions are stored as `application/octet-stream`, never refused. `Cache-Control`: `index.html`/`*.html`/`*.json` → `no-cache`; hashed build output (`assets/`, `_app/immutable/`, `static/` names carrying a hash token) → `public, max-age=31536000, immutable`; everything else `public, max-age=300`.
5. **No SPA fallback in v1** (hash routing or plain pages); a reserved `spa` mode later drives a CloudFront Function that rewrites dot-less paths under `/{slug}/` to its `index.html`. That function exists since 2026-09-27 (the path host's `…-path-host`, _CDN cost guard_ §11), so the mode would be a branch in it. The console and CLI show `publicUrl`, `basePath` (`/{slug}/`) and build hints (vite `base: "./"`, Flutter `--base-href /{slug}/`; absolute `/assets/…` references break on the path URL and work on the site's own host, _Site domains_ §10).
6. **Runtime config is a file in the build** (`config.json` beside `index.html` for the sample): API base, gateway URL, channel ids — all public. The console injects nothing and a site never receives a token from the platform.
7. **Catalog `web` platform is removed**: the catalog keeps binary bundles only. `web` leaves `CATALOG_PLATFORMS`, its tags (`entrypoint`, `mount_path`, `spa_fallback`), the `.zip` rule, CLI help and SPA types, and the DB enums through a `-- contract` migration whose preflight refuses while any artifact or pending upload row still says `web`.

This is the per-site origin _Static sites_ §1 deferred. Settled by the owner on 2026-09-26 (`todo/42`), including the redesign away from a CloudFront KeyValueStore the same day: its API is billed per call ($1 per 1,000), so any mapping written on every name change has an unbounded cost under a rate limit alone.

1. **The name is the storage prefix, so the edge needs no lookup.** A console-stack CloudFront distribution (IaC, beside the hand-made `g.yyt.life` one) answers `*.g.yyt.life`; a viewer-request CloudFront Function checks the Host against the name grammar and the stage suffix, refuses any path the zip grammar cannot produce (no `%`, no dot segments, no `//`), and prefixes the path with `/{label}` (a path ending in `/` gets `index.html`). Its origin is the site bucket's S3 **REST** endpoint (read through origin access control since 2026-09-27, _CDN cost guard_ §11; no website features): no directory redirects and no bucket `ErrorDocument` apply, a directory must be linked with its trailing slash, and a missing object is S3's 403. Nothing is written at the edge when a name changes; the only per-request cost is the function invocation. The flip side is that **S3 cleanliness is a security property**: anything left under a valid label is served on that label's origin, so every path that gives a prefix up also empties it (§6).
2. **Claiming a name moves the site.** `PATCH /sites/{site}` with `domain: "<name>"` renames the site's prefix from its current slug to the name; `domain: null` moves a named site back to a fresh random slug (a no-op on an unnamed one). A site with files is moved by the `siteDeploy` worker as a **move deploy** (a `site_deploys` row with `move_to`/`move_from`: copy every object, switch `sites.slug`, delete the old tree, invalidate its path on the path host), answering 202 with `movingTo` while it runs; an empty site is renamed at once (200). **Every rename is a `site_deploys` row and counts against the upload caps** (`SITE_DEPLOYS_PER_HOUR` per site, `SITE_DEPLOYS_PER_MEMBER_HOUR` per member), which is what bounds its cost: a move costs what a deploy costs. The old URLs (both hosts) stop working when the move completes, except in a returning visitor's browser whose page a service worker controls until it next updates. This supersedes "never changed" in _Static sites_ §2: a slug is still minted at random and never chosen by the caller; a **name** is chosen, and replaces it.
3. **Grammar**: 3–32 characters, `^[a-z0-9][a-z0-9-]{1,30}[a-z0-9]$`, no `--` anywhere (so no `xn--` punycode label). Input is trimmed and lower-cased; the stored value is byte-exact (`utf8mb4_bin`). Refused with 400: a reserved list (platform host labels and their `-dev`/`dev-` forms, mail/DNS/abuse role names; the code's `SITE_NAME_RESERVED` is the list), sign-in and admin words as a hyphen-separated token (`my-login`), and any name containing `yyt` or `yingyeothon`. A prefix that already holds objects nobody recorded (a hand-published legacy game) is recorded as nobody's on first sight and refused as taken.
4. **One name per site, globally unique.** The site's slug column is the uniqueness; a claim is also refused while a move in flight writes to or empties that prefix, or while an earlier tree under it is still being purged (409, `details.reason: "domain_cleaning"`, only when the purge the API tries inline fails).
5. **A name that served never passes to another team.** The `site_names` ledger records every name a team claims, and keeps every prefix a site gives up **once it served files** — recorded when a deploy or a move first writes to it, so it is history, not a listing at release time — (a released name, a random slug a move left behind, a deleted site's slug) against its team for good: only that team may claim it again. A deleted team's rows stay with no team and nobody can claim them. The reason is the browser, not only OAuth: an origin's localStorage, IndexedDB, cookies, service workers and permission grants outlive any hold, and an auth channel's `redirectAllowlist` or a printed QR code can outlive it too. A prefix that never served files has no browser state, so it is not kept: a name let go before its first deploy is free again at once, and an empty site's random slug is never recorded — which is also what keeps claim/clear loops from filling the ledger. The one release of a kept name is a **platform admin's** (`POST /admin/site-names/{name}/release` with a required reason, global audit log): the recovery for a deleted team's names, a squatter's, or a legacy prefix removed on purpose. It refuses while a site uses the prefix and empties the prefix first; the per-site host is not invalidated, so the next owner's origin may serve cached objects of the old one for up to its 300 s edge TTL.
6. **Emptying**: a move deletes the old tree after the switch, a failed move deletes what it copied, and a delete wipes the site's prefix. Anything that survives a crash is emptied by the daily sweep (`runSiteNameSweep`: released rows not purged since their release, 50 a day, one batched invalidation); a claim over the team's own uncleaned prefix empties it inline first. A stale move is healed from the site row: switched means `live` with `cleanup_failed`, not switched means `failed` and its target released.
7. **Cap: 20 names per team**, counting names in use and released names the team keeps from the last 30 days (409 `conflict` with `details.reason: "domain_cap"` and the team's counted names). Reclaiming one of the counted names does not add to the count. Random slugs never count.
8. **Rate: one name request per team per second**, and per member budgets that outlive a deleted site. Claim, change and clear take a team-keyed Redis slot (`console:{stage}:sdrl:{teamId}`, `SET NX`, TTL 1 s) after validation and before any write; a busy slot is 429 `rate_limited` with `details.retryAfterMs`. A 409 spends the slot, a 400 does not. A same-value request on an idle site is a no-op and takes nothing; while a move is in flight any domain change is 409. Name/description-only PATCHes and deletes are not gated. Each member may also make **30 name claims per day** (`sdcm:{memberId}:{day}`, TTL 2 d) and start **60 deploys or renames per hour** (`sdbm:{memberId}:{hour}`, TTL 2 h) across every site and team: the deploy rows the hourly cap counts cascade away with a deleted site, so without a counter a create/deploy/delete loop never met it, and the daily claim budget is what bounds how fast one account can make names permanent. Redis down is 503.
9. **Caching on the per-site host**: the distribution caps the edge TTL at 300 s and is never invalidated, so a deploy, move or delete shows on `{slug}.g.yyt.life` within five minutes (browsers still honour the object's own `Cache-Control`). The path host keeps its per-deploy invalidation.
10. **Views**: a site gains `domain` (the claimed name, or null), `hostUrl` (`https://{slug}.{suffix}/`, or null on a stage without the per-site host), `hostSuffix` and `movingTo`; a deploy gains `kind` (`upload`/`move`), `moveTo`, `moveFrom`. `publicUrl` and `basePath` stay the path URL and follow the slug. **The primary link is `hostUrl` only for a named site** (`domain ? hostUrl ?? publicUrl : publicUrl`), in clients and in a show entry: an unnamed site may be a `--base-href /{slug}/` build that only works on the path host. Build hints: a relative base (`./`) works on both hosts, `/` only on the per-site host, `/{slug}/` only on the path host — and a claim changes the slug, so a `/{slug}/` build must be rebuilt.
11. **The per-site host exists only where the owner turned it on**: a stage whose SSM `site-host-cert-arn` names that stage's own us-east-1 certificate for `*.g.yyt.life` (prod) or `*.dev-g.yyt.life` (dev) — one certificate per stage, so neither stage's renewal depends on the other's validation record (owner step, `rules/deployment.md`). Without it `hostUrl` and `hostSuffix` are null; claiming a name still works and renames the path URL.
12. **Same-site, not same-origin.** Every `{slug}.g.yyt.life` is a sibling subdomain of the console and auth hosts, so it is **same-site** with them: the console's `__Host-` cookies cannot be overwritten from it (the cookie parser trims ASCII whitespace only and drops a prefixed name seen twice) and the console keeps its exact-Origin check (`identity.ts`), which must never become a suffix match. A game that sets its own cookie on its host should use `__Host-`, since siblings can set `Domain=g.yyt.life` cookies. The structural fix is a Public Suffix List entry for `g.yyt.life` / `dev-g.yyt.life` (owner step, months of lead time). Out of scope, _not yet_: bring-your-own domains (each needs its own certificate), and a per-member cap on kept names (a served name costs a deploy, and the admin release is the recovery).

## Show (console) — added 2026-09-01

A **show** is a gallery: a place where members put up what they built and everyone else looks at it, comments and likes. The design notes and execution checklist were retired 2026-09-06 (`local/todo-archive/24-show.md`); the decisions below are the record.

1. **A show is platform-global, like an event, not a project resource.** It has an owner (its creator), an ACL model, a markdown page and a list of entries; it belongs to no team and no project. This is why _"permission is team membership, nothing finer"_ (see _Teams and projects_) and the 2026-08-26 withdrawal of the catalog's per-user grants (see _Binary catalog_) are not contradicted: both govern resources that hang off a project, and `teamAccess` is not on a show's axis at all. A show carries its own, much smaller grant table instead. The access check for the **thing an entry points at** is unchanged — it is still `projectResource`.
2. **ACL model, chosen at creation and editable afterwards: `public` or `member-only`.** `public` is readable by anonymous visitors; `member-only` needs a signed-in **non-`pending`** member. `pending` is deliberately excluded here even though it may read elsewhere: sign-up is self-service, so a `pending`-readable show would mean "anyone holding a GitHub account", and what a show hands its readers is a permanent unauthenticated CDN link to a team's work. **Narrowing the model is always allowed; widening `member-only` to `public` is refused with a 409 once the show has entries** — people submitted to the audience they were shown, and a one-field edit must not republish their work to a larger one. Everything a show contains inherits its readability: the entry list, an entry, its comments, its likes and its screenshot redirect. Failing that check is **404**, never 403 — the show is not revealed. There is a third, implicit level: a signed-in member who can read a show but holds no grant is **403** on writes, because pretending a page they are looking at does not exist would be a lie.
3. **Write is granted to one member at a time; there is no read grant.** `show_grants` is `(show, member)`. The owner and platform admins hold write implicitly. Since `public` and `member-only` already decide who may read, a read grant would express nothing, so the table has no permission column — a row _is_ write.
4. **An entry submits exactly one first-class deliverable.** The target is a catalog app, an asset bundle or a site — whatever the platform manages as a project resource — and an entry references **one** of them (since 2026-09-28: an encrypted bundle is refused, because its link is ciphertext and a gallery exhibits nothing with it); several deliverables cannot be bundled into a single entry, and a second one is a second entry. The submitter must be able to write the target (`projectResource`, `min: "member"`, and deliberately **not** `secret: true`, so submitting is not a privileged operation and a seatless platform admin may still do it). The same target may be entered in **several different shows**; within one show it is unique (`(show, kind, target)`).
5. **Submitting is an act of publication.** The target's name and its link are shown to everyone who can read the show, including anonymous visitors of a `public` show, even though the target itself is a team-private resource. The submitter is choosing to exhibit it; a gallery that hides what is on display has no purpose. **The link is pinned at submit time for a catalog app and an asset bundle** — the exhibited artifact and version, not "whatever that app holds today" — so a build the team ships months later is not published by an entry nobody touched; moving an entry forward is an explicit edit. A **site** links live, because a site is already public hosting whose whole content is one mutable tree, and so does a **live** asset bundle (since 2026-09-28), which has no version to pin.
6. **A deleted target does not delete the entry.** There is no foreign key from an entry to its target: the entry snapshots the display name at submit time, and a team stays free to clean up its own resources. Once the target is gone the entry keeps its page, its screenshots and its comments, and is marked as no longer available. The alternative — refusing to delete a resource that is in someone's show — would let a show hold a team's resource hostage. The team keeps a lighter remedy too: **anyone who can write the target may delete the entry that exhibits it**, so a team is never forced to destroy its own work to take it off a wall, and a resource page says which shows it is in.
7. **Lifecycle is a manual close, reversible.** A show has no status enum: it is open until its owner or an admin closes it, and closing can be undone. Closed means read-only — no new or edited entries, screenshots, comments or likes — and it is a **409, not a 403**: the caller is allowed, the show is not accepting. Closing changes nothing about who may read; readability is the ACL model's business alone.
8. **Any non-`pending` member creates a show; only a platform admin deletes one.** The same split as events, for the same reason: a show accumulates other people's entries and comments, so removing it is an operational act. An owner who is finished closes the show. Deletion writes a **bounded metadata snapshot** — the show, and the ids, titles, authors, object keys and counts of its grants, entries, screenshots, likes and comments — into `audit_log.detail_json` **before** anything is removed, with a byte cap and a `truncated` flag. Markdown bodies are not copied: at the caps below a full copy would be hundreds of megabytes against a 16 MB column, so the insert would fail after the S3 objects were already gone. The snapshot is what is left of a deleted show, and it is deliberately a record of what existed rather than a restorable backup.
9. **Screenshots: at most three per entry, replaced wholesale.** They are uploaded through the proven presign → PUT → `commit` flow into the console stack's existing private media bucket (the one that already holds event posters and site staging), under a `shots/` prefix, and delivered by an API route that redirects to a short-lived presigned GET, so screenshot visibility follows the show's. Server-minted keys, png/jpeg, 5 MB each, `Content-Type`/`Content-Length` signed into the PUT and re-checked on `commit`. **One `commit` sets the whole list**: an upload that fails leaves the entry with exactly the screenshots it already had, so there is no half-replaced state. Replaced objects are deleted immediately and a failed delete is retried by the daily sweep.
10. **Comments and likes are for signed-in non-`pending` members who can read the show.** Comments are markdown with the same caps as everywhere else, edited and deleted by their author, a show owner or an admin. A like is a set membership — idempotent, one per member per entry — and counts are derived, never stored, so nothing can drift out of step with a cascade. Entry lists sort by newest or by likes.
11. **An event spawns a show on a button, not on a schedule.** The event's owner or a platform admin creates it, which is what the end of the waiting period means in practice; the show takes the event's title and the two stay linked, at most one show per event. The button is gated on **the event already being visible to an anonymous visitor** — the same predicate the event routes use, evaluated on the settled row — not on "published" and not on a status name. Publication is not the fact that matters: an event is anonymous-visible only while `waiting`, `opened` or `closed`, so an event still taking date votes, and an event cancelled after publication, are both invisible to the world while being perfectly "published". Opening a `public` show from either would broadcast its title (`rules/security.md`, "a status enum is not the whole visibility rule"). Deleting an event does not delete its show — the link is cleared and the gallery survives. The event page renders its show's entries below the page, and the page history collapses by default to make room.
12. **Operator intervention is logged and is not anonymous.** A platform admin may edit or delete any show, entry or comment. A **reason** is required, and stored with the action in the global audit log, whenever an admin acts beyond their own content: moderating something they do not own, deleting a show (which destroys other people's entries even when the admin owns the show), and submitting an entry for a team they hold no seat in — the bare admin override lets them publish any team's private work, which is a larger act than reading it. `audit_log` gets its first read route in the process — admin-only, filtered by action prefix, target, actor and time, cursor-paged, `no-store` — because a log nobody can read is not an operational tool. Moderation is visible to operators only; the affected page carries no badge.
13. **Caps** reuse the existing numbers where one exists: markdown body 20 KB, comment 10 KB, screenshot 5 MB. New: 5 open shows per member, 200 entries and 100 grants per show, 200 comments and 3 screenshots per entry. Every recorded write takes the same per-member 500 ms slot as team and event writes.
14. **Ids are `sh_`, `se_`, `sc_` and `ss_`, all ULID-based**, because these rows are listed by `(created_at, id)` and only a time-ordered id makes that ordering total. They are deliberately **absent** from the `ID_LIKE` name grammar, exactly like the event prefixes: that grammar exists so the CLI can tell a team-scoped resource _name_ from an id, and shows are addressed by id only.

## List sort and filter (console) — added 2026-09-02

1. **Ordering and search are server-side, and they live in the data layer.** Every console list route takes `sort` and `order` (`asc` | `desc`), and the project/title/description lists (`GET /teams`, `/teams/{team}/projects`, `/events`, `/shows`, `/teams/{team}/discussions`, the issue lists, `/channels`, `/projects/{prj}/channels` and, since 2026-09-28, `/catalog/listings`) also take `q`. The repository (`@yyt/console-db`: Prisma implementation, memory fake and the shared contract test) applies them; a route only validates the query and passes it through, and the SPA never orders or filters rows itself. `sort` values are the response's own field names — anything else is a 400 — `order` defaults to `asc` and is ignored without `sort`, and `q` is a trimmed, case-insensitive `contains` of at most 100 characters over name/title (plus description for teams and projects, plus the project name for channels).
2. **A list keeps its historical default order when `sort` is absent**, so the CLI, which sends none of these parameters and resolves names from the whole list, is unaffected.
3. **MySQL semantics are the contract, mirrored by the fake**: `NULL` is the smallest value (first ascending, last descending — Prisma's `nulls:` is not rendered for MySQL), `ENUM` columns order by declaration, text columns by their collation (`utf8mb4_unicode_ci` unless the column is `_bin`), and every order breaks ties on the row id in the same direction.
4. **Values that exist only after the read — an event's or a channel's effective status, a version's link counts, a seat's `since`, an artifact's version tag — are ordered inside the repository after the fetch**, with the same pure derivation the route uses (it moved into `console-db` for that reason). They are still bounded by the list's scope cap, so this is a sort over at most a few thousand rows, never a scan. A caller must pass `now` for a derived-status sort.
5. **`q` on a `MEDIUMTEXT` description is a scan of the bodies inside the scope**, and is offered only where the scope is capped (5 teams per member, 20 projects per team by default; the hard value of `team.projects`, 1,000, still bounds it). No list gains an index for `q`: a `%q%` match cannot use one, and every scope already has its own index.
6. **`GET /shows` keeps its keyset cursor and takes `q` only** — the filter runs inside the same query as the cursor predicate so pages stay disjoint and complete, and a client re-sends `q` with `cursor`. Sorting a cursor-paged list by another column is not offered. The kv entry lists (2026-09-03) follow the same rule: keyset order on the key, `asc`|`desc` only, `prefix` and `owner` filters re-sent with the cursor.
7. **The SPA sorts by clicking a column header** (`aria-sort` on the header, ascending → descending → the server default; time and count columns start descending) and searches from a debounced text filter that applies as it changes; the rows on screen stay while the re-fetch is in flight instead of a skeleton.
8. **The side navigation nests the caller's teams under _Teams_** as a flat indented group of links (Mantine's `NavLink` with children swallows the click, so a collapsible parent could not itself navigate). Every team create/rename/leave/delete invalidates the shared teams query so the group never shows a stale name.

## Key-value store (`kv`) — added 2026-09-03

A **collection** is a project resource (beside channels, apps, bundles and sites) holding JSON values by key. It exists for the two things a game needs that are neither a per-player document nor ephemeral: values the team writes and every player reads (announcements, tuning), and small per-player records a client may write itself (progress, preferences). The design record is `docs/kvstore.md`; the execution checklist was retired 2026-09-06 (`local/todo-archive/33-kvstore.md`).

1. **Served by the state stack, not a sixth one.** `/kv/*` lives on `doc{-dev}.yyt.life` beside `/s/*`: the MariaDB connection budget is 55/60 (`rules/data.md`), and the state stack already resolves both credentials the store needs. The state account's grant widens by exactly three tables (`SELECT` on `kv_collections`, DML on `kv_entries` and `kv_keys`); console still owns the schema and every migration (`m0014_kvstore`, additive). The API Gateway throttle (20 rps / 40 burst) is therefore **shared with the doc store**, and — new — a player's JWT can now spend it on writes, not only on reading its own document.
2. **Three principals.** `team` is a console session or API token with team membership (`projectResource`; SPA and `yyt kv`). `server` is the auth channel's existing **doc apiKey** (`yds.{channelId}.{random}`), which thereby gains server rights over every collection of the channel's project — reading and writing any owner's entries — so revoking it cuts KV as well as documents; the doc-key block names the KV path too. `owner` is a player's channel JWT (`sub` = userId). Both API principals are bound to their auth channel's **project**: a collection in another project answers 404, an expired, disabled or deleted channel 401, exactly as the doc store. A project with several auth channels shares its collections between them.
3. **Two scopes per collection, fixed at creation.** `readScope` and `writeScope` are each `team` (console/CLI only; the API answers 403), `server` (the doc apiKey and the console, never a player — added 2026-09-08, #5 below), `project` (every player of the project) or `user` (the entry's owner). A collection is **per-owner** when `writeScope` is `user` **or** `readScope` is `user` (#5); every entry then lives in its owner's namespace (`(collection, ownerId, key)`), and otherwise the collection has one shared namespace (`ownerId = ""`), in which `project` lets any player overwrite any key — an accepted, documented property, not a bug. The `server` principal writes a user namespace on behalf of any owner (`/u/{ownerId}/…`); an `owner` writes only its own, and may say `me`. A `readScope: project` + `writeScope: user` collection (profiles, leaderboards) **lists every owner's entries and owner ids to every player** — the opposite of the doc store's "no list route" rule, stated here on purpose: a public profile that cannot be enumerated is not public. It first said "owner ids are opaque hashes" as well, which was **false until 2026-09-09** — the derivation was unsalted, so this route already handed any player of the project a list of ids that could be walked back to provider accounts offline (_Player ids are salted per auth channel_). It is true for a channel with a `userSalt` and stays false for one without. The cross-owner `?prefix` search this opens is served by an index (`kv_entries_prefix` on `(collection_id, k)`, migration `m0015`) and otherwise accepted under the stage throttle (owner decision, 2026-09-06). A collection whose scopes are **both** `team` answers 403 on the API even for `GET /kv/{col}` (the meta route): no API principal could ever touch its entries, so the API has nothing to say about it (owner decision, 2026-09-06 — until then the meta route answered 200 shape-only). **`readScope`, `writeScope` and `encrypted` never change after creation**: the state stack writes while console edits, and a shape change mid-flight would mix plaintext with ciphertext or shared rows with owner rows in one table; the change path is delete and recreate. Names, descriptions and caps stay editable.
4. **Conditional writes are optional, and require the right to read.** `PUT` returns and accepts `ETag`/`If-Match` (409 with the current version on mismatch) and `If-None-Match: *` (create-only); an unconditional `PUT` is allowed and is a bounded compare-and-set internally, so the version a caller gets back is always `read + 1`, never re-read (`rules/data.md`). `PATCH {incr, min?, max?}` adds a safe integer to a stored safe integer (409 `not_a_number` / `overflow` / `out_of_range` otherwise, #7). Because every one of these reveals a value or its existence, they are **403 on a collection the caller cannot read** — a write-only inbox takes plain `PUT`/`DELETE` and nothing else, and no 409 body ever carries a version it may not read. Two later exceptions, both from the mail shape (#6): a conditional header on a **cross-owner** write is a 400 before that 403 (the write can only ever be create-only, so there is no version to compare), and `409 exists` does tell a cross-owner writer that a key is taken — which is why such a key must begin with the writer's own id, so the only existence it reveals is its own. `PATCH`'s `out_of_range` carries the stored **value** in `details.value`, never in `details.current` (which means a version everywhere).
5. **Values are JSON, stored as sent, 16 KiB each**, the doc store's byte-exact rule (`null` included). Keys are identifiers, not data: `[A-Za-z0-9][A-Za-z0-9._:-]{0,127}`, no `/` and no `@`, because key names are plaintext even in an encrypted collection and appear in console tables — the request log records the matched route pattern, never the path, so neither keys nor owner ids reach CloudWatch. Audit rows for console entry writes carry the collection and owner, never the key or the value.
6. **TTL is per entry and relative** (`?ttl=` seconds, 1 s – 366 d): an expired entry is invisible to every read and to the cap, `PUT` over it is a create for `If-None-Match` purposes, but the **version keeps climbing** (an expiry never resets it, or a stale `If-Match` could land on the reborn key). Omitting `ttl` on an update keeps the existing expiry; `ttl=0` clears it. Reclamation is the console's daily sweep, per collection, in fixed batches; a collection that hits its cap purges its own expired rows once inline before refusing.
7. **Caps are per collection and editable** in console and CLI: `maxEntries` (default 10,000, at most 100,000) bounds everyone, `maxEntriesPerOwner` (default 100, at most 1,000) bounds what one **player** may create in a user namespace, so one JWT cannot fill a collection and lock its teammates out (`server` and `team` are bounded by `maxEntries` alone); 20 collections per project; 100 rows per list page. The two 409s are distinct (`owner_full` / `collection_full`).
8. **`encrypted` is a promise about who can read values, kept by key placement.** A stage KEK lives only in the state stack's SSM (`kv-kek`, generated once, kept across bootstraps unless explicitly rotated, backed up in the private ops repo — losing it loses every encrypted value for good). Each encrypted collection gets its own DEK, minted by the state stack on first write, wrapped by the KEK and stored in `kv_keys`, a table console never selects. Values are AES-256-GCM with the collection, owner and key as associated data, so a row moved in the database does not decrypt in another slot; a row whose form disagrees with its collection's flag is a 503, never served as data. Console and the CLI therefore see an encrypted collection's keys, owners, sizes and times and may delete entries, but can neither read nor write a value — which is why `encrypted` with a `team` read or write scope is refused at creation (nobody could read, or nobody could write), and why creating an encrypted collection on a stage without a state stack is 503 `state_not_configured`. A stage-wide kv outage (lost KEK, missing grant) is a 503 `AppError`, invisible to a Lambda `Errors` alarm — so the state stack's one alarm slot **widens** into a log-metric alarm that matches the unhandled-error line and the kv outage lines alike, instead of adding an 11th alarm (owner decision, 2026-09-06; `rules/serverless-aws.md`).
9. **Lifecycle.** Deleting a collection is a soft-delete that frees the name at once and drains the rows in bounded batches, inline first and by the sweep if the request budget runs out — a cascading `DELETE` of 10,000 off-page rows cannot fit MariaDB's 5 s statement limit. Entries a player wrote **die with their auth channel's hard deletion** (`kv_entries.channel_id`, purged by the sweep and by the explicit delete route beside `deleteChannelDocs`): a userId means nothing outside the channel that derived it, and orphan rows nobody can address are the alternative. The purge takes the **whole owner namespace**, console-written rows included (owner decision, 2026-09-06): rows the console put under an owner id (`channel_id = NULL`) go with the owners the dead channel's own rows name, scoped to the channel's project — a row the console meant to keep may go with them, which is the accepted price of never leaving an unaddressable owner behind; an owner the console alone ever wrote (no API row names it) still survives, because nothing maps it to a channel. Rows the console or a server wrote under a shared namespace outlive channels. Project and team deletion is refused while collections exist (the `RESTRICT` rule every resource follows; an older console bundle answers 503 there instead of 409 once collections exist, noted in `rules/deployment.md`).
10. **Every surface.** Console API `POST|GET /projects/{prj}/kv`, `GET|PATCH|DELETE /kv/{id}`, entry routes under `/kv/{id}/entries` (table, single, put, delete, delete-by-owner); SPA tab on the project page plus a collection page with the entry table; `yyt kv …` mirrors the console routes one to one; the KV API on the state stack is `GET /kv/{col}`, `GET|PUT|PATCH|DELETE /kv/{col}/entries[/{key}]` and the `/kv/{col}/u/{ownerId}/entries[/{key}]` twin, where `{col}` is the id **or the collection's name** (one plain segment by the console's name grammar; resolved within the caller's project; the same 404 on every miss — owner decision 2026-09-06, so a game addresses `announcements` rather than a ULID; the console's `api.namePath` and `yyt kv get`'s `apiName` print it). Ids are `kv_` + ULID and the prefix joins `ID_LIKE` on both sides. `KvStoreDb`/`kvstore` in code, because `Kv`/`kv` already name the Redis client.

## Serverless clients: leaderboard, kv `server` scope, callback-less match, social — added 2026-09-08

Assessment in `docs/serverless-client.md`: a client-only team (web site or mobile app, no Lambda) can sign in, host, load data, form rooms and persist its own progress today, but nothing on the platform can hold a value a player's JWT cannot write, sort anything, or express a relation two players both approve. Four additions close that, all owner decisions of 2026-09-08. Execution: `todo/36`–`todo/39`.

1. **Leaderboard is a dedicated project resource, not a kv flag.** `leaderboards` (`lb_` + ULID, team-unique name by the kv name grammar) is created in console/CLI and served by the state stack under `/lb/{board}` (`{board}` = id or name, resolved within the caller's project, every miss 404 — the kv rule). Scores live in MariaDB (`leaderboard_scores`; the primary key is `(board, period, period_key, owner)` and the one secondary index `(board, period, period_key, score)` — this sentence omitted `period_key` until 2026-09-10, and **its position before the key** is load-bearing: a retention delete keyed on `period_key` alone would walk the whole board under `utf8mb4_bin` and could take the alltime row with it. A second index `(board, owner)` was added the same day so that removing one owner from every bucket is a lookup rather than a scan), never Redis: `allkeys-lru` plus mandatory TTL would evaporate a ranking. Rejected: a `ranked` kv collection (sorting a JSON field needs an extracted column and bends the kv grammar into rank semantics) and a Redis sorted set (needs a MariaDB backing layer anyway).
2. **Submission is a per-board setting, `submit: server | owner`.** `server` = the auth channel's doc apiKey or the console/CLI; `owner` = a player's JWT for its own row only (`/scores/me`). A serverless team runs `owner` and accepts that scores are trusted; a team with a Lambda runs `server`. Per board also: `rule: best | latest | sum` (how a new score meets the stored one), `order: desc | asc` (`asc` for times), `periods` ⊆ `{alltime, daily, weekly}` (at least one), `maxEntries` per period bucket (**default 2,000, hard 10,000** — lowered from 10,000/100,000 on 2026-09-09, before any board existed: one board's worst case is `maxEntries × (1 + 2 × (retainPeriods + 1))` rows on a MariaDB five stacks share — 11 buckets at the defaults, 27 at the maximum, since retention keeps the current bucket of each period as well as `retainPeriods` past ones (the `+ 1` was missing from this sentence until 2026-09-10) — and `maxEntries` alone bounds the `count` behind every `rank`). Scores are safe integers; `sum` saturates at ±(2^53−1). An optional `meta` is a **JSON text field** ≤ 1 KiB (display name, a build id), sent as a string and stored byte for byte — the platform never parses it, exactly as a kv `valueText` and a state document are stored (it does refuse a raw control character, added 2026-09-10: `meta` is printed into the CLI's tables, where `textsafe.Clean` keeps `\n`, so a newline forges a row — and no well-formed JSON text can carry one anyway, which is the precondition the no-`Clean` exemption assumes) (2026-09-09: taking it as an object would mean re-encoding, and `JSON.stringify(JSON.parse(x))` loses integers past 2^53 and duplicate keys). The **doc apiKey may submit on an `owner` board too**, on anyone's behalf: it is the same widening the kv `user` scope already grants a server key, and it is the only way to correct a row — the console and the CLI read and delete scores but **never write one**, so every score row carries the `channel_id` of the credential that wrote it.
3. **Periods are computed by the platform in `Asia/Seoul`.** One submission updates every configured period at once; keys are `""` (alltime), `YYYY-MM-DD` (daily) and ISO `YYYY-Www` (weekly, Monday start). Every read carries `periodKey` and `periodEndsAt`, so a client never derives a bucket from its own clock. Past buckets are kept for `retainPeriods` (default 4, **max 12**) and dropped by a sweep with its own budget and cursor, never the kv sweep's. Rejected: a game-chosen period key (client clock, forgeable by a serverless game).
4. **Reads are open to the project.** Any credential of the project (`server`, `owner`, team) may `GET /lb/{board}/top?period=&limit=1..100&offset≤1000` and `GET /lb/{board}/scores/{ownerId|me}?period=` → `{score, rank, total}`; rank is `1 + count(better)`, a bounded query at the cap. Two console-side details settled while implementing (2026-09-10, `docs/leaderboard.md`): the console has the **same** per-owner read (`GET /leaderboards/{id}/scores/{ownerId}`), because an operator hunting one player on a full board would otherwise page to row 8,000 to find them; and its own score table pages to the board cap rather than to the API's 1,000, since that ceiling is a product bound on what a _game_ should ask for. A page's ranks come from **one** `count` — the true rank of the first row, ties sharing it downward — and that computation needs the page's `offset` as well as that rank, because a page starting inside a tie has a first rank below its own offset. A ranking that cannot be listed is not a ranking — the same reasoning as the kv `project`-readable user namespace. **The "owner ids are opaque hashes" clause this decision first carried was false** (found by review, 2026-09-09): the derivation was unsalted and a provider user id is public and enumerable, so a listed id could be walked back to a GitHub account. It is opaque now because the derivation is salted per channel (_Player ids are salted per auth channel_), and a board of a channel created before that stays reversible — which is why that work ships **before** the first board. `DELETE` of a score or a period is `server`/team only, and a score delete takes the owner out of **every** bucket of the board: removing a cheat from today's board and leaving them on last week's is not a removal. A bucket is addressed by **period name** on the API (always the live one) and by name **or** past key in the console; `alltime`, whose key is the empty string, can only ever be named. Rows carry `channel_id` and die with the auth channel like kv rows; the resource dies with its project (`RESTRICT` while it exists, like every resource).
5. **kv gains a fourth scope, `server`.** `readScope`/`writeScope` may now be `team | server | project | user`; `server` is the doc apiKey **and** the console/CLI, never a player JWT (403). It exists for the collections the earlier three could not express: announcements and tuning a Lambda or a cron updates (`project`/`server`), a player inbox the server fills (`user`/`server`), telemetry only the server reads (`server`/`user`). `encrypted` is allowed with `server` on either side (the state stack holds the KEK, and a server reader exists). **`server` is only as strong as the doc apiKey's secrecy**, and the key names a project's every collection _and_ every document of its channel: a client-only game has nowhere to keep one, so `server` is for the Lambda or cron a team already has, not a scope to ship inside a build. **The namespace rule is restated**: a collection is per-owner when `writeScope` is `user` **or** `readScope` is `user`; otherwise shared. This is a widening — every existing collection keeps its shape — and it is what makes `readScope: user` + `writeScope: server|project` an inbox rather than a contradiction (the old rule "`readScope: user` requires `writeScope: user`" is withdrawn).
6. **Player-to-player mail is `readScope: user` + `writeScope: project`, with a stamp.** In that shape any player may `PUT /kv/{col}/u/{ownerId}/entries/{key}` into another owner's namespace, under four rules that together bound what one player can do to another (owner decision 2026-09-09, after three plan reviews):
   - **Create-only.** An existing key answers 409 `exists`; there is no cross-owner overwrite and no cross-owner `DELETE` or `PATCH` (403). A conditional header on such a write is a 400, not a 403 — the write is already create-only.
   - **The key must begin with the writer's own id** (`{fromOwnerId}:…`; the key grammar already admits `:`). Each sender therefore owns a disjoint subspace of every inbox: nobody can squat the key a real sender needs, and the `409 exists` that create-only implies can only ever reveal the writer's own rows. A key outside that prefix is a 400.
   - **Both ends are capped.** The write is charged to the recipient's `maxEntriesPerOwner` (409 `owner_full`) **and** to the writer's own total in that collection, the same number (409 `sender_full`, served by an index on `(collection_id, from_id)`). Without the second, one player writing one row into each of ten thousand invented owner ids fills the collection for everyone.
   - **The platform stamps the writer.** `from` is the writer's `sub` (`server` for an apiKey write, `team` for a console write), re-stamped on **every** accepted write and never settable by the client, and `at` is the row's existing `updatedAt`. Both are returned only on a per-owner collection (`X-KV-From`/`X-KV-At` on a single GET, `from` in list rows), so a shared-namespace collection stays exactly as anonymous as it was. `from` is server-set, not cryptographically bound (it is outside the value's associated data), and it is **not durable**: the recipient may overwrite its own row, which replaces the stamp with its own. A successful cross-owner write is a `204` with no `ETag`, because the writer may not read the collection.

   Spam beyond those caps is bounded by the stage throttle only — accepted at this scale.

7. **`PATCH {incr}` takes optional `min`/`max`**: a result outside the range is 409 `out_of_range` with `details.value` (the stored number — `details.current` means a version everywhere else and is not overloaded), so a currency cannot go below zero in one atomic step. They are a **per-request guard, not a stored invariant**: nothing remembers them between calls, a missing counter still starts at zero (so `min: 10` makes the first `incr: 1` a permanent 409), and a value already outside the range cannot be repaired through `PATCH`. **`GET /time`** on the state stack answers `{now, epochMs}` unauthenticated with `no-store` — `now` is an ISO-8601 UTC string, `epochMs` an integer in **milliseconds**, while every other timestamp the platform emits (`expiresAt`, `updatedAt`, `x-kv-expires-at`) is in seconds. It is the platform clock every client can trust for resets and event windows; call it **without a bearer** (a token would cost the route a channel lookup) and keep the offset rather than polling.
8. **The match service works without a callback.** `callbackUrl` becomes optional on a match channel; when absent, a match delivers `{type:"matched", matchId, partial, result: null, members:[{userId}]}` and nothing is posted anywhere. `members` is added to the `matched` frame in **both** modes (additive) — including **channels that already exist**, which start disclosing the roster to their own party on the next match-stack deploy: a `userId` is an opaque per-auth-channel hash the lobby roster and a `readScope: project` collection already hand out to the same players, and a ticket only ever names players concurrently queued on that channel. The documented client recipe (preconditions and failure modes in `docs/serverless-client.md`): the member with the lowest `userId` runs `party.create` on the game's lobby channel and invites the rest by `userId`; everyone must already hold a lobby socket, since an invite to an offline user is `unknown_user`, and the lobby's `partySizeMax` must be at least the match channel's `partySize`.
9. **Social is a state-stack API scoped to the auth channel**, like documents — not like kv and leaderboards, which are scoped to the _project_, so a project running two auth channels has two disjoint friend graphs over one kv collection. `social_profiles` (`(channel, owner)`, `displayName` ≤ 32 characters, `avatar` ≤ 64 characters, an opaque string) and `social_relations` (`(channel, from, to, state ∈ requested | dropped | friends | blocked)`). Routes: `GET|PUT|DELETE /social/me/profile`, `GET /social/profiles?ids=` (≤ 50, any player of the channel — a profile is public within its channel, not enumerable), `GET /social/friends`, `GET /social/requests`, `GET /social/blocks`, `POST /social/requests {to}`, `POST /social/requests/{ownerId}/accept|decline`, `DELETE /social/requests/{ownerId}` (withdraw), `DELETE /social/friends/{ownerId}`, `PUT|DELETE /social/blocks/{ownerId}`. A block hides the blocker from the blocked (requests refused as 404, never "blocked"). Caps: 200 friends, 100 pending requests **in each direction**, 500 blocks per player. Rows die with the channel. Six things were settled by the owner on 2026-09-10, after three plan reviews and before a line of it was written (`todo/39`): (a) **A relation may only name players who both hold a profile — except a block, which is protective and may name any player id** (a lobby roster is where a harasser's id usually comes from, and requiring them to have opted into the graph first would be backwards). The bound still holds: the _blocker_ needs a profile, so blocks are at most 500 per profiled player. Without it the 100 outgoing slots can be spent on invented 32-hex ids nobody can ever accept or decline — the "row nobody can address" the kv owner grammar exists to prevent — and `social_relations` has no ceiling at all, which is a problem for the channel purge rather than for storage: a channel that cannot be drained inside the sweep's budget leaves rows that outlive the id that gave them meaning. Tying both ends to a profile derives the relation bound from the profile cap (10,000 per channel, the document store's number and its reasoning), and it gives the product a rule worth having: pick a name before you can be added. It also means **deleting a profile deletes that owner's relations**, which is what makes "delete my data" a real answer. (b) **The 404 stays** (this decision's own sentence, kept deliberately over the reviews' objection that it is an oracle — every other target answers 200, so a 404 said "that id blocked you"). What repairs it is (a): a target with no profile answers the same 404, so the code is shared by "blocked you", "never played" and "no such id". It is **not** proof, and the platform does not claim more: a block bounds harassment, it is not anonymity, and a caller who already knows a target has a profile can still infer one. For the same reason `GET /social/profiles?ids=` does **not** hide a blocker's profile — omitting a row a caller has seen before would be a stronger and passive oracle than the one being avoided. (c) **A declined request is kept as `dropped`, not deleted**, and a pending `requested` row expires after 30 days; both are reclaimed by the social sweep, on one 30-day clock rather than two (the separate 7-day cooldown the decision first named collapsed into the request TTL when the row turned out to be the same row). Deleting on decline makes request → decline → request free and infinite, which is the console's join→withdraw loop restated (`rules/security.md`); an inbox with no expiry can be wedged for the channel's lifetime by 100 throwaway accounts. A `dropped` row is charged to the **sender's** outgoing cap and not to the recipient's incoming one, so the cost of the cooldown lands on whoever spent it — and it carries a `cooldown_until` the sender's own block of that player does **not** clear, because block then unblock would otherwise be the two calls that delete the row and start the loop again (found by review, 2026-09-10). For the same reason `DELETE /social/me/profile` takes every relation of that owner **except somebody else's block of them**: a block is the blocker's row, and deleting your profile is not a way to lift it. A decline is silent: during the cooldown a re-request answers exactly what a pending one does, and the sender's own list shows the row as pending. (d) **The doc apiKey may delete a relation or a profile, never create a relation.** `DELETE /social/u/{ownerId}/profile` and `DELETE /social/u/{ownerId}/relations[/{other}]` beside the existing `GET /social/u/{ownerId}/friends` and `PUT /social/u/{ownerId}/profile`. Relations stay the players' to _make_ — a server that could create one could forge mutual consent, which is the whole content of a friendship — but leaving channel deletion as the only moderation tool means there is no moderation tool: it also destroys every player's documents, kv rows and scores. (e) **`avatar` is a narrow grammar, not a URL**: `^[A-Za-z0-9][A-Za-z0-9._-]{0,31}(?:/[A-Za-z0-9][A-Za-z0-9._-]{0,31}){0,3}$`, ≤ 64 characters. Opaque means the platform never resolves or interprets it, not that it must accept any string: a value with a `:` or a leading `/` is a scheme or a protocol-relative URL, and a client that renders one in an `<img src>` hands every viewer's address to whoever chose the name. A `displayName` refuses `\p{Cc}`, `\p{Cf}` and U+2028/2029 (a bidi override or a zero-width joiner is a forged row in a terminal or a second player with an identical-looking name) and is **not unique** — render the ownerId beside it wherever a mistake matters. (f) The two-row transitions take the pair in a **canonical order** (`from`/`to` sorted), re-read their precondition inside the transaction, and enforce both players' caps on every path that creates a friendship, including the mutual-request shortcut (two players who request each other become friends without an accept). Without the order, two players acting on each other deadlock into a 503; without the re-read, a block that lands mid-accept is silently undone.
10. **Presence is the gateway's, read by the client.** The state stack has no Redis and gains none; the gateway adds `GET /presence?channel={lobbyId}&users=a,b,…` (≤ 50 ids — the implementation halved the 100 this sentence first named, because a friends list is polled where a party roster is read once, and each id is a Redis key; bearer = a member's JWT, per-address bucket, Redis `MGET` on the session keys — the `/parties` precedent) and the client joins presence to its friend list itself. The state stack never calls the gateway. Two properties of that route, written down 2026-09-10 because a client will otherwise assume the opposite: it is a **widening**, not a restatement of an existing surface — `/parties` proves membership of the caller's own party and the match `members` frame names players concurrently queued, while `/presence` answers for any id a holder of a valid JWT on that lobby's auth channel cares to name (it confirms, it never discovers: 32-hex only, and "offline" and "no such id" are the same answer) — and `online` means a session key exists, which after an ungraceful gateway stop is true for up to the 15-minute session TTL. Presence is a hint for a friend list, never an input to an authorization decision. The ids also have to come from the **same** auth channel the lobby names, which is what makes a friend id from `/social/friends` addressable here at all.
11. **Deferred and rejected.** Quorum-attested writes (N party members submit one identical value within T seconds) would be the only way a serverless game commits a result nobody can forge alone; deferred to `todo/34-backlog.md` as an option, contest games accept trust. Client-created topics (JWT `POST /t` + CORS) rejected: the lobby party already is the private room. The `g.yyt.life` shared-origin exposure is unchanged and is why a serverless **web** game should keep its token in memory and short; a site opened through its own host (_Site domains_, `{slug}.g.yyt.life`) has its own origin, but the path URL stays shared.

## Player ids are salted per auth channel — added 2026-09-09

A `userId` was `sha256(channelId + ":" + provider + ":" + providerUserId)` with no salt. Every
input is knowable: the channel id is the `iss` of a player's own token and sits in the game's
client config, the provider name is one of two, and a GitHub `providerUserId` is a public
sequential integer. So a `userId` was never a one-way name — anyone holding one could confirm
whose it was, and anyone holding a _list_ of them could walk the whole provider id space
offline and publish the mapping. The leaderboard's `GET /top` is what found it
(owner decision 2026-09-09, `todo/41`), but it is **not** the first such surface and the flaw is
not prospective: `GET /kv/{col}/entries` on a `readScope: project` + `writeScope: user`
collection already lists every owner id to every player of the project (_Key-value store_ #3),
and any channel without a salt is exposed there today. The lobby roster and the match `members`
frame are the narrower case — they disclose only players already in the caller's own party.

1. **An auth channel mints a random `userSalt`** into `secret_json` at creation, alongside the
   signing secret and beside the doc apiKey. It never leaves the platform: no route, no console
   view and no log line renders it, and it is not the signing secret (rotating one must not move
   every player's id).
2. **`deriveUserId` takes the salt as its first input.** A channel **without** a salt keeps the
   old unsalted derivation, for ever: a player's id is the primary key of their kv rows, their
   state document and their scores, so re-deriving it for an existing channel would orphan all
   three. Existing channels therefore keep reversible ids, and the honest statement — a
   pre-2026-09-09 channel discloses "this provider account played" to anyone who can list its
   ids — belongs in `docs/auth-game-contract.md`, not in a footnote.
3. **A team that wants unlinkable ids creates a new auth channel.** No migration, no rotation
   route: both would mean deciding what happens to the data of the ids they invalidate, and the
   answer at this scale is "start a new channel", which a contest does anyway. The cost is
   stated rather than discovered: `userSalt` is the **first value in `secret_json` a leak cannot
   be recovered from**. Every other secret there has a rotation route; this one's only remedy is
   a new channel, which discards the players' data along with the ids. `docs/secrets.md`'s
   "rotation is the only real fix" does not apply to it, and `rules/data.md`'s note that four
   service accounts can `SELECT` that column is where the blast radius is written down.
4. Nothing on the game side changes: `sub` is still 32 lowercase hex, `deriveUserId` is still
   server-side only, and no client library computes it.

## CDN cost guard and emergency stops — added 2026-09-27

Public CDN cost grows with viewer traffic and nothing bounded it: any site, asset or build file can be fetched in a loop, there is no WAF and no rate limit at the edge. Settled by the owner on 2026-09-27 (`todo/44`). CloudFront flat-rate plans were considered and not adopted: the Free and Pro tiers forbid custom cache policies and custom response-header policies, which every content distribution here uses, and Business costs $200/month. Path-host invalidations stay as they are (_Static sites_ §3).

1. **Guard.** A scheduled console function (`cdnGuard`, every 5 minutes, dev and prod) reads CloudFront `BytesDownloaded` and `Requests` (`GetMetricStatistics`, `us-east-1`, `Region=Global`, Period 300, two calls per distribution per run: about 69,000 a month per stage, inside the free API tier) for the stage's four distributions — `artifact` (d, hand-made), `path-host` (g, hand-made), `site-host` (`*.g`, this stack) and `console` (this stack) — all at once, so one slow call does not starve the others. No CloudWatch alarm and no custom metric is created.
2. **Thresholds, per distribution.** Trip at 10 GiB or 2,000,000 requests in a 5-minute bucket, or 100 GiB (≈ $12 of transfer at Asia rates) or 20,000,000 requests (≈ $24) in the day; warn at a quarter of each. The day starts at UTC midnight or at the last re-arm, whichever is later; the 5-minute measures always look back 15 minutes, across midnight too, because CloudFront metrics land minutes late and a bucket is judged again, complete, on the next run. The bound is time, not bytes: after a threshold is crossed traffic keeps flowing for up to one run interval, the metric delay (about 3 minutes observed) and the disable's propagation (about 3–4 minutes observed on dev) — at 1 Gbps that is on the order of 100 GB. `--param cdnGuardScale=<k>` multiplies every line and `--param cdnGuardMode=alert` turns every trip into an announcement (a contest day that expects a spike); pausing without a deploy is disabling the function's EventBridge rule (`rules/deployment.md` _CDN emergency_).
3. **Trip = disable.** `artifact`, `path-host` and `site-host` are disabled (`Enabled=false` through `UpdateDistribution` with the config's ETag); a disabled distribution is not billed for requests or transfer and its host stops resolving, and every site or every asset behind it is down until re-enabled. Each distribution trips on its own: with `path-host` off, sites still load at `{slug}.g.yyt.life`, and the other way round. `console` is alert-only (it also carries the console API, whose HTTP API stage throttle — 50 rps, burst 100 — already bounds the API side); `CDN_GUARD_CONSOLE=off` drops it. Before disabling, the guard checks that the live distribution's aliases include the stage's host for that label, so a wrong SSM id cannot switch off another distribution. **The guard never re-enables anything.**
4. **Re-arm by observation.** A tripped distribution is only read (`GetDistribution`); once it shows `Enabled=true` again — `scripts/cdn-switch.sh … on`, or any update — the guard counts from the re-enable (its `LastModifiedTime`, on the 5-minute grid) and announces the re-arm. An armed distribution found disabled — switched off by hand, or by a guard run whose result was lost — is announced and treated as tripped. CloudFormation does not revert drift, so a console deploy leaves a disabled `site-host` disabled unless that deploy changes the resource, in which case the template's `Enabled: true` re-enables it and the guard re-arms. With its state lost (below), the guard counts from the distribution's `LastModifiedTime` when that falls on the current UTC day, and keeps that start.
5. **Notices** go to the stage's alarm topic (e-mail) on edges only: disabled, found disabled, disable failed (first failure; retried every run; the e-mail carries the error's class, the log its text), re-armed, warning (once per measure per UTC day), alert not disabled (console, or alert mode), blind (two consecutive failed reads, or an alias mismatch) and sees-again, and state unavailable (once per container). Subjects name the label and the public host, never a distribution id.
6. **State** lives in console Redis and is saved before a notice is sent: a crash re-sends a notice rather than losing it, and a notice SNS rejects stays queued (at most 8, dropped after 24 h). When Redis cannot be read or written the guard still disables past a trip threshold and still announces that, but other notices are only logged (a failed disable once per container).

   | Key (`console:{stage}:` prefix) | Value                                                                                              | TTL                       |
   | ------------------------------- | -------------------------------------------------------------------------------------------------- | ------------------------- |
   | `cdn:guard:{label}`             | JSON state: armed/tripped, re-arm time, today's announced measures, failure counts, queued notices | 35 d, rewritten every run |
   | `cdn:guard:run`                 | unix second of the last complete scheduled run                                                     | 90 d                      |

   The daily usage digest warns `cdn:guard:stale` when `cdn:guard:run` is older than an hour, and `cdn:<label>:unconfigured` for a host the stage serves whose distribution id is missing (the guard cannot protect what it has no id for). The guard has no Errors alarm (the 10-alarm cap), so on prod the gateway probe — the other 5-minute schedule — also reads `cdn:guard:run` and announces a guard that has not completed a run for 20 minutes (again every day it lasts) and its restart (`cdn:guard:watch`, 24 h); on dev only the daily digest notices.

7. **Permissions.** The guard runs under its own IAM role, the stack resource `CdnGuardRole` (Serverless's per-function roles refuse conditional statements): `cloudwatch:GetMetricStatistics`, `sns:Publish` on the alarm topic, and `cloudfront:GetDistribution`/`GetDistributionConfig`/`UpdateDistribution` on the three disable-able distributions only, plus an explicit `Deny` of `UpdateDistribution` on the console's distribution. IAM cannot narrow `UpdateDistribution` to the `Enabled` flag, so code running with this role could change those three distributions in any way; the shared role of `api` and the other functions gains nothing, and the guard's environment carries none of the provider's secrets. The dev-only debug payload (`STAGE=dev` and `DEBUG_HOOKS=1`) can lower thresholds for one label and dry-run a disable, for verification.
8. **Manual stops (owner-run scripts, usable while the console is down).** `scripts/cdn-switch.sh <stage> <artifact|path-host|site-host|console> <off|on>` toggles a whole distribution, the console included. `scripts/cdn-quarantine.sh <stage> <site|artifact> <key | prefix/> <on|off>` (and `… <site|artifact> list`) adds or removes a resource in one `Deny s3:GetObject` statement (`YytQuarantine`, principal `*`) of the bucket policy and invalidates the matching path on the stage's distributions for that bucket: the file, site or bundle stops being served on every host while everything else keeps working, and a quarantined site cannot be moved out (a move's copy reads the source). It refuses a bucket policy that names a deleted IAM principal (AWS rejects any rewrite of such a policy) and says which statements to remove. Deletes and uploads are unaffected; an upload under a quarantined prefix is stored but not served. The hot object is found in the CloudFront console's popular-objects report, which needs no access logs. A request flood has no single object: quarantine turns it into 403s that are still billed, so the answer is to keep the distribution off until it stops.
9. **Account alerts (owner-run `scripts/bootstrap-cost-alerts.sh`, all free).** Cost Anomaly Detection on the AWS-services monitor with a daily e-mail at $3 of impact; a CloudFront-only AWS Budget ($5/month; actual 20 % and 100 %, forecast 100 %); an account Budget of $60/month (actual and forecast 100 %) replacing `yyt-30usd`, so the yearly domain renewal (~$40, Amazon Registrar) no longer spends the only account alert for the month; and the us-east-1 `BillingAlarm` deleted (it was an 11th CloudWatch alarm; the Infra row above). Budgets and anomaly alerts are account-level and not in any stack.
10. **Known gaps, accepted for now.**
    - Direct S3 reads: closed by private origins (§11). The bucket names have been public in this repository's history; with no anonymous access they give nothing away.
    - Anyone can trip the guard on purpose — a few minutes of about 300 Mbps, or of 7,000 requests a second on random paths — and take every site (or every asset) of a stage down; after `cdn-switch … on` a continuing flood trips it again. That is the price of the bound; the answer is to keep it off until the flood stops.
    - Traffic just under the daily line (for example 90 GiB a day on every distribution) never trips: it warns every day, and the CloudFront budget and anomaly alerts see the bill.
    - Large assets (decided 2026-09-28, multipart built the same day): once _Limit requests_ allows 256 MiB files, about 40 downloads of one within five minutes cross the artifact distribution's 10 GiB line, and about 400 in a day cross its 100 GiB line (about 70 full installs of a 1.4 GiB bundle); either takes every team's APKs and assets down with it. The owner lowered the file ceiling from a proposed 512 MiB for this reason. A planned burst raises the lines with `cdnGuardScale`; a per-distribution scale is deferred (`todo/34-backlog.md`) and is to be revisited before a multi-GiB grant on prod.
11. **Private origins (2026-09-27; replaced the Referer origin lock of the same day).** Every CloudFront distribution in front of the site and artifact buckets reads the bucket's S3 REST endpoint through origin access control (SigV4, always signed; the script checks the control's signing). The per-site host uses the console stack's `CdnOriginAccessControl`. `scripts/origin-oac.sh` attaches the same control to the hand-made path host and artifact CDN. The dev artifact CDN keeps the control it was built with.
    - **Bucket policy:** it allows `s3:GetObject` only to `cloudfront.amazonaws.com`, with `AWS:SourceArn` set to the stage's distributions in front of that bucket (Sid `YytCloudFrontRead`). It has no anonymous statement.
    - **Block Public Access:** `IgnorePublicAcls`, `BlockPublicPolicy` and `RestrictPublicBuckets` are on everywhere. `BlockPublicAcls` is on too, except on the prod artifact bucket. The 2019 binary-distribution API (`api.yyt.life/d`, `deploy-to-yyt.sh`) still uploads there with `public-read`, a handful of calls a month. The ACL is ignored, so those objects are private too.
    - **Never `s3:ListBucket`:** a missing object answers 403 on every host, and `GET /` on the REST endpoint would list the bucket.
    - **Direct S3 reads:** once `apply` has closed a bucket, they answer 403, so the bucket names being public no longer matters. `revert` reopens them until the next `apply`. The account's own IAM roles (the console, the legacy uploader) still use the S3 API.
    - **Edge functions:** two console-stack CloudFront Functions keep the website-endpoint behaviour that clients rely on.
      - On the path host (`…-path-host`): `/{slug}` redirects to `/{slug}/` (302, query kept; only a segment in the prefix grammar, so the `Location` never names another host), a path ending in `/` gets `index.html`, and a raw `+` is sent as `%2B`. The REST endpoint reads `+` as a space; the website endpoint read it literally.
      - On the artifact CDN (`…-artifact-cdn`): the `+`, and `/` asks for `/index.html`.
      - Both drop the query string: on a signed request S3 honours `response-content-type` and the other response overrides.
    - **What the path host no longer does**, like the per-site host (_Site domains_ §1): redirect a nested directory that lacks its trailing slash, serve the bucket's error document, or follow `x-amz-website-redirect-location`. The error document was a root `index.html` that does not exist, so the result was a bare 404. No object used any of them.
    - **Revert:** the website configurations stay on the buckets, unused. `origin-oac.sh <stage> revert --apply` goes back to public website origins, with no secret, if something breaks. It also detaches the stack's functions, which a console rollback past this change needs first.
    - **Deploy check:** `scripts/deploy.sh console` runs `origin-oac.sh <stage> check-deploy`. It refuses while the site bucket does not let the stack's per-site host read it.
    - **Cost:** the functions cost $0.10 per million requests past the free 2 million a month, about a tenth of the request price, and the path host needs one anyway.

## Limit requests (soft/hard) — added 2026-09-28

Status: decided and built 2026-09-28 (`todo/46` P1); live on dev and prod 2026-09-28. Settled by the owner on 2026-09-28 (`todo/46`, from a proposal of 2026-09-27). A cap stops being one constant: every member gets its **soft** value, and a platform admin may grant a scope more, up to a **hard** ceiling, on request. `team.projects` (a team as its own scope, a stepped key) was decided and built 2026-09-29 and is live on dev and prod the same day (`todo/48`, migration `m0026_team_limit_scope`, `cli/v0.13.0`).

1. **Registry.** One code table (`services/console/src/limits.ts`) lists every key with its scope, unit, soft and hard value; changing a hard value is a code and decisions change. The effective limit is an unexpired override, else the soft value. An override is validated against hard, `unlimited` exists only where hard is unlimited, and a key is accepted only for its own scope kind. A key may carry a **step**: it is then asked for only as `effective + step`, and only once the usage has reached the effective value (#2).

   | Key                       | Scope   | Soft       | Hard      | Step |
   | ------------------------- | ------- | ---------- | --------- | ---- |
   | `asset.fileBytes`         | bundle  | 2 MiB      | 256 MiB   |      |
   | `asset.bundleBytes`       | bundle  | 20 MiB     | 3 GiB     |      |
   | `asset.projectBytes`      | project | 400 MiB    | 5 GiB     |      |
   | `asset.bundlesPerProject` | project | 20         | 50        |      |
   | `asset.versionsPerBundle` | bundle  | 50         | 500       |      |
   | `asset.filesPerVersion`   | bundle  | 200        | 5,000     |      |
   | `asset.filesPerBundle`    | bundle  | 10,000     | 20,000    |      |
   | `asset.mutableFileBytes`  | bundle  | 256 KiB    | 4 MiB     |      |
   | `channel.lifetime`        | channel | now + 28 d | unlimited |      |
   | `team.projects`           | team    | 20         | 1,000     | 5    |

   `team.projects` (2026-09-29) replaces the fixed projects-per-team cap of _Teams and projects_. The step keeps the queue free of speculative asks: a team files for five more only when every slot is used, and the admin still sees the count. The hard value bounds what `q` search scans (_List sort and filter_ #5); a project row is small, so 1,000 of them cost nothing that the resource caps under each project do not already bound.

   `asset.projectBytes` is new; its soft value is today's effective ceiling (20 bundles × 20 MiB). `asset.filesPerBundle` is new too and bounds rows: the multiplied counts would otherwise allow 2.5 million file rows in one bundle on the MariaDB that five stacks share — the leaderboard's reasoning (_Serverless clients_ #2). Even so a project may hold 200,000 file rows at the soft values (20 × 10,000) and 1,000,000 at the hard ones, the latter only through admin grants on every one of those scopes, so no check loads a bundle's rows: totals are aggregate queries over the covering index `asset_files_version (bundle_id, version, size, created_at)`, which reads only the index on MariaDB 10.5 and 11 alike (a container test pins the plan at 200,000 rows; the project total took 30 ms there), and every check still counts presigns in flight, as the caps always did. A refused upload names the key and its effective value (`details: {limit, value}`), and a commit re-checks every limit, so a limit lowered after the presign still refuses it. A live bundle's `asset.filesPerVersion` counts the whole bundle. At every hard value a project stores about $0.13 a month; transfer is the CDN guard's business (_CDN cost guard_ §10). The kv `*_DEFAULT`/`*_HARD` pairs (_Key-value store_ #7) stay as they are for now.

2. **Requests.** A member seated in the team that owns the scope asks with `POST /limit-requests {scope, key, value | "unlimited", reason}` (reason ≤ 2 KB); the team is taken from the scope's row, never from the body (for a team scope, `team:<id>`, the scope row is the team row). `GET /limits?scope=` shows soft, hard, the effective value, the override and the usage, and on every row `step` and `next` — for a stepped key, `next` is the one value a request may carry now (`effective + step` while `usage ≥ effective`, clamped to hard; `null` once the effective value is hard), else `null`; a request for a stepped key that is below its limit, or for any value but `next`, is a 400 whose `details` carry `{limit, value, usage, next}`, so a client renders the reason without a copy of the rule. A refused project create names the key too (409 `details: {limit: "team.projects", value}`), and `GET /limit-requests?team=&status=` lists the team's requests (paged) and `GET /limit-requests/{id}` reads one, the admin's note included; like every project read, these admit the team's members and a platform admin without a seat, and every one of them is `no-store` (they carry the members' reasons). The requester, while still seated, or a team owner may cancel a pending request. One pending request per scope and key and ten pending per team, both checked under the team lock (409); a request must ask for more than the effective value. A rejected or cancelled request blocks the same scope and key for 7 days (429 `rate_limited` with `details.retryAt`): cancelling counts as a rejection, the join-withdraw rule (_Teams and projects_), so request → cancel is not a free loop that mails the operator. Every recorded write takes the member's write slot, is audited (`limit.request.create`, `limit.request.cancel`) and lands in the team history. Deleting a channel — a soft delete, by a member or by the expiry sweep — cancels its pending requests and drops its override in the same transaction; its purge 30 days later removes the rows. Decided requests are purged by the daily sweep after 90 days; the audit log keeps them.

3. **Decisions belong to a platform admin**, seated or not, like channel extend. `POST /admin/limit-requests/{id}/approve {value?, note?}` grants the requested value or an adjusted one (≤ hard), `…/reject {note}` requires a note, and `GET /admin/limit-requests?status=` lists every team's (paged). Approval, rejection and cancellation each change a request only while it is still `pending` (a conditional update), so a cancel racing an approval leaves exactly one outcome. Approval upserts the override in the same transaction and is audited (`limit.request.approve`, `limit.override.set`). An admin may approve their own request — the platform has one operator — and the audit row says `selfApproved: true`. An admin may also set or revoke an override without a request (`PUT|DELETE /admin/limit-overrides/{kind}/{id}/{key}`, a note required), optionally with `expiresAt` for a temporary raise such as a contest day; the daily sweep deletes expired overrides (`limit.override.expire`).

4. **Lowering never deletes.** A revoked, lowered or expired override refuses new writes only; stored data stays, and the console shows the scope over its limit.

5. **Notifications.** The SPA shows admins a pending badge. The daily usage digest says `pending limit requests: N` once each UTC day the number is not zero — unlike level warnings, which are announced once, because a pending queue is work rather than a condition; a retried or hand-invoked sweep the same day stays quiet, and a count that cannot be read is its own warning. Every new request publishes one e-mail to the stage's alarm topic, at most 3 per team and 20 per stage per UTC day (Redis counters), after which only the badge and the digest tell. Subject and body are a fixed template — team, scope kind, key, requested value, requester login, a console link — and never carry the member-written reason, so no member's text arrives inside an AWS alarm e-mail. The publish runs with a short timeout and one attempt; a failure is logged and never fails the request.

6. **Rows.** `limit_requests` and `limit_overrides` name their scope through typed nullable foreign keys (`project_id`, `bundle_id`, `channel_id`, and since `m0026` `scope_team_id`; `ON DELETE CASCADE`; exactly one set), so deleting a bundle, a project or a team, or purging a channel, removes its requests and overrides without a cleanup path anyone has to remember. A team-scoped row carries the team's id in `team_id` and `scope_team_id` alike; the fourth column exists because one override per (team, key) is a unique index, and `(team_id, limit_key)` would collide as soon as two projects of one team held the same project-scoped key. The cascade also removes the rows a cooldown reads; the e-mail caps above are what bound a delete → recreate → request loop.

7. **`channel.lifetime`** takes only `unlimited` and never `expiresAt` (400): a numeric grant would fight extend's fixed cap, and a temporary one would leave the sentinel behind. Approval, or a direct set, writes the sentinel `expires_at = 253402300799` (9999-12-31T23:59:59Z) in the same transaction as the override, fails if the channel row no longer matches, and revives a disabled channel as an extend does; a soft-deleted channel is refused. The expiry sweep's soft delete re-checks that the channel is still disabled, so it cannot delete a channel revived a moment earlier. Every active check (`expires_at > now`) and the expiry sweep work unchanged, and the column stays `NOT NULL`. Extend answers 409 (the channel has no expiry), and its write is conditional on the expiry it read, so an extend racing a grant refuses (409) rather than write a date over the sentinel; revoking sets `expires_at = now + 28 d` and drops the override in one transaction. No expiry does not protect a channel from its own team: deleting it still wipes its secrets at once, and re-issuing a doc key still invalidates the old one. The console shows "No expiry" (the app its Korean equivalent), the CLI prints `no expiry`, and all three hide extend; the auth service's public `GET /c/{ch}/.well-known/config` returns the sentinel as a number (`services/auth/README.md`).

## Live and encrypted asset bundles — added 2026-09-28

Status: decided 2026-09-28. Live bundles (#1–#3) built 2026-09-28 and live on dev and prod 2026-09-28 (`todo/46` P2); encrypted bundles (#4) built 2026-09-28, live on dev (2026-09-28) and prod (2026-09-29, `todo/46` P5); the client libraries (#5) are unbuilt. Settled by the owner on 2026-09-28 (`todo/46`). The first consumer is a privately distributed app: its content (SQLite files, music) must not be readable by whoever finds a URL, and its manifest must be replaceable without an invalidation.

1. **Mode, fixed at creation: `versioned` or `live`.** A versioned bundle is unchanged (_Storage shapes_). A live bundle has one namespace, keyed `assets/{bundleId}/{path}` with no version segment — its rows store `version = ''`, and presigns, file lists and the CLI take no version for it — and each file is immutable (the default) or mutable, chosen at upload. Every upload to a live bundle carries the file's sha256.
   - **Immutable** files are served `public, max-age=31536000, immutable`. Uploading the same path with the same sha256 again is idempotent: the presign answers "already present" and nothing is transferred. Another sha256 is 409. Deleting one leaves a tombstone `(bundle, path, sha256)` for 400 days — a year of edge TTL plus margin — during which the path accepts only the same content again, so no edge can keep serving old bytes under a reused name (for a file over 64 MiB, as far as the uploader's sha256 is true: _Large asset uploads_ #3).
   - **Mutable** files are served `no-cache`, hold at most `asset.mutableFileBytes`, and are JSON or text (an encrypted bundle's are ciphertext like the rest). On prod the artifact distribution's legacy cache settings have a minimum TTL of 0, so every request revalidates (usually a 304; no invalidation); dev's managed `CachingOptimized` policy can add a second. A mutable file goes through staging like every single-PUT file, and the commit's `CopyObject` (`MetadataDirective: REPLACE`) carries S3's conditional write — `If-Match` on the stored ETag, `If-None-Match: *` for the first, both honoured on copies since 2025-10 — optionally conditioned on the caller's `ifSha256`, so two concurrent deploys cannot overwrite each other unseen; S3's 412 is a 409 carrying the current sha256, and a `ConditionalRequestConflict` (another write in flight) is retried twice, then a 409 that leaves the upload pending. A commit that died between its copy and its row update leaves the object ahead of its row; once that object is older than any commit in flight (a minute), the next commit heals the row to it and still answers 409, so the deploy runs again against what is really there. The object therefore changes only inside a commit, as the claim-first rule requires, and the condition is S3's, not a database lock held across an S3 call.
   - `DELETE /assets/bundles/{b}/files {paths}` deletes with `DeleteObjects` and no invalidation (immutable names are never reused with other content), in batches bounded by count and by request size. A sync marks files that vanished locally with `stale_since` and clears the mark when they return; `--prune` deletes only files that were already stale, which keeps the previous generation without the platform reading any manifest, and `--prune=now` deletes at once.
   - Presigns and commits take batches (`{files: […]}`, up to 100 per call — the show-screenshot precedent), because a sync of thousands of files would otherwise spend the stage's shared 50 rps.
2. **Where a live or encrypted bundle may not go.** A lobby `mapUrl` must name a committed file of a versioned, unencrypted bundle **of the channel's own team**, resolved through the stored `object_key` (rows from before 2026-08-26 have name-based keys): a live file can change under a running game, ciphertext is not a map, and another team's bundle is not this team's to pin. Only the same team's lobby channels count as references that refuse a delete (_Storage shapes_), so no team can hold another's bundle — and its storage limit — hostage (owner decision 2026-09-28; a team that wants a sample map uploads its own copy). A show entry links a live bundle live and refuses an encrypted one (_Show_ #4–#5). Project versions link versioned bundles only.
3. **Extensions** gain `.db`, `.sqlite`, `.bin` (`application/octet-stream`) and `.zip` (`application/zip`): none renders in a browser, the response headers policy already sends `nosniff`, and neither distribution compresses these types (prod does not compress at all), so byte ranges stay those of the stored object. html, svg and js stay refused.
4. **Encrypted bundles (`encrypted`, fixed at creation) are public ciphertext.**
   - **Why not edge authentication.** The 2026-09-27 proposal checked read keys at the edge: a second distribution whose viewer-request CloudFront Function looked keys up in a KeyValueStore. Every KVS write is billed per call ($1 per 1,000), so a write path that members trigger (issuing and revoking keys) has an unbounded cost under a rate limit alone — the reason _Site domains_ dropped KVS on 2026-09-26 — while ciphertext on the existing CDN costs nothing extra and needs no new distribution, host, function or guard label.
   - **Format** (`docs/asset-encryption.md`, `yyt-enc v1`): Tink's AES-CTR-HMAC-SHA256 streaming segments — AES-256, HKDF-SHA256, 32-byte HMAC tags, 64 KiB segments, the file's key below the bundle (`{version}/{path}` or `{path}`) as associated data — except that the salt and nonce prefix are derived from the key, the associated data and the plaintext instead of drawn at random. One file under one key therefore always encrypts to the same bytes, and the sha256 idempotency, sync skipping and write-once rules above hold for ciphertext unchanged. Segments are authenticated one at a time, so a Range request or a resumed download decrypts without the rest of the file. AES-GCM was not chosen: Unity's netstandard2.0/2.1 lacks it, and the C# library would need a third-party dependency.
   - **Plaintext never enters an encrypted bundle by accident.** A presign there requires `format: "yyt-enc-v1"` (400 otherwise, which also stops an older CLI), and the commit refuses an object whose first byte is not `0x28` or whose length breaks the format's rules (a single PUT is checked in staging before any claim; a multipart object is checked right after its completion at the final key, and again by a retried commit and by the daily sweep, because the check can only run once the object exists — so a member of the bundle's team could, deliberately, have the CDN serve a plaintext file for the seconds between the completion and its deletion). This is a shape check, not authentication: the per-file ceiling is applied to the plaintext length, the object type is always `application/octet-stream`. The CLI's `asset upload` and `asset push` refuse an encrypted bundle; `asset sync` is its uploader, with `--version` for a versioned one.
   - **The console holds the key.** One 256-bit key per bundle, minted at creation and stored wrapped by a stage KEK (SSM `console/asset-kek`) in a table only the console reads (`asset_bundle_keys`). The state account's grant is table-scoped and does not name it; the auth, topic and match accounts hold a database-level `SELECT` (`SHOW GRANTS` 2026-09-28, both stages), so they could read the wrapped rows, which open only under the KEK — narrowing those grants is an owner item in the ops repo. The KEK reaches the `api` function only, never `siteDeploy`, `gatewayProbe`, `cdnGuard` or `expire`. It is created once and on purpose (a dedicated mode of `bootstrap-ssm.sh`, never as a side effect of a routine bootstrap) and backed up in the private ops repository. It is never rotated in place: replacing the parameter would orphan every wrapped key, and a re-wrap under both KEKs, the only rotation, is not built. Losing it loses the console's copies, not the apps': a new bundle is the remedy. A stage without it answers 503 `asset_encryption_not_configured` on the encrypted routes. Any team member may read a key with `POST /assets/bundles/{b}/key` — a POST so that the console's Origin check applies, since a GET would let any same-site page (a site on `*.g.yyt.life`) make a member's browser write audit rows in their name — with `secret: true` (a seatless admin gets 403, as for every secret), `no-store`, the write slot and audit `asset.key.read`. The CLI fetches the key, encrypts locally and never writes the key to disk; the server never encrypts or decrypts content. **This is not kv's `encrypted`** (_Key-value store_ #8), which promises that the console cannot read values: here the console can unwrap every bundle key, and the promise is only that the CDN never serves plaintext.
   - **Threat model.** The key ships inside the consumer app — the owner's premise is that such apps are privately distributed — so anyone holding the app binary can extract it and decrypt the bundle. Encryption keeps content from whoever finds or guesses a CDN URL, which public assets never did. Ciphertext still reveals paths, exact plaintext lengths, and whether the file at a path changed. A key is never rotated in place: a new key changes every ciphertext, and immutable paths refuse changed bytes, so rotation is a new bundle and an app release.
   - The SPA lists an encrypted bundle's files and reveals its key but does not upload to it; every object is `application/octet-stream`; a member who leaves keeps the keys they could read, so the leave response lists the team's encrypted bundles (_Teams and projects_).
5. **Receiving side.** A new wire package `asset-client` in each client library — tslib, csharplib and flutterlib — will download, resume and decrypt, and the examples repository will show it (_Game kit_ #1). Conformance is the test-vector file beside the format specification.

## Large asset uploads — added 2026-09-28

Status: decided 2026-09-28. Built 2026-09-28 with live bundles (`todo/46` P2): the single-PUT claim rule of #2, the checksums of #3 for single PUTs, the lifecycle rule of #4 and the batched deletes and pages of #5. Multipart (#1, the rest of #2–#4: migration `m0023_asset_multipart`, routes `POST|GET /assets/uploads/{id}/parts`, `DELETE /assets/uploads/{id}`, the `completing` status, the sweep's abort phase) and the CLI's multipart resume (#6) built 2026-09-28 (`todo/46` P3; on prod the same day). Settled by the owner on 2026-09-28 (`todo/46`).

1. **Multipart above 64 MiB**, in 32 MiB parts (at most 8 at the 256 MiB ceiling). The console inserts the pending row first, then creates the multipart upload at the file's **final** key with the `Content-Type` and `Cache-Control` it chooses, and keeps the upload id on the row (TTL 24 h, not the 1 h of a single PUT). `POST /assets/uploads/{id}/parts` presigns the parts it is asked for in one call (all of them on a first run, the missing ones on a resume): each URL signs its part's exact `Content-Length` and SHA-256 checksum, part numbers run 1..⌈size / 32 MiB⌉, and URLs live 1 h (or what is left of the upload's day) and are presigned again on resume — the CLI re-asks for a part whose URL lapsed mid-run. `GET …/parts` lists the parts already uploaded for a resume, and `DELETE /assets/uploads/{id}` aborts.
2. **Commit stays claim-first** (_Storage shapes_). It checks the parts (`ListParts`: count, sizes, checksums — a read that binds nothing), marks the upload `completing`, inserts the file row (the claim), completes with `If-None-Match: *` and the expected object size, so S3 itself refuses to overwrite an existing object, and confirms with `HeadObject`. This path has no CopyObject, so the catalog's 25 s synchronous-copy bound does not apply; every S3 call is bounded by the Lambda's remaining time. A claim is released only when the upload is known aborted (or gone) **and** `HeadObject` answers 404 — never on a 403, which a quarantined key also answers (_CDN cost guard_ #8). A completion whose answer was lost is reconciled by the retry or the sweep, never rolled back blindly, because a published immutable object must keep its row. **The single-PUT commit follows the same rule** (revising _Storage shapes_, which rolled the claim back on any failed copy): a lost CopyObject response can mean a published object.
3. **Integrity.** Every file of a live bundle and every part carries a SHA-256; a single PUT to a versioned bundle may still omit it. With a sha256 the presign signs `x-amz-checksum-sha256` as a header, so S3 verifies the whole file; the presigner otherwise hoists checksums into the query string, where S3 does not enforce them (confirmed on dev 2026-09-28 with the runtime's SDK 3.1105.0: other bytes of the same size are refused `400 BadDigest` against the signed header and stored `200` against the hoisted one), and the presigning client sets `requestChecksumCalculation: "WHEN_REQUIRED"` so an SDK default cannot add one. S3 has no whole-object SHA-256 for a multipart upload, so the stored `sha256` of a file over 64 MiB is the client's claim; the format authenticates an encrypted file end to end regardless. The Lambda runs the runtime's AWS SDK, which can change underneath it: the console logs that version at cold start, and dev probes (no stray checksum in a grant, a 412 on a conditional write, the copy's stored SHA-256) run as a smoke test (`POST /debug/s3-probe`, `scripts/smoke/assets-live.mjs`). A commit also reads the staging object's stored SHA-256 back and refuses a mismatch.
4. **Cleanup.** Abandoned parts are invisible and billed. The daily sweep aborts expired multipart uploads before it deletes their rows (the existing clean-up of expired uploads skips rows that carry an upload id), a bundle delete aborts its in-flight uploads first, and the artifact buckets' one lifecycle rule (`scripts/s3-intelligent-tiering.sh`) gains `AbortIncompleteMultipartUpload` after 1 day as the backstop — a rule that expires no object. The rule is applied to both stages before any multipart code ships, and `deploy.sh console` refuses while it is missing.
5. **Request budgets.** Bundle and version deletes use batched `DeleteObjects` (1,000 keys a call) and stop after a 15 s budget with `202 {done: false, deleted, failed}`: the rows of what went are gone, so the caller repeats the delete to continue — the CLI and the SPA do — and a bundle half deleted stays visible with what is left rather than hidden behind a marker no read path knows (revised 2026-09-28; the design had the sweep finish the rest). Batch presigns and commits (100 files) and single-file deletes (1,000 paths, 64 KiB bodies) are bounded the same way — a batch commit runs eight commits at once and stops starting new ones after 15 s, answering `unavailable` for the rest, which stay pending for a retry — and every list of files or of limit requests is paged: one S3 call per file and one unpaged list fit neither 25 s nor the 6 MB response at these counts.
6. **CLI.** `yyt asset sync <bundle> <dir>` compares sha256, uploads missing immutable files in parallel with retries, then mutable files with `ifSha256`, then prunes — the order that keeps a manifest from naming files that are not there yet — and resumes a multipart upload from `ListParts`; `--version <v>` syncs one version of a versioned bundle (no `--mutable`, no `--prune`). `yyt asset download <bundle> <path>` fetches one file, decrypting it when the bundle is encrypted.
7. **Deferred:** files over 256 MiB need an asynchronous commit and a higher CDN guard line (_CDN cost guard_ §10); both wait in `todo/34-backlog.md`.

## Catalog listings (publishing an app) — added 2026-09-28

Status: decided 2026-09-28. Server side (#1–#6, #8: migration `m0025_catalog_listings`, `@yyt/console-db` `ListingsDb`, the routes below) built 2026-09-28 and deployed to dev (`todo/47` P1); the clients (#7) built 2026-09-28 — SPA and CLI (`cli/v0.12.0`, 2026-09-29) on dev, the console app 1.5.6 (2026-09-29: browse tab, shared badge, and a publish panel on the team's own app detail) on both stages' catalogs; server live on prod 2026-09-29 (`m0025`, `todo/47`). Settled by the owner on 2026-09-28. Need: let people outside the team install a project's app without a team seat, and without a second deploy target.

1. **A listing publishes an app, not an artifact.** `catalog_listings` is one row per catalog app (`app_id` primary key, cascading on app deletion): title, summary, tags, audience, `published_by`, `published_at`. It always points at the app's **newest artifact per platform**; every later upload is published by the listing. This is the deliberate opposite of a show entry (_Show_ #5), which pins an artifact because nobody chose to publish future builds there; here publishing the app's distribution channel is the choice, and the publish UI says so.
2. **Audience: `public` or `members`.** `public` is readable by anyone, anonymous included. `members` is readable by the members named in `catalog_listing_viewers (app_id, member_id)` (cascading on either side). A named viewer must be a platform member that is not `pending` when named, and is checked again on every read (a member demoted to `pending` sees nothing). The owning team always reads through its seats. Both directions of change are allowed; narrowing does not revoke CDN URLs already fetched (same as _Teams and projects_, "Leaving does not revoke anything"). Named viewers are kept across an audience change, and a listing that names the caller counts as naming it whatever its audience (built 2026-09-28), so widening to `public` does not drop the app from a viewer's list. An empty summary is stored as none.
3. **No approval step.** Being an approved platform member is the permission to publish. Publishing, editing, unpublishing and naming viewers need write access to the app (`projectResource`, `min: "member"`, not `secret: true` — so a seatless platform admin may publish, as it may submit a show entry) and record `team_history` (`resource.create|update|delete` with `resource.kind: "listing"`, field names only); every listing mutation, the admin's takedown included, takes the per-member recorded-write slot (_Show_ #13). As for every project resource the history row is best-effort beside the write, not inside its transaction — the listing tables live in their own repository and there is no transaction shared across repositories (`rules/data.md`); the global `audit_log` (`catalog.listing.*`) is the second record.
4. **Not a seat.** A viewer gains no `team_members` row, so `teamAccess`/`projectResource` never see it: app detail, artifact history, settings, uploads, and every other project resource stay 404 to a viewer. This is why _Teams and projects_ #2 ("nothing finer") and the 2026-08-26 withdrawal of per-app grants (_Binary catalog_) stand: a listing grants read of the newest artifacts only, never write, and is scoped to one published app.
5. **Read routes.** `GET /catalog/listings` (optional auth, `no-store`) returns listings the caller may read — `public` ones plus, when signed in as a non-`pending` member, those naming the caller and those of the caller's own teams — with server-side `q` (title, summary), `tag`, `platform` (keeps the listings that have an artifact of it) , `sort` (`publishedAt` | `title`, newest published first by default) and `order` (_List sort and filter_). Each row carries the team name (no team id), title, summary, tags, `artifacts` (the newest artifact per platform, without the storage key) and the `withSummary` pair (`latestArtifact`, `applicationIds`); a page is at most 200 rows in the list's order (the console answers on one connection into a 6 MB body), and the listing rows appended to the app list follow their own newest-published order, whatever `sort` the seats' rows use. The console app's single list request (`GET /catalog/apps?artifacts=summary`) also returns listings that **name** the caller and whose team the caller is not seated in, after the team's own rows, each row marked `access: "team"` or `access: "listing"` (a listing row carries `listing: {title, summary, tags, audience}`, no project crumbs and the listing's summary as `description`), so they appear in the viewer's app list with install and update; `public` listings are found through search. The plain list (no `artifacts=summary`, the CLI's name resolver) carries seats only. Downloads use the existing public CDN links; nothing new is billed per call.
6. **Tags**: lowercase slugs (`[a-z0-9-]`, 1–32 chars), at most 10 per listing. Title is 1–100 characters (trimmed) and summary at most 2,000, the description cap. At most 100 named viewers per listing (naming one already named is a no-op that passes the cap).
7. **Clients.** SPA: a publish panel on the app page (audience, viewers by GitHub login, title, summary, tags), a public browse page (`/listings`, in the menu as _Apps_ beside _Shows_) and the admin's `/admin/listings`. CLI: `yyt catalog publish|unpublish|listing|viewer add|rm|ls` and `yyt catalog listings` (browse). Console app: a browse/search tab (`GET /catalog/listings?platform=android`, built on first visit), and named listings in the app list with a "공유됨" badge, no entry into the project and, on the detail screen, the newest build only (the artifact history is the team's).
8. **Platform admin takedown.** A platform admin may take any listing down (owner decision 2026-09-28: something inappropriate must come off). Takedown (`POST /admin/catalog/listings/{app}/takedown`, optional `reason`; allowed on any app, listed or not, so an unpublish that races a complaint does not escape it) hides the listing from every read route and writes `audit_log`; the record is a row of its own, `catalog_listing_takedowns (app_id, taken_down_by, taken_down_at, reason)`, hanging off the **app** rather than the listing (built 2026-09-28: a column on the listing would vanish with an unpublish, and delete + publish would have undone the takedown). While it stands the team sees `takenDown: true` on its own route, may edit the hidden listing or unpublish it, and a `PUT` with no listing row answers 409 `taken_down`, so a takedown is not undone by republishing. Only an admin clears it (`DELETE …/takedown`); `GET /admin/catalog/listings` lists every listing, taken-down ones with the detail. The artifacts themselves are untouched — they are the team's resource, and admin deletion of team resources stays as in _Teams and projects_.
