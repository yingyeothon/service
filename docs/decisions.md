# Decisions (confirmed 2026-08-22)

Single source of truth for settled product/technical decisions. Change this file first, then the code.

## Purpose

- Shared contest-support services with near-zero traffic outside hackathon day.
- Goal: with tslib (`@yingyeothon/*`) plus these services, a team builds a casual MORPG (lobby HTTP API / party matching / instant dungeon) within a 7-hour contest, spending **2–3 hours on the server**.
- Therefore auth, matchmaking, and broadcast are pre-built services the game only calls.

## Console SPA frontend stack (revised 2026-08-24)

- Earlier "no UI library, single `styles.css`" decision is superseded.
- UI: **Mantine 8** (core/hooks/modals/notifications) + `@tabler/icons-react`; compact theme (form components default `size: sm`, small type scale), light-only, system fonts. Layout via Mantine `AppShell` (header + role-filtered side navigation; navigation config is the single source for both the menu and route guards).
- Router: keep **react-router 7** with `basename="/ui"` (small page count; no file-based routing).
- Data layer: **TanStack Query 5** replaces the hand-rolled `useAsync`; 401 handling still drops the session via the auth provider.
- API client stays hand-written (`src/api.ts`); no OpenAPI codegen (the console API has no spec).
- Invariants preserved: `/ui/` base path, `credentials: "same-origin"` + Origin-based CSRF, plain-text rendering of user text (no HTML), one-time secret display with history-state scrub, same-origin poster images with cache buster, accessible status/alert roles.

## Console permission model

- Login: **GitHub OAuth only**. Session = httpOnly cookie (SPA) or Bearer API token (CLI).
- Roles `admin` / `member` / `pending`. New sign-ups are `pending` until an admin approves.
- Bootstrap admins: GitHub logins listed in `ADMIN_GITHUB_LOGINS` (comma-separated) become `admin` on their **first** login only (GitHub logins can be re-registered; later changes go through `/members/{id}/promote`).
- Channels (auth/topic/match/lobby/q) belong to their creator (`member`+). Admins can view/extend/delete any channel but never read or change its secrets/config (PATCH, rotate-secret are owner-only). topic/match/lobby/q channels must reference an auth channel the caller owns.
- Channel expiry: 7 days, extendable by 7 (cap now+28). Expired → disabled (401/410) by the daily sweep; extending a disabled channel revives it; deleted (secrets wiped) 30 days after being disabled.
- Secrets are shown once on creation and can be rotated.

## auth service

- Channel = `{ channelId, secret (HS256), audience, tokenTtlSec (default 86400), providers: { github?: {clientId, clientSecret}, google?: {clientId, clientSecret} } }`.
- Users register **their own OAuth app** and set its callback to `https://auth.yyt.life/c/{channelId}/{provider}/callback`.
- JWT: HS256, `iss = yyt-auth/{channelId}`, `aud = channel.audience`, `sub = userId`, `exp = iat + tokenTtlSec`. `userId` = first 32 hex of `sha256(channelId + ":" + provider + ":" + providerUserId)`. No PII stored or claimed.
- Routes: `GET /c/{ch}/start?provider=&redirect=` → provider → `GET /c/{ch}/{provider}/callback` → `302 {redirect}#token=…&userId=…`. Manual: `POST /c/{ch}/token {provider, accessToken|idToken}` → `{jwt, userId, exp}`. `GET /c/{ch}/verify` (Bearer) → `{userId, exp}`.
- Games verify locally with the channel secret (tslib `createJwtRequestAuthorizer`; contract in `docs/auth-game-contract.md`).
- An auth channel may also carry a **doc apiKey** (`secret_json.apiKey`, added 2026-08-26), which the auth service itself never reads. It authenticates the server side of the state service and is issued, rotated and revoked on its own route so that neither it nor the signing secret can invalidate the other — see _state service_.
- **Debug seeding**: dev `POST /debug/channels` writes the console DB, so console's dev MySQL account is supplied separately as SSM `/yyt-service/dev/auth/debug-mysql-{user,password}` (copied by `bootstrap-ssm.sh dev`) and injected only when deployed with `--param debugHooks=1`. prod has neither the keys nor the routes. Move seeding to the console API/CLI once they exist, then remove the keys.

## topic service

- Channel (console) → `{ channelId, apiKey, authChannelId, wsUrl }`.
- `POST /t` (Bearer apiKey) `{ allowUserIds?, ttlSec? ≤ 1200 }` → `{ topicId, wsUrl, expiresAt }`. **Topic lifetime ≤ 20 min.**
- Connect: `wss://topic-ws.yyt.life/?topic={topicId}` (the `wsUrl` returned by `POST /t`; API Gateway cannot map an HTTP API and a WebSocket API onto one custom domain, so the HTTP control API lives on `topic.yyt.life` and sockets on `topic-ws.yyt.life`) + `Sec-WebSocket-Protocol: bearer, <auth JWT>`. Allowed if in `allowUserIds`, or (when empty) the JWT verifies against the linked auth channel.
- Clients send `{type:"msg", payload}` (`{type:"ping"}` → `{type:"pong"}`). Messages are wrapped as `{ type:"msg", from:userId, seq, payload }` and echoed to **everyone including the sender**; `{type:"join"|"leave", userId}` on membership changes (the joiner does not receive its own `join`). 16 KB cap (`{type:"error", code:"too_large"|"bad_message"}`). No history. `POST /t/{id}/publish {payload}` sends `from:"server"`; `GET /t/{id}` returns meta + connection count; `DELETE /t/{id}` broadcasts `{type:"closed"}` and drops every socket. An expired or deleted topic answers the next client message with `{type:"expired"}` and does not close the socket (clients close).
- State: `topic:{stage}:t:{topicId}` (meta), `:conns` (set), `:seq` (counter), `conn:{connId}` → `{topicId,userId,at}`; all with the topic's TTL.

## match service

- Channel = `{ channelId, apiKey, authChannelId, partySize (2–16), waitTimeoutSec (60), onTimeout: "partial"|"fail", callbackUrl, wsUrl }`.
- Connecting = submitting a ticket: `wss://match.yyt.life/?channel={channelId}` + `bearer, <auth JWT>`. Invalid JWT → rejected. Reconnecting with the same userId replaces the ticket; disconnect removes it.
- Algorithm: FIFO only. Every connect triggers a match attempt (run by an async worker invocation, because a socket cannot be posted to from inside its own `$connect`); disconnect only removes the ticket. An EventBridge 1-minute schedule handles timeouts and acts as the backstop (documented as "handled within ~2 min").
- Match → `POST callbackUrl` `{ matchId, channelId, members:[{userId}], partial }` with `X-Yyt-Signature: hmac-sha256(channel.apiKey, body)`. The 2xx JSON response (≤8 KB, empty body → `null`) is forwarded verbatim to each client as `{type:"matched", matchId, partial, result}`. Callback failure (network, non-2xx, non-JSON; one retry on 5xx/network) → `{type:"failed", reason:"callback"}`. The server never closes the socket after a terminal message (closing right after `PostToConnection` loses the frame); clients close, idle sockets expire.
- Reconnect with the same userId: the old socket receives `{type:"replaced"}`. `{type:"ping"}` → `{type:"pong", position, waited}`.
- Timeout: `partial` → match with whoever is present, possibly a single player (`partial:true`); `fail` → `{type:"failed", reason:"timeout"}`. A disabled/expired channel (seen within the 60s config cache) or a ping from a socket without a ticket → `{type:"failed", reason:"closed"}`.
- Callback target may be the topic service (`POST /t`) or a tslib dungeon server (creates `GameActorStartEvent`, returns `{wsUrl, gameId, token}`).

## Realtime gateway (`lobby` / `q`) — added 2026-08-25

Design in full: `todo/14-websocket-gateway.md`. Game-side blueprint: `examples/sample-morpg/README.md`.

- Two channel kinds join auth/topic/match. **`lobby`** is a client-authoritative position relay plus chat and a party primitive; **`q`** bridges client sockets to a tslib actor Lambda (inbound over a Redis list, outbound over pub/sub). Both are served by one platform-operated process whose strategy is chosen per channel.
- **Deployment**: a single Go Docker container on the `yyt-stateful` box, 256 MB cap, design ceiling **10 concurrent players**. Not per team, not on Lambda. One process means the peer index is trivially global and no cross-instance replication is ever built; it also means a deploy or restart disconnects everyone, so clients must reconnect and the SDK's backoff must not stampede.
- **Endpoint**: `wss://gw.yyt.life/?channel={channelId}`, token in `Sec-WebSocket-Protocol: bearer, <jwt>` (never the query string), selected subprotocol echoed back. The console renders this URL only once the host is actually configured; until then a `lobby`/`q` channel view carries no `wsUrl` at all, because a copyable URL for a name that does not resolve reads as "working".
- **Identity**: the gateway holds no channel secrets. It verifies every token by calling auth `GET /c/{authChannelId}/verify` and caches the result keyed by a hash of the token until the JWT's `exp`. auth's `reservedConcurrency` is 10 and a dungeon start bursts 8 connects, so the cache is mandatory, not an optimisation. `authChannelId` is the gateway channel's config, which is why one token works for both the lobby and the dungeon socket.
- **Channel config comes over HTTP** (settled 2026-08-25): the gateway reads it from `GET /gw/channels/{id}`, never from MariaDB. A shared secret from SSM authenticates it (it is a process, not a person, and may read any owner's `lobby`/`q` channel — and only those: every other kind answers 404). `GET /gw/health` exists so the gateway can tell "wrong console, or one older than this route" from "the channel is gone"; both would otherwise be a bare 404. It stays out of the 57/60 connection budget and adds no second schema consumer; the cost is one HTTP hop per cache miss (60 s cache, the existing platform rule).
- **`lobby` and `q` channels carry no apiKey** (settled 2026-08-25). `buildChannel` mints one for every non-auth kind today; these two get a secretless branch, since neither has a server-to-server caller. That also lifts `rules/data.md`'s ban on caching a secret-bearing row. Adding a server-initiated push later (`POST /lobby/{channelId}/publish`, mirroring topic) would reintroduce one deliberately.
- **The gateway routes scopes, never semantics.** `pos` goes to a zone, `say` to a zone/party/user, `event` to a scope with its payload unread. Only `pos` and the party operations have gateway-side meaning; dungeon-entry negotiation, emotes and trades are all `event`.
- **`mapUrl` is pinned to the asset CDN**, not merely required to be https: it is announced to every client and fetched server-side by the game, which makes a free-form URL both an SSRF primitive and a way to point every player's browser at someone else's origin (the same reasoning already applied to stored webhook URLs).
- **`hello` is the first frame**: `{ userId, tick, mapUrl, capabilities, zone }`. The client learns its map and its feature set from the server and holds no configuration of its own. All of it is channel metadata edited in console; the gateway forwards, never computes.
- **Capability flags per `lobby` channel** (`pos`, permitted `say` scopes, `party`, `event`, `debug`). A message whose capability is off is refused with a typed error, never ignored — silence during a contest is expensive to debug. Invalid combinations (`say: ["party"]` without `party`, `say: ["zone"]` without `pos`) are rejected at channel creation, not at connect.
- **No area-of-interest filtering.** Zone-wide relay, retained last-known position per connection, gateway-synthesised `enter`/`leave` (without which a departed character freezes on every screen), coalesced at **5 Hz / 200 ms** to match the dungeon tick. Grid bucketing and radius config are explicitly not built at this scale. Movement is rate-limited and capped per-message delta; terrain is never validated.
- **Zone changes are decided by the game's HTTP API**, not the gateway — a rule-free relay cannot own them. The client re-announces and the gateway emits leave-from-old / enter-to-new from its retained state.
- **Sessions** (settled 2026-08-25): one player may hold a lobby socket and a dungeon socket at once; a second socket of the _same_ kind for the same `(channel, userId)` replaces and closes the first. Enforced through Redis `session:{channelId}:{userId} -> connectionId` with compare-and-delete on release, so the game's HTTP API can also see who is online. Two tabs writing one character record is the duplication path this closes.
- **Actor death is the gateway's to detect.** `RPUSH` returns the new list length, so queue depth is free — never poll `LLEN`. An absolute cap (~200) plus a no-progress timeout (~5 s) triggers an abort: close every connection for that `gameId` with a dedicated 4000-range close code **distinguishable from a normal finish**, `DEL` the queue key, `UNSUBSCRIBE`, alarm. A retry must allocate a **new `gameId`**, because the dead actor's lock outlives it. The queue key still needs a TTL as the backstop for the case where the gateway is the thing that died.
- Channel expiry is unchanged (7 d, extend +7, cap now+28): games are not left running for days.

## Storage shapes (settled 2026-08-25)

The platform generalises **storage shapes**, never game logic. Every game datum belongs to exactly one of three, and yyt never interprets a game's schema — it lives opaquely inside the value. The direction of travel is that a participant writes only a game Lambda and everything under it is the platform's.

- **asset** — immutable public files on S3 + CDN (`d.yyt.life` / `dev-d.yyt.life`): the map, with its NPC definitions inlined. The client GETs it directly, like a web page, and does local collision only; the dungeon Lambda fetches the same URL server-side because it is the authority. Format spec: `examples/sample-morpg/README.md` §4.6. Work: `todo/15-static-assets.md`.
- **doc** — MariaDB, per-`(channel, ownerId)` versioned JSON with **enforced CAS** (`If-Match` → 409 on mismatch): character, inventory, quest progress. Written only with a channel apiKey, read by the owner alone (`sub != ownerId` → 403) or by the server. Deliberately not Redis: `allkeys-lru` plus the mandatory-TTL rule would evaporate a player's level. Body size and per-channel document caps are required. Served by its own Lambda stack on `doc{-dev}.yyt.life` — see _state service_ below. Work: `todo/16-state-service.md`.
- **ephemeral** — Redis, TTL mandatory: party rosters, retained positions, dungeon queues and start events. Gateway-owned. A party survives a _reconnect_ (sliding TTL, mirrored to Redis so the game's entry API reads a roster it can trust rather than believing a client) but not a logout; a party that outlives a session would be a guild, which is out of scope.

Consequences settled with them:

- **Assets get a dedicated resource** (decided 2026-08-25, implemented 2026-08-25 as `asset_bundles`/`asset_files`/`asset_pending_uploads`, migration `3_assets`), not an extra `platform` enum value on `catalog_apps`. Object read is public and unauthenticated — a game client holds no GitHub account and fetches straight from the CDN; the management API is member-gated, and writes need the bundle owner or an admin. That flat owner rule _is_ the model: reproducing the catalog's per-app/per-group grid is exactly what a separate resource exists to avoid. Object keys are versioned (`assets/{bundle}/{version}/{path}`, the path relative inside the bundle so a map's own references keep resolving) and served `Cache-Control: public, max-age=31536000, immutable`, set with `MetadataDirective: REPLACE` when commit copies staging to the final key. Versions and paths are stored `utf8mb4_bin` (migration `4_assets_binary_paths`): they are S3 key segments and S3 keys are case-sensitive, so the database index has to agree with the storage it names — under the inherited `_ci` collation `v1/map.json` and `V1/map.json` were one row addressing two objects. Bundle **names** stay case-insensitive on purpose. Because the object is immutable, a `(bundle, version, path)` triple is **write-once** — a second commit under a different upload id gets 409 (re-committing the _same_ upload is idempotent and returns its file) — and a bundle that holds files **cannot be renamed**, its name being a live key segment. Commit **inserts the row before copying the object**: the row is the claim, so a lost race cannot overwrite a live `immutable` object, and a failed copy rolls the claim back. Deleting a version or a bundle is **refused while a lobby channel's `mapUrl` still points into it**, and a failed object delete keeps its row so the retry can finish — `assets/` is outside every sweep, so a stranded object is unreclaimable. The "current version" pointer lives in **channel config, not the CDN** — publishing a map is a config edit, so no invalidation ever happens. `Content-Type` is set at presign time from an extension allowlist (json/png/jpg/jpeg/webp/gif/bmp/ogg/mp3/wav/txt/csv; no `text/html`, no `image/svg+xml`, which scripts): letting a caller choose it would put attacker-controlled markup on our own CDN origin. Staging lives under `asset-uploads/`, swept exactly like the catalog's `uploads/`, and **no retention policy touches `assets/`** — a 404 there is not a degraded game but one that cannot load at all. `uploads`, `assets` and `asset-uploads` are reserved catalog app names, since an app name is the first key segment. Caps: 2 MB per file, 20 MB per bundle, 200 files per version, 50 versions per bundle, 20 bundles per member (admins exempt); every one of them counts presigns still in flight, because a grant is a reservation and a caller that pipelines them would otherwise see an empty bundle each time. Staging objects are reachable on the CDN by their random id until the sweep takes them, exactly like the catalog's `uploads/`; they carry the same allowlisted type, so this is not a new exposure.
- **The client is a browser.** It holds no content and no rules, receives its map URL and capability set in `hello`, and performs only the predefined actions of the protocol plus local collision. This is a constraint, not a description — it is what makes a shared client SDK possible later.
- **Participant credentials.** A game Lambda runs in the participant's own AWS account and talks to yyt Redis directly, so each `q` channel is issued a Redis ACL user scoped to `~game:{stage}:{channelId}:*` / `&game:out:{stage}:{channelId}:*` — a wrong prefix fails `NOPERM` instead of reading another game's queue. The `{stage}` segment matters: one Redis instance serves both stages, so without it a dev credential would match prod keys. That credential is issued once and never logged, the same discipline as `rotate-secret` — but the `q` **channel** itself has no secret and `rotate-secret` refuses it; the two are separate things.
- **The console mints them itself** (decided 2026-08-26, implemented the same day: `POST|GET|DELETE /channels/{id}/redis-user`). Redis has no way to delegate "may create users below this prefix", so anything holding `ACL SETUSER` can widen itself — the credential the console carries for this is root-equivalent in Redis terms, and that is accepted rather than worked around. The reasoning: console already holds every auth channel's signing secret, so its blast radius does not change class; the alternatives each buy less than they cost (routing issuance through the not-yet-written Go gateway inverts `todo/14`'s order and adds a console→gateway auth path, and issuing by hand puts a manual step between a team and their first working Lambda, which is the friction this platform exists to remove). What the design does buy is that **no accidental path reads data**: the issuer is a _second_ account per stage (its name lives in `yyt-stateful`, never here) with `-@all`, four `acl|…` subcommands and **no key or channel patterns at all**, used by one module that never runs a data command, while the console's own user keeps `-@dangerous` and no ACL rights. The username is derived like the prefixes (`game_{stage}_{channelId}`) and the issuer refuses every name outside `game_` — `ACL SETUSER` is an upsert, so one miscomputed id would otherwise rewrite one of the platform's own service accounts and lock a whole service out of Redis. Issue is idempotent-by-replacement (`reset` first, so a re-issue rotates rather than stacking a second password) and always `ACL SAVE`s, or the credential would work until the next Redis restart and then fail on contest day. The account is revoked when the channel is **deleted** (by hand or by the daily sweep) but deliberately **not when it merely expires**: extending revives a channel, and stripping a credential the owner still holds would be a silent trap. The participant grant also removes `scan`, `randomkey`, `dbsize`, `pubsub` and `memory` on top of `-@dangerous`: Redis does not filter `SCAN` by ACL key patterns, so without that a credential could enumerate every key name on the instance — both stages, every service — while being refused every read (measured, and fixed, 2026-08-26). The same fact is why every key that names a secret stores its digest instead. **Redis has no per-account memory quota** and `allkeys-lru` means an abuser evicts other services' data rather than their own, so the platform's answer is observation plus revocation, not a limit: the daily cron reports instance memory and per-channel key counts. Splitting participants onto their own Redis instance with its own `maxmemory` is the only real isolation and is deliberately deferred.
  A stage without a state stack is a valid state too: `POST`/`DELETE /channels/{id}/doc-key` answer 503 with `reason: state_not_configured` rather than minting a credential with nowhere to spend it, while the **read** still returns the block with `configured: false`, because that read backs every auth channel's detail page.
  A stage without an issuer account is a valid state — `POST`/`DELETE` answer 503 with `reason: redis_acl_not_configured`, while the **read** still returns the derived block with `configured: false` rather than failing, because that read backs every `q` channel's detail page and a 503 there would paint an error over a perfectly healthy channel.
- **The Redis prefixes are derived, not configured.** All four keys tslib's actor needs plus the pub/sub channel are computed from the channel id — `game:{stage}:{id}:{event,queue,lock,awaiter}:` and `game:out:{stage}:{id}:` — and are never stored or typed in. Deriving three of the four would be worse than deriving none: the fourth would be invented outside the participant's ACL scope and fail `NOPERM` at actor start. They have to agree on three sides at once — the gateway, tslib, and the participant's own Lambda — and a mismatch is a silent no-op rather than an error, so exactly one place computes them and the console, CLI and SPA present the result as one copyable block. The block is passed to tslib's prefix options directly: helpers that append a segment of their own turn `…:queue:` into `…:queue:queue:`, which stays inside the ACL and therefore fails silently rather than loudly. Abuse is handled in person; what is not optional is per-prefix key-count and memory observability before the shared 256 MB ceiling evicts someone else's state.

## state service (`doc.yyt.life`) — added 2026-08-26

Serves the **doc** shape from _Storage shapes_ and nothing else: one versioned JSON blob per `(auth channel, ownerId)` in `state_docs` (migration `5_state_docs`).

- **Its own Lambda stack, not a process on the box.** The `yyt-stateful` host exists for the two things that must hold a socket or the data itself — Redis and MariaDB — and a REST reader/writer holds neither, so the _Stack_ table's rule puts it on Lambda. The obvious name was in any case unavailable — `state` is already taken by an existing record for that box (see the private ops repo) — which is why the API is `doc{-dev}.yyt.life`. (Until 2026-08-26 the `doc` bullet above said "served under the existing `yyt-stateful` hostname"; that sentence read the _storage_ location as the _serving_ one and contradicted the _Stack_ table two screens earlier.)
- **Scoped to the auth channel, not to the game channel.** `ownerId` is `deriveUserId(authChannelId, provider, providerUserId)` — it means nothing outside the auth channel that produced it, so any other scope needs a mapping and a channel segment in every path. A team has exactly one auth channel and therefore exactly one document namespace, whether it runs a `q` channel, a `lobby` channel, or both. `q`/`lobby` keep their empty `secret_json`.
- **The client reads only its own row.** `GET /s/{ownerId}` with the same channel JWT the gateway takes: `iss` names the channel, `sub` must equal `ownerId`, otherwise 403. There is no list route — enumerating a channel's owners is a server capability, and a route that a client can reach with its own token would hand it one.
- **Only a server writes**, holding a channel apiKey as `Authorization: Bearer`. Auth channels had none; they get one now, deliberately and _separately_ from the signing secret, issued and rotated by `POST /channels/{id}/doc-key` and revoked by `DELETE`. A second secret rather than a reuse of `secret`, because the two have different holders — the signing secret never leaves the platform, this one is pasted into a participant's Lambda — and rotating either must not invalidate the other. The key is **self-identifying** (`yds.{channelId}.{random}`, the `.` being outside the channel-id charset): the routes carry no channel segment, and the alternative to reading the id out of the credential is scanning `secret_json` across every row.
- **Every write is conditional.** `PUT /s/{ownerId}` requires `If-Match`; `"0"` means "no row yet" and creates. A missing `If-Match` is **428**, a stale one is **409** carrying the current `ETag`. This is the entire point of the shape — two dungeon results landing on one inventory is the failure it exists to prevent, and an unconditional whole-blob write is that bug restated. `DELETE` accepts `If-Match` but does not demand it.
- Caps: **64 KB** per document, **10000** documents per channel, both refused rather than trimmed. `owner_id` is `utf8mb4_bin`: it is an identity the authorization check compares byte-exactly, so a case-insensitive index would let two identities share one row — the same bug migration `4_assets_binary_paths` fixed for S3 key segments.
- **No Redis and no cache.** Rows carry secrets, and `rules/data.md` forbids caching those; one `SELECT` per request is the cost of correctness here. That `SELECT` runs for **any** bearer, before a body limit or an authorization check, so unauthenticated junk is what actually competes for the stack's `reservedConcurrency` — which is why the stack sets an API Gateway throttle rather than leaning on the reservation alone.
- **The document is stored as sent, byte for byte.** The request is parsed only to prove it is JSON; re-encoding it would be interpreting it, and `JSON.stringify(JSON.parse(x))` silently rewrites an integer past 2^53 (a snowflake id), collapses duplicate keys and reorders integer-like ones. The size cap is therefore measured on those same bytes.
- **A browser is a first-class caller**, so the routes carry CORS with `*` — the credential is an explicit `Authorization` header, never an ambient cookie — and, critically, `Access-Control-Expose-Headers: ETag`. `ETag` is not CORS-safelisted, so without it a browser client cannot read the version it is then required to send back in `If-Match`, and the whole conditional-write contract is unusable from the client the design assumes.
- **This is the first writer of the database that is not console**, so the ownership rule is narrowed rather than broken: console still owns the schema and every migration, and the state account's grant is `SELECT` on `channels` plus `SELECT, INSERT, UPDATE, DELETE` on `state_docs` alone. That grant is table-level, so it does include every channel's `secret_json` — the same reach auth/topic/match already have, and the honest claim is "cannot touch members or api_tokens", not "sees only what it needs". A stage whose account has not been created yet simply has no state stack deployed.
- Documents die with their channel: the console sweep drops a channel's documents when the channel is deleted, the same lifecycle point at which a `q` channel's Redis credential is revoked, and for the same reason — expiry is reversible by extending, deletion is not.

## Hackathon workflow (console)

- Event state machine `draft → proposing → voting → decided → published → closed`, advanced by admins.
- Proposals/votes require GitHub login (`pending` allowed). Proposal = free text (title/body incl. date, place, topic). One vote per person, changeable while `voting`.
- In `decided` an admin picks the winner and uploads a poster (S3); `published` exposes `/events/{id}` publicly.
- Visibility: anonymous sees `published`/`closed`; logged-in members see everything except `draft`; admins see all. Vote counts are hidden while `voting` (only the caller's own vote is returned) and public from `decided` on. Members may hold up to 3 proposals per event, edit/withdraw them while `proposing`; admins may remove proposals until `decided`.
- Posters live in a private bucket owned by the console stack (`yyt-console-posters-{stage}`, retained on stack removal), uploaded through a presigned PUT (png/jpeg ≤ 5 MB, content headers signed) and attached only after a `commit` step re-checks the object. Poster visibility follows the event's visibility and is enforced by the API, so CloudFront does not front the poster bucket: `GET /events/{id}/poster` redirects to a 10-minute presigned GET (browsers may cache it, so a replaced poster can lag up to 10 minutes).

## Binary catalog (console)

- The legacy binary distribution platform ("catalog": apps/groups/artifacts/permissions API, admin web UI, `cata` CLI, Android installer app) is absorbed into this repo: console API routes + SPA section + `yyt catalog` CLI subcommands + `apps/installer` (Flutter). The standalone catalog stack and its API domains (`cata.yyt.life`, `dev-cata.yyt.life`) are retired; the API lives on the console domain.
- Identity/permissions: console `members` only. Catalog permission model is kept (admin > app owner > per-app > per-group, levels `read` | `edit`) but keyed on `members.id`. Legacy username-based rows are migrated by matching `members.github_login`; unmatched users are imported as a pending mapping list resolved on their first console login.
- Auth for CLI/installer: console gains a **GitHub device flow** login that issues a console API token (the operator OAuth app has device flow enabled). Catalog's separate `cata_` API keys are retired; console `yyt_` API tokens are used everywhere.
- Storage: catalog tables move to console MySQL (migration v3: apps, groups, artifacts, app/group permissions, pending uploads). SQLite-on-S3 and the external HTTP Redis are retired; a one-off script imports the legacy SQLite data. Redis is used only for short-lived state (device-flow codes, upload tracking) under `console:{stage}:`.
- Schema management moves to **Prisma 7** (decided 2026-08-24, superseding the same-day rejection): `schema.prisma` + generated client (`prisma-client` generator, `@prisma/adapter-mariadb` driver adapter — Rust-free, so Lambda bundle/cold-start cost is negligible). Migrations run at **deploy time only** — `prisma migrate deploy` from the local deploy script (and later GitHub Actions); the in-runtime cold-start `migrateConsoleDb`/`GET_LOCK` model is retired once the cutover lands. Existing v1–v3 tables are absorbed as a baseline (introspect, no destructive change); new schema work starts on Prisma migrations. Repository interfaces (`ConsoleDb`/`EventsDb`/`CatalogDb`) stay as the seam; their implementations move onto PrismaClient. Tests may use Prisma's testing guidance or **testcontainers-run MySQL** (amends the earlier "no Docker" testing stance); in-memory fakes remain where they still pay for themselves.
- Artifact serving stays **public CDN direct links**: `d.yyt.life` (prod) / `dev-d.yyt.life` (dev) in front of the existing buckets `yyt-binary-dist` / `yyt-binary-dist-dev`; existing object keys and URLs remain valid. Uploads go through presigned PUT to an `uploads/{uploadId}/{filename}` key and are finalized by an explicit `commit` call (HeadObject verify → copy to the final key → artifact row), mirroring the proven poster flow. The S3-event finalizer was considered and rejected: bucket notifications on these manually-managed buckets sit outside IaC and the dev bucket's notification config is still owned by the legacy catalog stack's custom resource, so a second writer would race it. Stale pending uploads and orphaned `uploads/` objects are reclaimed by the daily sweep. The CDN/DNS for these domains is pre-existing manual infra; its state is surveyed and recorded before any change.
- Carried-over features: version/tag metadata (JSON tags incl. platform, abi, build type), retention cleanup (`keep_recent_versions`, daily sweep + dry-run preview), Slack notification per app, iOS ad-hoc OTA (`manifest.plist` + `itms-services://` install URL), upload-status tracking.
- Game assets reuse the bucket, CDN and presigned-upload plumbing but **not** the app/artifact resource or its permission model — see _Storage shapes_. They are a separate, publicly readable resource with its own key layout and `Content-Type` allowlist.
- Installer app: new applicationId **`life.yyt.catalog`** with a new signing key (the legacy id/signature is abandoned; existing installs reinstall once). It logs in via the device flow and talks only to the console API; it is distributed through the catalog itself.
