# Deployment

- **A contract migration is its own commit, and only after every stage runs the bundle that fills the columns.** `deploy.sh` applies every pending migration unconditionally, so a `NOT NULL`/`DROP` file that sits in the tree is applied by the next `deploy.sh console <stage>` whether or not that stage was ready — the technical gate (2026-08-26) is `migrate.sh`: a pending file whose first line is `-- contract` is refused unless `--allow-contract` is given and `scripts/contract-preflight.mjs` passes, and `deploy.sh` never passes the flag. The commit is still a gate of its own: check `migrate status` on prod and the deployed bundle version before committing `m0008_team_project_contract`, and apply it by hand (`migrate.sh <stage> deploy --allow-contract`) before the next `deploy.sh console`.

## Decision flow

1. Decide whether the change needs only a `dev` redeploy (default for every task) or a `prod` release.
2. `prod` is deployed only when the user asks; confirm which stacks are affected before running.
3. CLI releases: tag `cli/vX.Y.Z` on `main` → `.github/workflows/cli-release.yml` runs `cli/scripts/build-release.sh` (linux/darwin/windows × amd64/arm64) and publishes the GitHub Release; `install.sh`, `install.ps1` and `yyt self update` all read that asset layout (`rules/workflow.md` _Go CLI_). Decide patch vs minor bump with the user when not obvious.
4. After deploying, run the smoke commands from the area's todo doc and verify the uploaded artifact/endpoint.

## Conventions

- Region `ap-northeast-2`, `AWS_PROFILE=yyt`, stages `dev`/`prod`, domains `{auth,console,topic,match,doc}.yyt.life` plus `topic-ws.yyt.life` (dev: `-dev` suffix) via `serverless-domain-manager`. The state stack is on `doc`, not `state`: the `state` name already resolves to the stateful box (the record lives in the private ops repo), so the two would collide.
- **Order for the first state deploy on a stage: cut the other stacks' reservations first, then console, then state.** `reservedConcurrency` only changes on deploy, so shipping `state` while auth/match/topic still hold their old numbers puts the budget over the host's `max_connections` — and the symptom is `ER_CON_COUNT_ERROR` for _every_ stack, not just the new one. Then console before state, because console owns every migration and `state` reads a table one of them creates (deployed the other way round, state answers 503 with `prisma P2021` in the cause, which is at least diagnosable). A stage may legitimately have no state stack: `bootstrap-ssm.sh` and `get-env.sh` skip `state` when its env file / SSM prefix is absent (every other service stays fatal), and console then omits `docUrl` from auth channel views rather than advertising a dead host. The state account is table-scoped — `SELECT` on `channels`, read/write on `state_docs` — so a bug there cannot touch `members` or `api_tokens`; verify a new stage's grant with `SHOW GRANTS` before believing it.
- `doc-base-url` is a stage-wide plain `String` parameter (a public domain, not a secret), written by `bootstrap-ssm.sh` when `local/env/state.<stage>.env` exists and **deleted** when it does not. `put` never deletes, so anything that can be un-configured needs an explicit delete branch or the stage keeps advertising what it no longer serves — the same shape as the console ACL issuer pair.
- **A stack deploy ships everything merged, not just the feature that asked for it.** `deploy.sh <service> <stage>` builds from the working tree and `migrate.sh` applies every pending migration in order, so a later feature's prod rollout silently carries every earlier "prod on request" change of the same stack (the 2026-09-06 kv rollout shipped the event redesign and list sort/filter that were still marked "awaiting prod"). Before planning a prod deploy for a pending item, check the stack's `LastUpdatedTime` (`aws cloudformation describe-stacks`) against the commit date — it may already be live; and conversely, never assume a prod deploy of one feature leaves other merged-but-unannounced changes behind.
- Secrets come from SSM `/yyt-service/{stage}/*` (per-service MySQL/Redis values uploaded from `local/env/*.env` by `scripts/bootstrap-ssm.sh`). `scripts/get-env.sh <stage>` rebuilds `local/env/` from SSM on a new machine. Rotation order: update `local/env` via `yyt-stateful` → `bootstrap-ssm.sh <stage>` → redeploy every stack of that stage (SSM values are baked into Lambda env at deploy time) → revoke the old credentials. `bootstrap-ssm.sh dev` keeps the existing `debug-key` unless `DEBUG_KEY` is exported, and every stage keeps its existing `gateway-token` (generated on first run, written to `local/deploy/gateway-token.<stage>`) unless `GATEWAY_TOKEN` is exported — rotating it means redeploying console **and** restarting the gateway with the new value. Never commit `.env*` or anything under `local/`. `scripts/bootstrap-ssm.sh` is the source of truth for what lives under `/yyt-service/{stage}/`; when it gains or loses a key, update the enumerations in `docs/secrets.md` §2 and this file in the same change (checked in sync 2026-09-06).
- Lambda: `nodejs22.x`, arm64, `serverless-esbuild` (no layers), built-in prune keep 5, log retention 14 days.
- Infra changes (ACM, Route53, CloudFront, buckets) are manual, outside IaC; record what was created by hand in this file's relevant section and put the identifiers in `local/ops-notes.md` (the old ledger `todo/07-infra.md` retired 2026-09-06 into `local/todo-archive/`). Two exceptions live in the console stack and are never edited by hand: the console's own distribution, and the per-site host distribution (_Per-site host_ below) — except their `Enabled` flag: the CDN guard and `scripts/cdn-switch.sh` switch the per-site host off and on, and only the script the console's own (_CDN emergency_ below).
- Console stack needs stage-wide SSM keys `github-client-id`, `github-client-secret`, `admin-github-logins`, `session-secret`, `gateway-token`, `cloudfront-cert-arn` (us-east-1 ACM cert for `*.yyt.life`, looked up by `bootstrap-ssm.sh`) (`scripts/bootstrap-ssm.sh <stage>` reads them from `local/env/console.<stage>.env`; shell env vars override); `bootstrap-ssm.sh prod` refuses an empty admin list. `--param webUrl=` points post-login redirects at the SPA host once CloudFront exists. `artifact-bucket` and `site-bucket` (plain Strings, the hand-made distribution/site buckets — required since 2026-08-30; `serverless.yml` no longer carries bucket names), `gateway-ws-url`, `cdn-distribution-id` (the CloudFront distribution of the stage's artifact CDN, read by the daily usage digest; absent = no CDN metric) and `site-distribution-id` (the static-site distribution, invalidated after every site deploy; absent = deploys go live without invalidation and the edge serves the old tree for its TTL) are optional and set by hand (plain `String` parameters, not secrets — but the distribution id is still an infra identifier: it belongs in SSM/`local/ops-notes.md`, never in source or docs) once the gateway host resolves; while it is unset, `lobby`/`q` channel views deliberately omit `wsUrl` rather than print a dead one. Scheduled functions use a fixed `cron(...)` (console `expire`: 18:00 UTC) and get their own Errors alarm — except `gatewayProbe` (`rate(5 minutes)`, prod schedule only), which swallows its own errors and publishes to the alarm topic directly (`rules/serverless-aws.md`). The optional `site-host-cert-arn` (plain String, set by hand per stage, default `""`) switches the per-site host on (_Per-site host_ below).

- The console stack owns the poster bucket `yyt-console-posters-{stage}` (`DeletionPolicy: Retain`): `sls remove` leaves it behind, and a re-created stack adopts it only if the name is unchanged (delete or rename the bucket first otherwise). Uncommitted presigned uploads (`posters/{eventId}/…` never bound by `commit`) are not swept yet; empty them by hand if they matter.
- Client compatibility routes are removed only after **every installed client** has moved, not after the new build is published: the old installer finds its own update through the very route being removed, so removing it first strands those devices on manual sideload. Confirm device versions with the user before deleting a compatibility route.

## Stateful host (Elastic IP, DNS)

- Attaching an Elastic IP to an instance that only had an auto-assigned address **is a replacement**: the old address is released at association and cannot be recovered. Before attaching, list every DNS record that points at the current address by _value_ (reverse search across all hosted zones — there were more names than expected) and have the Route53 change batch ready so the UPSERT (and a shorter TTL) goes out in the same window; then verify from the host check script, both stages' CLI login, and a WebSocket smoke. Any address that becomes static is an identifier for the public-repo guard (`rules/security.md`).

## Channel-kind migrations (learned 2026-08-25)

- The realtime gateway is **not** a Serverless stack: `gateway/vX.Y.Z` tags run `.github/workflows/gateway-release.yml`, which pushes `ghcr.io/yingyeothon/yyt-gateway:{X.Y.Z,latest}` (distroless, non-root, `linux/amd64+arm64`). The private `yyt-stateful` repo runs it (256 MB limit, restart policy, TLS at its proxy or `GATEWAY_TLS_*`) with its own Redis ACL user spanning `~gateway:{stage}:* ~game:{stage}:*` + `&game:out:{stage}:*` (`-@dangerous` like every account), `GATEWAY_TOKEN` = SSM `gateway-token` of the same stage, and then sets SSM `gateway-ws-url` so console starts rendering `wsUrl`. Rotating `gateway-token` means redeploying console **and** restarting the gateway. A deploy disconnects every player (`1001`); deploy before the event, never during.
- `channels.kind` is a MySQL ENUM, so a new kind is a migration plus an expand/contract sequence. `2_gateway_channels` (adding `lobby`, `q`) is additive and safe in the forward direction: the value goes on the end, matching `schema.prisma`'s order, and nothing reads it until the new bundle is live.
- **Rolling back is not symmetric.** Once a `lobby`/`q` row exists, an older console bundle's `channelView`/`rotateSecret` fall through to their `match` branch (a lobby would list a `wss://match-…` URL, and `rotate-secret` would mint and store an apiKey into a channel that is meant to have none), and the older generated Prisma client may reject the unknown enum value outright on read, which would 503 the whole channel list rather than mis-render one row. Delete the new-kind rows before rolling a stage back past this commit. auth/topic/match are unaffected either way — they go through `findAuthChannel`/`findMatchChannel`/`findTopicChannel`, which return `undefined` on a kind mismatch, and topic's only scan filters `{kind:"topic"}`.
- **prod's Prisma cutover already happened** (2026-08-24, together with the catalog release — the earlier note here claiming prod still ran pre-Prisma Lambdas was wrong; `/catalog/apps` answering `401` on `console.yyt.life` only exists in post-Prisma code). What survives as a lesson is the sequencing: **apply the migrations on their own before the deploy** rather than letting `deploy.sh console prod` do both. `scripts/migrate.sh <stage>` is standalone, all three pending migrations were additive (a widened enum plus three new tables), and the live runtime kept serving through them, so the schema and the bundle move as two separately verifiable steps instead of one. That order is also the safer rollback: the old bundle tolerates the new tables, so only the bundle has to go back. Done on prod 2026-08-25 — `2_gateway_channels`, `3_assets`, `4_assets_binary_paths` applied first, then `deploy.sh console prod` reported "No pending migrations to apply".
- Pre-flight for `3_assets`: `select name from catalog_apps where lower(name) in ('uploads','assets','asset-uploads')` must return nothing on the stage being deployed. The reservation in `catalog.ts` only guards new apps; a pre-existing app named `asset-uploads` would have its committed binaries deleted by `runAssetSweep` 24h later. Both stages were verified empty on 2026-08-25.
- `schema_migrations` (the legacy pre-Prisma migrator's table) is frozen at whatever version each stage reached before the cutover — prod stopped at 2, dev at 3 — and nothing reads it any more. It is not drift; do not try to reconcile it with `_prisma_migrations`.

## Local credential files

- `scripts/get-env.sh <stage> [service…]` rebuilds `local/env/<service>.<stage>.env` from SSM and refuses to overwrite unless `FORCE=1`. That refusal is the only thing standing between a routine re-pull and data loss, because the file is **not** a pure projection of the per-service SSM prefix: console's copy also carries stage-wide values (`github-client-*`, `admin-github-logins`) that `bootstrap-ssm.sh` reads back out of it. A `FORCE=1` pull that restored only the per-service keys left those blank, and the next `bootstrap-ssm.sh` would have uploaded an **empty** OAuth app — breaking console login on that stage. Fixed 2026-08-26 by having `get-env.sh` restore them too; the round trip is now lossless, verified by diffing before and after.
- The general shape of the trap: any file that is both generated and hand-extended needs its generator to reproduce _everything_ in it, or it needs to stop being hand-extended. Treat `FORCE=1` as destructive until the round trip is proven.

## SSM environment values (2026-09-04)

- **An `${ssm:…}` without a default is resolved at deploy time, so it blocks the whole stack, not the feature that needs it.** `KV_KEK` was written that way to make a missing KEK loud; the effect was that a stage whose parameter did not exist yet could deploy nothing at all — a `/s/*` hotfix included, and `sls remove` too, since that re-resolves the config. That is exactly the coupling `services/state/src/handler.ts` goes to trouble to avoid at runtime (a bad KEK 503s `/kv/*` and leaves `/s/*` alone). Give such a value the `, ""` default, treat empty as "not configured" in code, and make the emptiness loud in the log and in the smoke instead of at the deploy. `test/serverless-invariants.test.ts` pins it, because the tempting "fix" under deploy pressure is to remove the default again.
- A 503 raised as an `AppError` is a **successful** Lambda invocation, so no `Errors` alarm sees it. A stage-wide fault expressed that way (every `/kv/*` answering `kv_encryption_not_configured`) is visible only in the log group — name the log lines in the service README's runbook. For state the owner spent its one alarm slot on this (2026-09-06): prod `api-failures` is a term-matched log metric covering both the handler's 5xx lines **and** the runtime's own non-JSON failures (`Task timed out`, `Runtime.`) — widening to a `$.m` JSON filter alone would have silently dropped the timeout/init-crash coverage the old `Errors` alarm had (`rules/serverless-aws.md`). Consequence for the prod rollout: deploying state before the kv grant makes every `/kv/*` probe a `request failed` line, so the smoke will page — apply the grant first or expect the page.
- **A key-encryption key is not a rotatable secret like the others.** `debug-key` and `gateway-token` follow "keep what SSM holds unless the operator forces a new one" because a stale copy is only an inconvenience; `kv-kek` follows the same shape (`scripts/bootstrap-ssm.sh`, 2026-09-04) with two additions, because a replacement makes every wrapped DEK — and therefore every stored kv value — unreadable for good. First, a _different_ value in the env file is refused unless `KV_KEK_ROTATE=1`, where the others would silently rotate. Second, the read that decides "there is nothing here yet" distinguishes `ParameterNotFound` from every other `aws ssm get-parameter` failure and aborts on the latter: an IAM hiccup or a wrong profile would otherwise look exactly like a fresh stage and mint a new KEK over a live one. The script's blanket rotation instructions (update `local/env` → re-run → redeploy every stack) explicitly exclude it.
- **`envval` is a pipeline, and `set -o pipefail` makes an absent key fatal.** `bootstrap-ssm.sh`'s `envval` starts with `grep -E "^KEY="`, which exits 1 when the key is not in the file; every existing caller reads a mandatory key, so nothing noticed until `KV_KEK` — an _optional_ one — took the whole script down at the assignment, before any of its own logic or a single log line ran. The failure is silent (`set -e`, no message, exit 1 after the previous step's happy log), which reads as "the script finished" unless the exit code is checked. Any optional key needs `$(envval … || true)`.
- **A field that becomes optional deploys against the direction of the read**: **match before console before web** for the callback-less match mode (2026-09-08, `todo/38`). `MatchChannelConfig.callbackUrl` is read through an unchecked `JSON.parse(... ) as MatchChannelConfig`, so an old match bundle handed a config row without the key passes `undefined` into `new URL()` — every match on that channel answers `{"type":"failed","reason":"callback"}` until match is redeployed, and the playbook sends the operator to look for an unreachable URL that does not exist. Console must not be able to _create_ the shape before match can _read_ it. The general rule: when a producer starts emitting a value (or an absence) a consumer's type does not admit, the consumer ships first, however "additive" the change reads on the producer's side. The reverse order for the SPA is merely noisy (an old console answers 400 to the empty field), so web goes last as usual.
- **A new enum value deploys against the direction of the read, like an optional field does** (`m0016_kv_server_scope`, 2026-09-08): Prisma's generated client throws when it _reads_ a value it does not know, so `console` (which mints the value) and `state` (which reads it) must ship back to back with **no `server`-scoped collection created in between**, and a rollback of either needs those collections deleted first. The failure is not a 403 but a 500 — and on the console side it kills a whole list page, which stops the daily kv sweep. Order and rollback preconditions: `docs/kvstore.md` _Deploy order_. On prod the migration goes first and alone (`scripts/migrate.sh prod`, dump taken, before/after checks from the migration header), because `deploy.sh console prod` would apply this table rebuild unattended along with whatever else is pending.
- **A collection-scoped limit row is the same rollback hazard (`m0027_collection_limit_scope`, 2026-09-29, `todo/54`):** before rolling console back past it, delete or decide-and-purge every row with `collection_id IS NOT NULL` in `limit_requests` and `limit_overrides`; deploy console before web and CLI, which now file `collection:` scopes and read `kv.*` keys.
- **A team-scoped limit row breaks an older console bundle's reads, not its writes (`m0026_team_limit_scope`, 2026-09-29).** The old generated client selects an explicit column list without `scope_team_id`, so `scopeOf()` throws `internal` for such a row — a 500 on `GET /admin/limit-requests`, the team's request list and the daily sweep's override/decision purge, for as long as the row exists. Deploy console before web and CLI (they only file such rows against a console that has the column), and before rolling console back past this commit delete or decide-and-purge every row with `scope_team_id IS NOT NULL` in `limit_requests` and `limit_overrides` (a revoke plus a purge of the decided requests does it through the API).
- **A new field the producer writes and the consumer reads deploys consumer-first, even when nothing is optional about it** (`userSalt`, 2026-09-09, `todo/41`). Console mints the salt into an auth channel's `secret_json`; auth reads it to derive a player's `sub`. Console-first opens a window where a channel already has a salt while auth still derives **unsalted**: a player who signs in during it gets one id, and the moment auth ships the same human gets a different one — new character, new kv rows, new state document, the old ones orphaned, and no error anywhere. Their old JWT keeps verifying until `exp` (up to 7 days) and the gateway caches it by token, so both identities are live at once. Auth-first is a byte-identical no-op over channels that have no salt yet, so the window is zero. **`deploy.sh auth <stage>` then `deploy.sh console <stage>`** — and on `dev`, auth needs `--param debugHooks=1` or every smoke loses its seeding hook.
- **A stored identity input can be rolled forward but not back.** Once auth is salted and a salted channel has issued one token, rolling auth back past that commit re-derives every player of every salted channel to their unsalted id. The salt is _stored_, not derived, so rolling forward restores the exact ids and only the writes made inside the window are orphaned — but "delete the `userSalt` to make it consistent" is the one repair that cannot be undone, because it pins the channel to the reversible id for ever. Console rollback is safe by contrast: every writer of `secret_json` spreads the stored object, so an older console preserves an existing salt and merely stops minting new ones.
- **`deploy.sh console <stage>` runs `migrate.sh` first, so a console deploy is never "just this change" on a stage with a pending migration.** On 2026-09-09 prod still had `m0016_kv_server_scope` pending behind an owner-gated procedure, which made `deploy.sh console prod` unusable for an unrelated change: it would have applied that table rebuild unattended and shipped the kv `server` scope with it. Check `migrate.sh <stage> status` before assuming a console deploy is available, and prefer the stack that does not need one — 41 ships to prod as **auth only** for exactly this reason.
- **Leaderboard rollout order per stage** (`docs/leaderboard.md` _Operating notes_): `deploy.sh console <stage>` (applies `m0017_leaderboard` **and** `m0018_lb_owner_index`) → the owner's `GRANT` in the ops repo (`SELECT` on `leaderboards`, DML on `leaderboard_scores`; the tables must exist, so a `GRANT` before the migration is `ERROR 1146` and applies nothing) → `deploy.sh state <stage>` → `deploy-web.sh <stage>` → the leaderboard smoke. Until the grant lands, every `/lb/*` route answers `503 database error` while `/s/*`, `/kv/*` and the whole console API work — measured on dev 2026-09-10, and on prod that is `api-failures` log lines, so apply the grant before the state deploy or expect the page. There is **no** enum-widening hazard here (unlike `m0016`): the migration only creates tables, so an old bundle of any stack simply never selects them, and `auth`/`topic`/`match` need no redeploy. Only the **new table** starts that three-step dance: `m0018` adds an index to a table the grant already covers, so it needed neither a grant of its own nor a pause and simply rode along with `m0017` (the index half of the rule `rules/data.md` states for a column). Rollback is **not** symmetric, and this is the part to read twice: a console bundle older than this work answers 503 instead of 409 on project/team delete once boards exist (the kv rollout's trap), and it also has no `deleteChannelLbScores` and no `runLeaderboardSweep` — so while it is deployed, every auth-channel delete orphans its players' scores **permanently** (the ids exist nowhere else once the channel row is purged) and retention stops entirely, both silently. Rolling forward does not repair either. Treat a console rollback here like the `userSalt` one above: possible, but with a known cost, and the order stays console → state → web.
- **Deploying the _reader_ last is what buys you a calm gate.** The leaderboard's prod rollout (2026-09-10) was console (migrations + API) → web → the ops repo's `GRANT` → state. Because state went **last**, prod spent the whole gap serving a bundle with no `/lb/*` routes at all: nothing 503ed, `api-failures` stayed quiet, and the grant could be taken at whatever pace its owner wanted. The kv rollout ordered grant-before-state for the same reason and `rules/deployment.md` already warns that the reverse pages — say the positive version too, because "no alarm pressure" is the property that makes a two-repository handoff pleasant instead of a race.
- **Acceptance on prod is not the smoke.** Prod has no debug hooks, so the check is a real credential against the real API — and it should spend _every_ privilege a new grant adds, not just the first. The leaderboard's was `GET /lb/{board}` (SELECT), a first `PUT` (INSERT), a better `PUT` (UPDATE), `GET /top` + `/scores/{owner}`, and a `DELETE` (which is also the `m0018` index's lookup), then a cross-project 404. A grant missing only `UPDATE` would otherwise first show up the day a player beat their own score.
- **`channels doc-key issue` replaces the stored key; it does not return the existing one.** So a prod acceptance must **not** borrow a live channel's key — issuing one invalidates whatever the owner holds. Create a throwaway auth channel, issue its key, run the check, delete the channel (which kills the key). The cost is one soft-deleted channel row holding its `(team, name)` for 30 days until `purgeChannels`, which is the same residue every dev smoke leaves and is worth it.
- **Social rollout order per stage** (`docs/social.md`, `todo/39`): `migrate.sh <stage> status` → `deploy.sh console <stage>` (applies `m0019_social`) → the owner's `GRANT` in the ops repo (`SELECT, INSERT, UPDATE, DELETE` on **both** `social_profiles` and `social_relations`; the tables must exist first, or the `GRANT` is `ERROR 1146` and applies nothing) → `deploy.sh state <stage>` → the gateway image and its container recreate (owner) → `deploy-web.sh <stage>` → `scripts/smoke/social.mjs`. The leaderboard's calm-gate property holds again: an old state bundle has no `/social/*` at all, so the gap between the migration and the grant is a **404**, not a 503, and nothing pages. `UPDATE` is easy to leave out of the grant and hard to notice — the first thing that needs it is a player _renaming_ a profile, so the smoke renames one. There is no enum-widening hazard (`social_relation_state` lives on a table that did not exist, so no generated client anywhere can read a value it does not know) and `auth`/`topic`/`match` need no redeploy. **The gateway is independent**: `/presence` touches neither the migration nor the grant, so a stalled grant must not hold its release hostage — but a release recreates the container and disconnects every player with `1001`, so it goes before an event, never during. Rollback: a console bundle older than this work has no `deleteChannelSocial` and no `runSocialSweep`, so while it is deployed every auth-channel delete orphans its players' profiles and relations permanently and expired requests stop being reclaimed — both silently, and rolling forward does not repair the first. Backing the migration out is two `DROP TABLE`s with no foreign key to unwind, but at a channel's scale the rows come out in bounded batches first. Two more things the leaderboard's bullet did not need: the smoke needs **auth** on dev with `--param debugHooks=1` as well as console (it mints three player tokens), and after the first deploy invoke the sweep once (`aws lambda invoke --function-name yyt-console-<stage>-expire /dev/stdout`) and grep for `social sweep` — its two `DELETE`s are the only thing that ever exercises `social_relations_stale`, and a plan or permission problem there would otherwise surface a day later at `error` with no alarm. **And the prod acceptance cannot be done with a doc key alone**: a server key may never create a relation (`docs/decisions.md` #9d), so it can prove all four privileges on `social_profiles` but only `SELECT` and `DELETE` on `social_relations`. A grant missing `INSERT, UPDATE` there passes that check and fails on the first player's first friend request — so the acceptance needs a real player token on the throwaway channel (an OAuth sign-in), or the gap has to be stated out loud when it is skipped.
- **kv rollout order per stage** (`docs/kvstore.md` _Deploy order_): `bootstrap-ssm.sh <stage> state` (mints `kv-kek` only when absent) → `deploy.sh console <stage>` (applies `m0014_kvstore`) → the owner's `GRANT` in the ops repo (needs the tables) → `deploy.sh state <stage>` (bakes the KEK into the env) → `deploy-web.sh <stage>` → the kv smoke. Until the grant lands, every `/kv/*` route on that stage answers `503 unavailable` while the console API works. Rollback: a console bundle older than S4 answers 503 (not 409) on project/team delete once collections exist, because the delete guard's count includes a table it does not know; the state bundle older than S3 simply has no `/kv/*` routes; an S6 SPA over a pre-S4 console API is **not** graceful (the header prints `undefined kv collection(s)` and the tab shows a 404), which is one more reason the order is console, then web.

- **Live asset bundles (`todo/46` P2, 2026-09-28) are a console-only rollout**: `s3-intelligent-tiering.sh <stage> --apply` once (the abort rule; `deploy.sh console` checks it) → `deploy.sh console <stage>` (applies `m0022_asset_live`, a pure expand: every new column is nullable or `NOT NULL DEFAULT`, so the old bundle keeps inserting between the migration and the deploy) → `deploy-web.sh <stage>` → `node scripts/smoke/assets-live.mjs` on dev (needs `--param debugHooks=1`; it also asserts the S3 probe). No other stack reads an asset table, so auth/topic/match/state need no redeploy. **Rollback past P2 has four preconditions**: (a) delete the live bundles first — the older bundle cannot upload to one (its presign requires a version) but does not refuse a lobby `mapUrl` into one, pins a show entry to the empty version (`assets/{id}//`), counts every team's lobbies against a delete and deletes one object per call (a big live bundle outruns 25 s); (b) no live upload presigned in the last hour, or the older commit copies it to `assets/{id}//{path}`, which nothing sweeps; (c) settle the uploads that name a claim (`file_id` on a non-completed row: run the sweep, or check them by hand), because the older sweep drops them and orphans the claim; (d) roll the SPA back with the console. The CLI is compatible both ways as far as `asset create` goes (it sends `mode` only for a live bundle, which the older `.strict()` body would refuse), and from `cli/v0.11.0` `yyt asset rm` deletes files of a live bundle and no longer aliases `asset delete` (v0.10's `rm` took exactly one argument, v0.11's takes two or more, so no script silently changes behaviour).

## Artifact/asset CDN (`d.yyt.life` / `dev-d.yyt.life`)

- These two distributions are **manual infra, outside IaC**, and they are not twins (survey with distribution/OAC ids in gitignored `local/ops-notes.md`). Both read the bucket's S3 REST endpoint through origin access control (dev from the start, prod since 2026-09-27, _Private origins_ below); prod keeps the legacy `ForwardedValues` behaviour rather than a cache policy. Attaching the managed `SecurityHeaders` policy works on either shape — a response-headers policy is independent of `CachePolicyId` vs `ForwardedValues`, so the legacy behaviour did not have to be modernised first.
- The prod distribution shipped **without any response-headers policy**, which the 2026-08-26 release surfaced: prod objects came back `200` with the right `Content-Type` and `immutable` but **no `X-Content-Type-Options: nosniff`** — the one header `scripts/smoke/assets.mjs` asserts, and smoke only ever ran against dev, so nothing caught it. Fixed the same day by attaching `Managed-SecurityHeadersPolicy` to the default behaviour; verified on a fresh miss and a cached hit. **Correction 2026-08-30:** a response-headers policy is _not_ reliably applied to every already-cached variant — after swapping the artifact CDN to `Managed-CORS-and-SecurityHeadersPolicy`, `curl` (and misses) saw `Access-Control-Allow-Origin` while Chrome's variant (`Accept-Encoding: … zstd` + `priority`, cached 5 h earlier) came back without it, and the browser client failed CORS; only a `/*` invalidation fixed it. **After attaching or changing a response-headers policy, invalidate `/*`** on that distribution and re-test from a real browser, not curl. **A dev-only smoke suite proves nothing about a stage whose CDN is hand-built** — when the two stages' edges are configured by hand, diff them explicitly rather than inferring prod from a dev pass.
- Until 2026-09-27 prod's website endpoint was public, so `assets/` objects, and every catalog artifact, could be read directly, bypassing CloudFront and any policy attached to it. The bucket is private now (_Private origins_ below).
- Both buckets carry the CORS rule the SPA's presigned PUT needs (`GET/PUT/POST`, `*`, expose `ETag`); prod's was applied by hand on 2026-08-24 and re-verified 2026-08-25.
- `sample-morpg` (`yingyeothon/examples`) `serverless.yml` carries `provider.httpApi.cors` (wildcard origin, `authorization` + `content-type`, GET/POST/DELETE/OPTIONS) since 2026-08-30 for the browser client — a Bearer-only API without cookies, so the wildcard is the right shape; deployed to dev the same day (preflight 204 verified). A stack copied from the sample keeps it.
- **S3 CORS headers do not survive CloudFront caching** (found 2026-08-30 by the first browser game client): S3 adds `Access-Control-Allow-Origin` only when the request carries `Origin`, `CachingOptimized` keys the cache on the URL plus `Accept-Encoding` only, so the `br` variant of the map bundle was cached from the Lambda's fetch (no `Origin`) and every browser fetch failed with "no Access-Control-Allow-Origin" while `curl` (identity/gzip variants, cached from requests with `Origin`) showed `*`. The fix is at the edge, not in the cache key: swap the default behaviour's response-headers policy from `Managed-SecurityHeadersPolicy` to `Managed-CORS-and-SecurityHeadersPolicy` (`e61eb60c-9c35-4d20-a928-2b84e02af89c`, same security headers plus `Access-Control-Allow-Origin: *` with origin override, applied at delivery so cached objects pick it up) — `aws cloudfront get-distribution-config --id "$(aws ssm get-parameter --name /yyt-service/<stage>/cdn-distribution-id --query Parameter.Value --output text)"`, edit `DefaultCacheBehavior.ResponseHeadersPolicyId`, `update-distribution --if-match <ETag>`. The assistant's auto mode cannot run `update-distribution` (classifier), so this is a user step per stage; `scripts/smoke/assets.mjs` now fetches the committed object first without `Origin` and then with it and asserts the header on the cached variant, so a stage that regresses fails the smoke rather than the first player.
- **Correction 2026-09-05 — the managed CORS policy is not a delivery-time fix.** `Managed-CORS-and-SecurityHeadersPolicy` has `CorsConfig.OriginOverride: false`, so CloudFront defers to whatever CORS headers the _cached_ origin response carries. The game Lambda's server-side fetch of `MAP_URL` (no `Origin`) fills the `br` variant with an S3 response that has no `Access-Control-Allow-Origin`, the object is `immutable`, and every browser fetch of that exact object fails again — observed on dev on 2026-09-04 with the policy still attached; the security headers of the same policy _were_ on the failing response. The 2026-08-30 `/*` invalidation only worked until the next cold start re-poisoned the entry. Fix = a **custom** response-headers policy with `OriginOverride: true` (`yyt-artifact-cdn-headers`: CORS `*` + `nosniff`/HSTS/`X-Frame-Options`/referrer, same as the managed one otherwise) attached to the default behaviour of both hand-built distributions, then `/*` invalidated: `scripts/cdn-cors-policy.sh <stage>` does all of it (idempotent; `--dry-run` shows the plan). Creating the policy and `update-distribution` are classifier-blocked in auto mode; **applied to both stages on 2026-09-05 with the owner's approval** and proven the hard way: an Origin-less node fetch filled a fresh entry (`Miss`, no ACAO from S3) and headless Chrome then read `access-control-allow-origin: *` on the cached hit, on dev (`br`) and prod (identity). The policy id is in `local/ops-notes.md`.
- **Only a real browser can verify the artifact CDN's CORS**: at one POP, node `fetch` and `curl` were served an edge entry carrying the header while Chrome, at the same second, got one without it (HTTP/3 ruled out with `--disable-quic`). `scripts/smoke/cdn-cors-browser.mjs <url…>` drives headless Chrome over CDP and reads `Network.responseReceivedExtraInfo` (fires even for a CORS-blocked fetch); pass an object the game Lambda has fetched server-side (the current `MAP_URL`), not a fresh one. `scripts/smoke/assets.mjs`'s node-side CORS assertion stays as a regression guard but a green run does not prove a stage healthy.

## Console domain = CloudFront

- `console{-dev}.yyt.life` is **not** an API Gateway custom domain: the console stack owns a CloudFront distribution (`/ui`, `/ui/*` → S3 `yyt-console-web-{stage}` with OAC + a viewer-request Function that rewrites extension-less paths to `/ui/index.html`; default `*` → the HTTP API's execute-api endpoint with `CachingDisabled` + `AllViewerExceptHostHeader`) plus Route53 A/AAAA alias records. The us-east-1 cert ARN comes from SSM `cloudfront-cert-arn`.
- Order for a stage: `scripts/deploy.sh console <stage>` (CloudFront creation/updates take 5–15 minutes) → `scripts/deploy-web.sh <stage>` (builds the SPA, syncs `dist/assets` as `immutable`, `index.html` as `no-cache`, invalidates `/ui*`). The SPA is not part of `sls deploy`; redeploy it whenever `apps/console-web` changes.
- Migrating a stage that still has the old API Gateway custom domain: delete the API GW domain name and its Route53 A (and any AAAA) record **before** deploying, otherwise the `WebDnsA` RecordSet fails with "already exists". `serverless delete_domain` needs the plugin, which console no longer installs — run it from a checkout of the previous commit, or use `aws apigatewayv2 delete-domain-name` + `aws route53 change-resource-record-sets`. The host is unreachable until the CloudFront create finishes (5–15 minutes); for prod, deploy once without the two RecordSets, then swap DNS, to shrink the gap to the DNS TTL.
- `WebBucket` is rebuildable and has no Retain policy, but CloudFormation refuses to delete a non-empty bucket: empty `yyt-console-web-<stage>` before `sls remove`.
- The execute-api default endpoint stays enabled (it is the CloudFront origin). It carries no `__Host-` cookie for that host, so direct hits are unauthenticated API calls, same as any other origin.
- Never map S3 `403` to `index.html` (a permission denial turns into a 200 HTML page and hides real misconfiguration); `scripts/deploy-web.sh` deliberately does not `s3 sync --delete` — deleting old lazy chunks before the invalidation propagates breaks tabs that are already open.

## CDN emergency (2026-09-27)

- **Guard** (`docs/decisions.md` _CDN cost guard and emergency stops_): console `cdnGuard` disables `artifact` (d), `path-host` (g) and `site-host` (`*.g`) past 10 GiB or 2 M requests in a 5-minute bucket, or 100 GiB or 20 M requests in the UTC day (warn at a quarter); `console` is alert-only (`--param cdnGuardConsole=off` drops it). It never re-enables anything. Its IAM is the stack's `CdnGuardRole`; ids come from SSM `cdn-distribution-id`/`site-distribution-id` and the stack, and it refuses any distribution whose aliases lack the label's host.
- **Runbook:** (1) the alarm e-mail names the label, the host and the measure. (2) **Bytes**: find the hot object in the CloudFront console → Popular objects (no access logs needed, UTC dates; sort by total bytes — the top 50 are by requests) and contain it with `scripts/cdn-quarantine.sh <stage> <site|artifact> <key|prefix/> on --apply` (one file, site or bundle, on every host and on direct S3 reads; bucket-policy `Deny` + one invalidation). **Requests**: a flood has no single object and 403s are still billed — keep the distribution off until it stops. (3) To stop a whole distribution by hand: `scripts/cdn-switch.sh <stage> <label> off --apply` (the console one too; the console API goes down with it). (4) `scripts/cdn-switch.sh <stage> <label> on --apply` — the guard e-mails "re-armed" on its next run and counts from then; a flood still running trips it again. (5) `quarantine … off` once the file is gone or fixed; `quarantine <stage> <site|artifact> list` shows what is still held, in the form `off` takes (a prefix ends in `/`), and `off` on a key under a quarantined prefix says the prefix still covers it. (6) Record what happened in `local/ops-notes.md`. Every script is a dry run without `--apply`. With `path-host` off, sites still load at `{slug}.g.yyt.life` (and the other way round) — say so to the teams.
- **A deploy does not re-enable a tripped `site-host`** unless it changes that resource (CloudFormation leaves drift alone); re-enabling is always `cdn-switch.sh … on`.
- **Contest day / false positive:** 10 GiB in five minutes is about 200 people opening a 50 MB build at once, and a trip takes every site (or every asset) of the stage down. Before a big public event raise the lines (`scripts/deploy.sh console prod --param cdnGuardScale=4`, or one host's with `--param cdnGuardScaleArtifact=4` / `PathHost` / `SiteHost` / `Console`; the factors multiply, and every notice states the one it was judged at) or announce only (`--param cdnGuardMode=alert`). To pause the guard immediately without a deploy: `aws events disable-rule --region ap-northeast-2 --name "$(aws events list-rules --region ap-northeast-2 --name-prefix yyt-console-<stage>-CdnGuard --query 'Rules[0].Name' --output text)"`, then `enable-rule` the same way afterwards — the digest's `cdn:guard:stale` warning is the reminder. `console` stays up regardless.
- **Observed on dev (2026-09-27):** a disable and a re-enable each took about 3.5 minutes to reach `Deployed`; a disabled distribution's host stops resolving (curl exit 6, a DNS failure — not an HTTP error page); the guard's own disable, the script's switch-off (seen by the guard as "found disabled") and both re-arms behaved as documented; a quarantine answered 403 on the path host, the per-site host and the S3 website endpoint within about 10 s, and `off` restored the policy exactly. The owner-approved `update-distribution` and `put-bucket-policy` ran from the session through the scripts. After the dead principals were removed, a single-key artifact quarantine through dev-d (REST origin with OAC) answered 403 while the sibling key stayed 200. A repeated `on` rewrote the policy each time, because S3 hands a one-element `Resource` list back as a plain string. Compare policy JSON after normalizing such fields, never byte-for-byte against what was written. Since 2026-09-27 a repeated `on` leaves the policy alone and only invalidates again, which is the retry for an `on` whose invalidation failed after the policy was written.
- **Private origins** (`scripts/origin-oac.sh <stage> <status|apply|revert|check-deploy> [--apply]`, decisions §11): CloudFront reads the site and artifact buckets through origin access control, and no anonymous reader can. The account's own IAM roles (the console, the legacy uploader) still use the S3 API. The order on a stage:
  1. `apply --apply`: each bucket policy gets `YytCloudFrontRead` naming its distributions. This is additive.
  2. `scripts/migrate.sh <stage> status` (the deploy applies pending migrations), then `scripts/deploy.sh console <stage>`: it creates `CdnOriginAccessControl` and the two edge functions and switches the per-site host. `deploy.sh` refuses to run before step 1.
  3. `apply --apply` again:
     - The hand-made path host and artifact CDN move to the REST endpoint with the control and their function. The script waits for `Deployed`.
     - Anonymous statements are removed and Block Public Access goes on. `BlockPublicAcls` stays off on the prod artifact bucket: the 2019 `api.yyt.life/d` uploader still sends `public-read`.
     - The retired `origin-secret` is deleted.
     - Probes run.
  - Nothing goes down on the way: the old statement keeps the old origins working while the new ones propagate.
- **If CloudFront answers 403 after the switch:** `scripts/origin-oac.sh <stage> revert --apply` puts the hand-made distributions whose bucket has website hosting back on the public website endpoint and adds an anonymous read statement. It detaches the console stack's function from every hand-made distribution. The per-site host keeps its control.
  - While reverted, the bucket can be read directly from S3, past the CDN guard and `cdn-switch`.
  - `apply --apply` goes forward again.
  - A cached 403 lasts CloudFront's 10 s default.
- **Rolling console back past 2026-09-27:** run `revert --apply` first. An older template reads the site bucket without access control, and CloudFormation cannot delete the access control or a function while a hand-made distribution uses it (the dev artifact CDN keeps its own control). To roll forward, deploy, then run `apply --apply`. `apply` and `revert` refuse while the console stack is `*_IN_PROGRESS`.
- **What changed on the path host:**
  - `/{slug}` still redirects to `/{slug}/` (the function answers 302 and keeps the query, re-serialized: keys grouped, `a=` becomes `a`; the website endpoint's redirect dropped it), and `/{slug}/` still serves `index.html`. Only a segment in the prefix grammar is redirected.
  - The query string never reaches S3 (both functions drop it).
  - A nested directory without its trailing slash, a missing object (403 now, 404 before) and `x-amz-website-redirect-location` now behave as on the per-site host.
  - A literal `+` in a path: the REST endpoint reads it as a space, so both functions send it as `%2B`. Without that, dev-d (REST since it was built) answered 403 for `…-1.0.24+25-release.apk`, while console links worked because they use `encodeURIComponent`.
- **A bucket policy naming a deleted IAM role cannot be rewritten** (`MalformedPolicy: Invalid principal`): AWS shows the dead principal as its unique id (`AROA…`). The dev artifact bucket had three such statements from the retired catalog dev stack (found 2026-09-27); `cdn-quarantine.sh` and `origin-oac.sh` refuse up front and name them. Cleared on dev 2026-09-27 (the session ran it once the owner had approved it explicitly; the first attempt, before that, was refused by the auto-mode classifier). To clear one, in one shell (a locked bucket's policy carries the origin secret, hence the umask; the filter drops whole statements, so a statement that also names a live principal needs a hand edit instead — read the diff first): `umask 077; B=$(aws ssm get-parameter --region ap-northeast-2 --name /yyt-service/<stage>/<artifact|site>-bucket --query Parameter.Value --output text); P=local/deploy/<stage>-<artifact|site>-dead-principals-$(date -u +%Y%m%dT%H%M%SZ); aws s3api get-bucket-policy --bucket "$B" --query Policy --output text > "$P.backup.json" && jq '.Statement |= map(select([.Principal | .. | strings] | any(test("^A(ROA|IDA)[0-9A-Z]{16,}$")) | not))' "$P.backup.json" > "$P.clean.json" && diff <(jq -S . "$P.backup.json") <(jq -S . "$P.clean.json")`, then `aws s3api put-bucket-policy --bucket "$B" --policy "file://$P.clean.json"`.
- **Observed timings (dev, 2026-09-27):** the console distribution took about 10 minutes to reach `Deployed` when switched off (about 3 when switched on); the others about 3.5 both ways. CloudWatch showed a traffic burst about 1.5 minutes after it ended.
- **Account alerts:** `scripts/bootstrap-cost-alerts.sh <email> [--apply]` (us-east-1, idempotent, e-mail never stored): Cost Anomaly Detection daily at $3, Budget `yyt-cloudfront` $5, Budget `yyt-account` $60 replacing `yyt-30usd`, and deletes the hand-made `BillingAlarm` (an 11th alarm). Owner-run.

- Every stack's CloudWatch alarms take `AlarmActions` from the optional stage-wide SSM `alarm-topic-arn` (CloudFormation condition `HasAlarmTopic`); without it the alarms exist but notify nobody. `scripts/bootstrap-alarms.sh <stage> <email>` creates `yyt-service-<stage>-alarms`, subscribes the address (confirm the email) and stores the ARN; then redeploy every stack of that stage. Both stages have a confirmed-or-pending email subscription (prod subscribed 2026-08-26). The alarm inventory is capped at the free tier — `rules/serverless-aws.md`.
- **Prod has no debug hooks, so `scripts/smoke/*` and `yyt smoke` cannot run there** (`todo/10`); the prod acceptance after a data migration is a CLI round trip with the prod profile (`team ls`, `catalog app get <name>`, `project version ls`, `artifact upload` + `list`). `apply-team-project-map.mjs` treats an unknown member login as a hard problem, not a skip — prod only knows the members who have logged in there, so a map copied from dev must drop the rest (they join with `yyt team join`).
- **Rollback precondition after `todo/46` P3 (multipart):** before reverting console to a build older than P3, abort every open multipart upload (`DELETE /assets/uploads/{id}` per pending row with `s3_upload_id`, or `aws s3api abort-multipart-upload` from `list-multipart-uploads`) and settle the `completing` rows: the older sweep drops expired rows without aborting (billed parts until the lifecycle rule's day) and the older code answers a `completing` upload `409 upload is completing` for ever. The migration `m0023` stays (expand only; old code ignores the columns). A CLI older than `cli/v0.12.0` cannot upload a file over 64 MiB after P3 — the grant has no URL — which pre-launch is accepted; the SPA refuses such a file with a message naming `yyt asset sync`.
- **Catalog listings (`todo/47` P1, 2026-09-28) roll out with `deploy.sh console <stage>` alone** (`m0025_catalog_listings`, expand-only, four new tables). Rollback needs no precondition: an older console bundle ignores the tables, its app delete is a Prisma `deleteMany` so the database cascades still clear a deleted app's listing, viewers and takedown, and no path deletes a `members` row, so the three RESTRICT keys to `members` cannot fail it; the tables stay. A listing that exists while the older bundle runs is simply unreadable until the newer one returns.
- **Encrypted asset bundles (`todo/46` P4, 2026-09-28) roll out console-only, with the KEK as a separate owner step**: `deploy.sh console <stage>` (applies `m0024_asset_encryption`, expand-only) → `node scripts/smoke/assets-encrypted.mjs` shows `503 asset_encryption_not_configured` (the stage has no KEK yet; that is the check) → owner: `ASSET_KEK_INIT=1 scripts/bootstrap-ssm.sh <stage>` (stage only, no service args; creates `console/asset-kek` when absent and never replaces it) → `FORCE=1 scripts/get-env.sh <stage> console` and the ops-repo backup → `deploy.sh console <stage>` **again** — the value is baked at deploy time and the `${ssm:…, ""}` default means the first deploy was silently KEK-less → `deploy-web.sh <stage>` → the smoke again, now the full run, then the CLI half (`rules/manual-verification.md`). The handshake: the `kekId` the bootstrap logs must equal the `asset keyring` cold-start line of `yyt-console-<stage>-api`; every `POST …/key` answering 503 `asset_key_unreadable` while the bundle exists means they differ (`ASSET_KEK is malformed` is logged at `error`, an empty one at `warn`). No other stack needs the KEK: the sweep's own check is the object's first byte. **Rollback precondition after P4**: delete every encrypted bundle before reverting console to a pre-P4 build — the older presign accepts plaintext into one (no `format`), the older commit checks no first byte, the older SPA/CLI show no flag — and `m0024` stays (expand-only; old code never selects the table). A CLI older than `cli/v0.12.0` gets 400 on presign into an encrypted bundle, but its `asset download` writes the ciphertext to disk as if it were the file (it knows no `encrypted` flag). `console/asset-kek` belongs to the "SSM environment values" list above beside `kv-kek`: never rotated in place, no rotate flag exists.

## Artifact CDN and browser clients

- The hand-made artifact distributions (`d.yyt.life`, `dev-d.yyt.life`) answer `access-control-allow-origin: *` with `access-control-expose-headers: ETag,Content-Length` only (probe 2026-09-28: `curl -sI -H 'Origin: https://example.com' -H 'Range: bytes=0-0' https://dev-d.yyt.life/assets/x/y`). They also allow only `GET`/`HEAD`, so a CORS preflight (`OPTIONS`) is 403 and a browser cannot send any non-safelisted request header (`If-Range`, `If-Match`, `Cache-Control`) to them. A browser client therefore sends a `HEAD` for the total length and the `ETag`, then ranged `GET`s with `Range` alone (`docs/asset-encryption.md` _Ranged reads and resume_). Allowing `OPTIONS` and widening the exposed list live in the distribution's behaviour and response headers policy, outside IaC: owner changes, recorded in `local/owner-checklist.md`.
- **In an autonomous session the prod dump is refused by the auto-mode classifier ("Production Reads") even when the owner approved prod in the same conversation** (2026-09-29; the same refusal as a fresh session on 2026-09-28), while `ASSET_KEK_INIT=1 bootstrap-ssm.sh prod` and prod catalog uploads through the CLI ran. The procedure forbids a prod migration without a dump, so do not split the sequence: hand the whole rollout over as one script under `local/tools/` (preflight → dump → `deploy.sh console prod` → `deploy-web.sh prod` → acceptance) and finish everything that does not depend on it.
- **`deploy.sh <service> prod` itself is refused the same way ("Production Deploy", 2026-10-01, `todo/55`)**, handover pre-approval included; the owner ran it from the prompt (`! AWS_PROFILE=yyt scripts/deploy.sh auth prod`) and the session took over from there — a read-only acceptance (`curl` with an `Origin` header against an unknown channel: 404 and a 204 preflight both carry the CORS headers) needs no credential and no debug key, so it is the whole check for a header-only change. Plan a prod step as "owner runs one command, session verifies", and do the parts that do not depend on it first.

## Push rollout order (`todo/56` P0, 2026-10-06)

- Per stage: **owner creates the Firebase project and puts its key in SSM → `deploy.sh console` (applies `m0028_push`) → `deploy.sh auth`, `topic`, `match` → owner grants the state account `push_tokens` and `push_send_stats` → `deploy.sh state` → `deploy-web.sh`.** Console first because it owns the migration and state reads the table; the grants after the migration because a `GRANT` on an absent table is `ERROR 1146`; the SPA last, after the API it calls.
  - **Auth, topic and match are redeployed before the first push channel exists.** Their bundles carry a generated client built before `push` joined the `channels.kind` enum; they read a channel by id and check the kind afterwards, so a request naming a push channel's id where theirs belongs makes the client throw (a 5xx where a 404 belongs). No code of theirs changed — the redeploy only refreshes the generated client. Until they are redeployed, do not create a push channel on that stage.
  - The SSM step may come at any point: the pool is read at run time, so a stage without it deploys and answers 503 `push_not_configured`, and a key added later is picked up within 10 minutes with no deploy.
  - State deployed before the grant is safe: `/push/*` answers `503 database error`, the other routes work. `scripts/smoke/push.mjs` names that case "grant missing".
  - The state deploy adds the `pushSend` function (`POST /push/{channelId}/send`, 28 s, 2 reserved containers — two more MariaDB connections, 57 of 60), a second metric filter on its log group feeding the existing alarm's metric, and two IAM statements; `api` keeps its 10 s.
  - State deployed without the `push_send_stats` grant still sends; each call logs `push send stats failed` and the digest shows no send failures.
- **Rollback precondition.** Before rolling console back past `m0028_push`, hard-delete the `push` channel rows and their `push_apps` rows: an older generated client throws on the enum value it does not know, so every read that returns such a row fails as a whole — the team's channel list, and the daily expiry sweep once the row is due (the `lobby`/`q` lesson above). Delete the channels through the API first where possible, so their Firebase apps are removed too; a row deleted by hand leaves its app behind, which the next reconciliation removes (it carries the marker and no claim). Auth, topic and match bundles older than the migration throw the same way when a caller names a push channel's id (the redeploy step above); the rows being gone is what makes any old bundle safe. Backing the migration itself out: the rows, then `push_tokens` in bounded batches, then four `DROP TABLE`s; the trailing enum value stays.
- A Firebase project id never enters a deploy note in this repo: slot labels here, ids in `local/ops-notes.md` and `local/identifiers.extra.txt`.

## Deferred match rollout order (`todo/56` P1, 2026-10-06)

- Per stage: **`deploy.sh match` → `deploy.sh console` → `deploy-web.sh`.** Match first for two reasons: an older match bundle reads a deferred channel's config as live (no `mode` check) and accepts sockets on it, and console hands out `ticketUrl`/`apiBase` on the ticket host, which exists only once match is deployed.
- The match deploy creates a second custom domain, **`match-api.yyt.life` / `match-api-dev.yyt.life`** (HTTP API; `customDomain.http`, `autoDomain`), beside the WebSocket one, plus the `http` function (3 containers, taken from `ws` and `authorizer`: the stack stays at 18). The dev debug routes move to that host. Console reads the base from its `matchApi` URL setting; empty means a deferred channel's view omits `ticketUrl`.
- The match account needs `SELECT` on `push_tokens` for the push hook (owner grant); without it pushes are skipped and matches are unaffected.
- **Rollback precondition.** Before rolling match back past this bundle, disable (or delete) every deferred channel: the older bundle treats them as live. Their Redis state (`dq:`, `du:`, `dp:`, `dps:`, `dr:`, `dactive`, `dcd:`, `dpn:`, `dkick:`) expires on its own. Rolling console back alone needs nothing: the rows keep their `mode`, and the older console's PATCH would drop it — do not edit a deferred channel through an older console.
