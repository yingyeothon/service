# Data

> Storage is self-hosted MariaDB + Redis (host and account details live only in the local private ops repo `yyt-stateful` — never in this public repo). The previous sqlite-on-S3 + Upstash design was removed on 2026-08-22 (`todo/09-storage-migration.md`).

## Accounts and environments

- One MySQL database per stage (name in `yyt-stateful`), owned by console: it owns the schema and every migration and writes every table but one. auth/topic/match use `SELECT`-only accounts.
- **`state` is the single non-console writer** (2026-08-26). Its grant is `SELECT` on `channels` plus `SELECT, INSERT, UPDATE, DELETE` on `state_docs`, and nothing else — a table-scoped grant narrows the ownership rule rather than dropping it, and it is what keeps a bug in that stack away from `members` and `api_tokens`. Say it precisely, though: MySQL grants are per **table**, not per column or row, so that `SELECT` covers `secret_json` for **every** channel — every auth channel's signing secret and every configured OAuth `clientSecret`, not only the ones this service needs. The same is already true of auth/topic/match. The stack's bundle also carries the whole `createConsoleDb` repository, so nothing in the code prevents a wider read; **the grant is the only control**, which is why checking it is a step and not a formality. Verified on the box with `SHOW GRANTS` before the first deploy; do the same for prod. The account is created by hand in `yyt-stateful`, so a stage without one simply has no state stack: `bootstrap-ssm.sh`/`get-env.sh` skip `state` instead of failing.
- One MySQL account and one Redis ACL user per service×stage. Redis ACL users are restricted to keys/channels `{service}:{stage}:*` (`resetkeys ~… resetchannels &…`, `+@all -@dangerous`), so a wrong prefix fails with NOPERM instead of leaking — keep the `{service}:{stage}:` prefix rule anyway for readability.
- Credentials live in `local/env/{service}.{stage}.env` (gitignored; layout in `local/env.example`, see `local/README.md`) and are pushed to SSM for Lambda. Never commit or log them. Rotate via `yyt-stateful` scripts (`ALTER USER` / `ACL SETUSER … >pw` + `ACL SAVE`) and update the `.env` in the same step.
- tslib's `naive-redis` authenticates with `AUTH <username> <password>` only when `username` is set (`REDIS_USER` via `gamebaseOptionsFromEnv`); without it the ACL user never logs in and every command fails `NOAUTH`. Its test suite uses `resetkeys ~pattern` so a wrong prefix surfaces as `NOPERM`, same as ours.
- The store is **Valkey 8** (Redis 7.2 lineage) since 2026-08-28 (`yyt-stateful/docs/redis.md`; it was Redis 6.2 before). Still true there: a new ACL user starts with `allchannels` (`acl-pubsub-default allchannels` is set on purpose); adding `&pattern` errors unless `resetchannels` precedes it — and `reset` does **not** stand in for it, so a scoped user needs both.
- **ACL selectors are available** (`(%R~pattern +get +mget)` = read-only extra scope; verified on the host). The console issuer does not emit one yet — see `todo/16` — so a participant still cannot read `gateway:*` and the gateway `GET /parties/{partyId}` route stays the way a game reads a roster.
- **Participant credentials are minted by the console** (`createRedisAclAdmin`, `docs/decisions.md` _Participant credentials_), through a second Redis account per stage (name in `yyt-stateful`, never in this repo) — `-@all` plus `+acl|setuser +acl|deluser +acl|getuser +acl|save`, with `resetkeys resetchannels` so it holds no key or channel pattern of its own. Valkey 8 (and Redis 6.2 before it) accept those first-arg rules; a data command from that account fails `NOPERM`, which is the property the split is for. The console's own per-service user is unchanged and still cannot run `ACL` at all.
  - The issued username is **derived** (`game_{stage}_{channelId}`) like the prefixes, and the admin **refuses every name outside `game_`**. `ACL SETUSER` is an upsert: one miscomputed id would rewrite a platform service account's password and scope, locking a whole service out of Redis with no error anywhere. The guard runs before anything reaches the socket.
  - Every mutation is followed by `ACL SAVE` — the host authenticates from an `aclfile`, so without it the account is live now and gone after the next restart, a credential that fails on contest day rather than one that never worked. **`ACL SAVE` rewrites the whole file**, so this repo is now a second writer of it: nothing may hand-edit that file and expect the edit to survive, and a hand-run `ACL SETUSER` without `SAVE` gets persisted by the next issue (`yyt-stateful` `docs/redis.md`).
  - **Revoke saves unconditionally, even when `DELUSER` removed nothing.** Saving only on a change looks like an optimisation and is a one-way trap: if an earlier revoke deleted the user from memory and then failed to save, the file still holds it, the next restart brings the account back — and every retry sees `removed === 0` and skips the very save that would repair it. The return value therefore means "this call removed something", not "no such account existed".
  - **A failed `ACL SAVE` on issue does not fail the request.** `reset` leads the rule string, so by the time `SAVE` runs the previous password is already gone; throwing would destroy a working credential _and_ discard its replacement, leaving the owner with nothing and a 503 that reads as "nothing happened". It retries the save once, then returns the password with `persisted: false`, and the console, CLI and SPA all say the account dies at the next restart.
  - **Delete-time revocation is best-effort, so a daily reconciliation is what makes it safe.** One transient error there and the row is hard-deleted with the account still live — nothing left in the database names it, and the issuer holds no `acl|list`-style rights to go looking. `runRedisAclReconcile` closes that: one `ACL USERS`, keep only `game_{stage}_` names, and revoke every one whose channel `findChannelRow` no longer returns. An orphan is not harmless — it is `+@all -@dangerous` inside its own prefix on a 256 MB `allkeys-lru` instance, so an ex-participant can write until eviction starts taking other services' state.
  - Issuing is **rate-limited per member** (10s). Every issue is an `ACL SAVE`, i.e. a full file rewrite on Redis' single main thread, on the box every service and both stages share; without a limit a channel owner — the lowest privilege that can reach the route — is a denial-of-service primitive against the whole platform.
  - `reset` leads the `SETUSER` rule string so a re-issue _replaces_ the password and scope; `ACL SETUSER` is otherwise additive and would leave the previous password valid.
  - Revocation follows **deletion**, not expiry: the daily sweep revokes every hard-deleted channel id (a no-op for non-`q` kinds, cheaper than reading each row back), and the explicit delete route does the same. An _expired_ channel keeps its credential because extending revives it.
  - Errors from this client never forward a message: the `ACL SETUSER` argument list contains the password it just generated, so only the first token of a driver error survives into the cause (`redis ERR`).
- **A key _name_ is not protected by the ACL's key patterns.** Redis does not filter `SCAN` by them, and `SCAN` is not in `@dangerous` (only `KEYS` is), so until 2026-08-26 a participant credential could list every key name on the instance — both stages, every service — while still being refused every read. `RANDOMKEY`, `DBSIZE`, `PUBSUB CHANNELS` and `MEMORY STATS` (no key argument to filter on) leaked the same way. The grant now removes all five, verified against a freshly issued credential. Two consequences to keep:
  - **Never put a secret in a key name.** Console sessions were already `sess:{sha256(id)}`, which is what saved them; the OAuth state keys were not, and are now `oauth:{sha256(state)}` / `state:{sha256(state)}` in console and auth.
  - When adding a command class to any scoped account, ask what it reveals _without_ touching a key. `-@dangerous` is not a synonym for "cannot enumerate".
- **There is no per-account or per-prefix memory quota in Redis**, and there is no per-DB one either; `maxmemory` is instance-wide and `maxmemory-clients` is 7.0+ and about client buffers, not data. With `allkeys-lru` a runaway participant therefore does not hit their own wall — eviction takes the least recently used key, usually somebody else's. Changing the policy does not help: everything platform-side carries a TTL, so `volatile-lru` evicts the same victims, and `noeviction` turns silent loss into loud write failures for whoever writes next, still not the abuser. The defences are (a) seeing it, and (b) revoking. `runRedisUsageReport` runs daily with the expire cron and returns raw numbers only — instance `used_memory` against `maxmemory`, `evicted_keys`, key counts per `game:{stage}:{channelId}:` prefix and the top five; every threshold and every log/notification lives in `runUsageDigest` (one place, so the numbers cannot drift). It counts rather than measures, deliberately — `MEMORY USAGE` needs access to the key it measures and the issuer account holds no key patterns, which is the property worth more than byte precision. `yyt-stateful`'s `redis-usage.sh` reports exact bytes with the admin account when a count looks wrong. Since 2026-08-28 `serverMemory()` also returns `evicted_keys` (`INFO memory stats` — one call, two sections), and `runUsageDigest` (`services/console/src/usage-digest.ts`) compares it with yesterday's value kept in console Redis: the counter resets on a server restart, so a value that went backwards is 0 growth, not an eviction. Any growth means somebody's data was dropped and goes to the alarm topic. Real isolation would need a second Redis instance for participants with its own small `maxmemory` (the box has ~1.4 GB available, so it is affordable); that is deliberately not built yet.
- The usage report groups by the segment after `game:{stage}:`, so the sample game stack shows up as a channel named `queue`: it writes `game:{stage}:queue:*` directly rather than under a channel id, using `svc_game_{stage}`, whose grant is the whole `~game:{stage}:*` namespace. That account predates per-channel credentials and can reach every participant's keys — acceptable while it is our own sample stack, not acceptable if a participant is ever given it.
- Measured on the host (2026-08-26), an issued participant credential: reads/writes inside `game:{stage}:{channelId}:*` and publishes inside `game:out:{stage}:{channelId}:*`; `NOPERM` for another channel's keys, another service's keys, **the same channel under the other stage**, another channel's pub/sub, and for `FLUSHALL`/`KEYS`/`ACL`. `-@dangerous` does **not** remove `RESET` (it is `@fast`/`@connection`), which drops a connection back to the `default` user — that is only a bypass if `default` is `nopass`, and it is not: `ACL GETUSER default` shows a password set (checked 2026-08-26). Keep it that way.
- Redis `maxclients` is 10000 (measured 2026-08-26), which is why the console may hold a second connection per container for the ACL issuer (and the `gatewayProbe` container its own one) while MariaDB's 60 stays the budget that actually binds. The issuer client is `lazyConnect`, but note that _reading_ a `q` channel dials it too, not only issuing.
- Host limits (see `yyt-stateful`): Redis `maxmemory 256mb allkeys-lru` (every runtime key still needs a TTL; eviction is a safety net, not a design), MariaDB `max_connections=60` — keep Lambda pools tiny (1 connection per container) and prefer short-lived connections.

## MySQL (console-owned)

- Schema lives in `@yyt/console-db` `prisma/schema.prisma` + `prisma/migrations/*` (Prisma 7, `prisma-client` generator, `@prisma/adapter-mariadb`). Migrations run at **deploy time only**: `scripts/migrate.sh <stage>` (called by `scripts/deploy.sh console <stage>`) assembles the URL from `local/env/console.<stage>.env` inside `prisma.config.ts` and runs `prisma migrate deploy` — the URL embeds the password, never print or log it. Pre-existing databases are baselined once with `scripts/migrate.sh <stage> baseline` (`prisma migrate resolve --applied 0_init`); baseline now refuses when the live schema drifts from the baseline (learned on prod: v3 tables were missing but the baseline was marked applied, so `migrate deploy` reported "up to date" over an incomplete schema).
- Collation: every table must sit on the database default `utf8mb4_unicode_ci`. The legacy runtime DDL's `default charset=utf8mb4` pinned tables to `utf8mb4_general_ci`, and Prisma-generated DDL pins `utf8mb4_unicode_ci` — a mixed fleet makes every new FK to an old table fail with errno 150. Both stages were converged (drop FKs → `CONVERT TO CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci` → re-add FKs; `foreign_key_checks=0` alone is NOT enough, MariaDB still refuses to alter an FK-referenced column's collation). Both collations are case-insensitive, so `ci`-dependent contracts were unaffected. The legacy runtime migrator (`migrateConsoleDb`/`GET_LOCK` at console cold start) is retired; the old `schema_migrations` table remains as a modeled no-op relic. Operational discipline: migrations are forward-only and must be expand/contract-safe (the schema goes live before the new code, and old code keeps running against it until every stack is redeployed); deploy console first when a change spans services; the deploy machine needs direct DB reachability (the Lambda migrator did not).
- Prisma repositories: `updateMany/deleteMany` return matched/affected counts (the boolean contracts rely on it), `P2002` → `AppError("conflict")`, every other Prisma/driver error → `AppError("unavailable")` with only `prisma <code>` in the cause (Prisma messages can quote values — never forward them). BigInt columns come back as JS `bigint`; repositories coerce with `Number()`.
- **Prisma's `startsWith`/`endsWith`/`contains` reach MySQL as a bare `LIKE` with no `ESCAPE` clause and no escaping of the value**, so `%` and `_` in caller input are live wildcards (measured 2026-09-01 on the `audit_log` read: `actionPrefix: "%"` returned every row, `"sho_."` matched `show.`). An indexed prefix filter silently becomes the leading-wildcard full scan it exists to avoid. Validate the value's character set at the repository boundary and escape what must stay legal — `_` appears in real action names (`team.admin_lock`), so it is escaped with MySQL's default `\` rather than banned. The list search (`q`, 2026-09-02) goes through `escapeLike`/`likeContains` in `src/list.ts` for the same reason, and its contract pins `%` and `_` as literals on both implementations.
- **List ordering lives in `src/list.ts` and mirrors MySQL, not JavaScript** (2026-09-02, `docs/decisions.md` _List sort and filter_): Prisma's `nulls:` is not rendered by the MySQL query compiler (verified in the wasm: no `NULLS FIRST/LAST`), so both sides use MySQL's native placement — `NULL` first ascending, last descending (`nullable(cmp)`); `ENUM` columns order by declaration (`enumRank(ARRAY)`, and `test/enumOrder.test.ts` pins every array to `schema.prisma`); `_ci` text compares with `cmpCi` (`Intl.Collator("en", { sensitivity: "base" })`, trailing blanks trimmed) and `_bin` text with `cmpBin`. The collator is not UCA 4.0.0, so contract fixtures are ASCII letters and digits with distinct case, and every order breaks ties on the id in the same direction (`orderBy: [{ col: o }, { id: o }]`). Logins and project names are relation `orderBy`s (`members.github_login`, `projects.name`, two hops from `team_members`); the fakes take a `loginOf`/`projectName` dependency so the same sort is testable without the join. Values that only exist after the read (effective event/channel status, link counts, `since`, an artifact's version tag) are ordered inside the repository after the fetch with the same derivation the route uses — `effectiveStatus` and `channelStatus` moved into `console-db` for that — and a derived-status sort needs `now` (both implementations refuse without it). Keep MEDIUMTEXT out of the list projection even when a list gains sorting: `IssueListRow`/`DiscussionListRow` are the rows without the body. Two more traps the reviews caught: a **bounded window sorts inside the window** (`listDeploys` takes the newest N in SQL and orders them in the repository — `ORDER BY status LIMIT 20` would have surfaced the oldest `pending` rows and hidden today's failure), and the LIKE escape is only a literal while `sql_mode` lacks `NO_BACKSLASH_ESCAPES`, so `createPrismaClient`'s `initSql` strips it from the session rather than trusting the host.
- **InnoDB extends every secondary index with the primary key**, so on a table with PK `id` an existing `@@index([at])` already _is_ `(at, id)` and serves an `(at, id)` keyset page (measured: EXPLAIN picks it with `key_len` covering both). Declaring `(at, id)` beside it adds a B-tree written on every insert and is never chosen. Add the trailing PK column only where it is not the PK.
- **A sweep queue is keyed on the selective column, and it needs a purge.** `WHERE replaced_at IS NOT NULL AND deleted_at IS NULL` over `(replaced_at, deleted_at)` was measured as a full scan + filesort — neither column is selective. Key it on the status enum instead (`status = 'replaced' AND deleted_at IS NULL`), give the read a `take`, and add the counterpart that drops rows once their object is gone: without it the table keeps one row per object ever uploaded and the nightly scan grows with it forever.
- **`createMany({ skipDuplicates: true })` compiles to `INSERT IGNORE`, and `INSERT IGNORE` downgrades a foreign-key failure to a no-op as well** (2026-09-01, `ShowsDb.insertLike`; only the testcontainers run saw it — the fake threw `unavailable` for an unknown parent while the real driver returned `count: 0`, so "like an entry that does not exist" answered "already liked"). For an idempotent insert use `create` inside a `try` and treat `isConflict(e)` as "already there"; let everything else throw. Reserve `skipDuplicates` for tables with no foreign key at all.
- A deletion snapshot written into `audit_log.detail_json` excludes **every** markdown body, the parent row's own included (`shows`, 2026-09-01): a body is the one field a size-bounding pass cannot shrink, so leaving it in turns a bound into a hope. Snapshot ids, names, counts and object keys, and say in the type that the body is deliberately absent.
- Times are unix seconds in `bigint`; JSON configs are `mediumtext` parsed in code. MariaDB returns `bigint` as JS numbers up to 2^53 (`supportBigNumbers` + `bigNumberStrings:false`); repositories still coerce with `Number()` so a string never leaks into comparisons.
- `Db` maps driver errors: `ER_DUP_ENTRY` → `AppError("conflict")`, everything else → `AppError("unavailable")` with the driver error as `cause` (never in the message — messages reach clients). A SELECT-only account hitting an INSERT therefore surfaces as 503, not 500.
- Pool (`createPrismaClient`, mariadb adapter): `connectionLimit: 1`, `connectTimeout` 3s, `acquireTimeout` 5s, `idleTimeout` 60 (seconds), keep-alive on, `initSql: "SET SESSION max_statement_time=5"` (runs on every new connection; mariadb has no per-query timeout), built once per Lambda container. Never create a client per request. Interactive `$transaction` pins the one connection — inside the callback use only `tx`.
- Raw SQL (2026-08-27, `summarizeArtifacts`): only through `$queryRaw` tagged templates with `Prisma.sql`/`Prisma.join`/`Prisma.empty` — never `$queryRawUnsafe` or string concatenation — named columns instead of `select *`, wrapped in `run()` so errors translate, and covered by the testcontainers contract (the fake must compute the same answer). Prod is MariaDB 10.5: window functions and `json_extract` are available; a non-object `tags_json` yields NULL with a warning there (MySQL would raise). Character/collation traps the mariadb driver has: `json_unquote(...)` and any `collate utf8mb4_bin` expression come back as a `Buffer`, so `cast(... as char character set utf8mb4)` the value you return and compare bytes with a separate `cast(... as binary)` (a `char` expression collates `_ci` and folds case). Keep `MEDIUMTEXT` columns out of list projections as well — a `findMany` with no `select` on a table carrying one reads every body over the single connection before any route can trim it (measured 2026-09-01: `audit_log` at `limit` 200 is up to 51 MB in a 256 MB Lambda, and a show's delete-path snapshot pulled 200 discarded markdown bodies). Keep them out of window/`group by` derived tables — pick ids there and join back by primary key, or the sort spools the text into on-disk temp tables (measured: 695 ms vs 26 ms for 20k rows).
- Connection budget: a frozen/reaped container never closes its socket, so the server holds it until `wait_timeout`. Every function sets `reservedConcurrency`, and the sum is the number that has to stay under the host's `max_connections=60`. Rebalanced 2026-08-26 to seat the state stack: **auth 10 + console 12 (api 10, expire 1, siteDeploy 1 — added 2026-08-30, the async site-zip worker; `gatewayProbe` holds Redis only, no MariaDB) + match 18 (ws 8, authorizer 6, worker 2, tick 1, debug 1) + topic 9 (ws 4, authorizer 3, http 2) + state 6 = 55**, down from 57.
  - **auth and console were deliberately not cut.** `docs/auth-game-contract.md` pins auth's 10 to a concrete burst — the gateway's verify cache misses for every token at the start of an event, so an 8-player dungeon start issues 8 concurrent verifies — and console's `api` is the SPA every organiser uses. Cut where nothing states a burst, not where the number is round.
  - Do **not** justify a cut with "the design ceiling is 10 concurrent players": `docs/decisions.md` scopes that to the realtime gateway (one Go container), not to auth, console or topic, each of which serves every participant of every channel.
  - The table is **per stage**, `max_connections` is **per host**, and dev and prod share the box. Reservations are ceilings rather than steady state, so the sum has never been the real number — treat it as a bound on the worst case of one stage, and keep the slack.
  - A throttle is not a Lambda `Error`, and a WebSocket API publishes no 5xx metric, so cutting a reservation on a WebSocket path is only safe alongside a **Throttles** alarm — topic had them, match did not until 2026-08-26, and a throttled `$connect` is a 500 the player sees and nobody else does. `yyt-stateful` must still set a short `wait_timeout` (≈120s) — tracked in `todo/07-infra.md`. Dev with debug hooks uses two pools per container. Changing a number here only takes effect on **deploy**, so a stack whose reservation was cut is still holding the old one until it is redeployed.
- `Db.transaction` pins one connection; inside the callback use only `tx` (the outer handle would wait for the same connection and the pool rejects it). A connection whose rollback/commit failed is destroyed, never released back. `migrateConsoleDb` runs inside `transaction` because `GET_LOCK` is per-session; lock wait is 5s (< Lambda timeout).
- **A per-member rate slot does not bound a per-parent cap.** "Count-then-insert may overshoot by a burst, and the write slot bounds the burst" holds while the cap and the slot share a subject (drafts per member, shows per member). For entries per show or comments per entry, a hundred different members each hold their own slot against the same parent, and what actually bounds the overshoot is the function's `reservedConcurrency`. Say which of the two you are relying on.
- A **claim column** on a parent row (`sites.active_deploy_id`, 2026-08-30) serialises writers without a partial unique index: `updateMany where id and (claim is null or claim = holder)` and the affected count is the claim. The Prisma mariadb adapter reports _matched_ rows for `updateMany` (a re-entrant claim by the same holder in the same second is still `true` — pinned by the sites contract on testcontainers, 2026-08-30; the older "MariaDB counts changed rows" note applies to raw `mysql2` without `CLIENT_FOUND_ROWS`, and `updated_at` is bumped on every write anyway so both agree). Pair the claim with a stale heal keyed on `updated_at`, or a request that dies holding it bricks the row.
- `upsertMember` updates only when the `github_id` matched; a colliding _id_ with another `github_id` is a no-op + `AppError("conflict")`, and the call returns the id that owns the GitHub user — use that id for foreign keys (the debug seed learned this the hard way).
- Writers that are not console (dev-only debug seeding in auth) use console's dev account through separate `DEBUG_MYSQL_*` env (`docs/decisions.md` §auth "Debug seeding"); the code path must degrade to "hooks disabled" when those vars are absent.
- Prisma baseline on an existing database: split the baseline per table generation (`0_init` for what every stage has, `1_catalog` for tables only dev had) so `migrate resolve --applied` marks exactly what exists; a single baseline marked "applied" on a stage missing the newer tables silently skips DDL. `scripts/migrate.sh` refuses `deploy` on a DB whose `0_init` is pending and refuses `baseline` when drift is non-zero.
- Do not remove a `reservedConcurrency` setting to "save cost": reserved concurrency is free (provisioned is the billed one) and it is the cap that keeps the MariaDB connection sum inside `max_connections`. Lower the number; keep the knob. Do not cut `auth`'s reservation when re-balancing: it covers a concrete burst (a full party starting a dungeon misses the gateway's verify cache for every token at once, and a throttle there is a refused socket).

## Redis (ioredis, TCP)

- Every key starts with `{service}:{stage}:` — the `REDIS_KEY_PREFIX` env must equal `{service}:{stage}:` and handlers assert it at cold start. The ACL user enforces the same pattern; a mismatch shows up as `NOPERM`.
- ACL users have `-@dangerous`, which removes `INFO`: set `enableReadyCheck: false` in ioredis or every connection logs "Skipping the ready check" and waits. `KEYS`/`FLUSHALL`/`CLIENT` are also unavailable — design without them (no key scans; track membership in sets with TTLs).
- A write and its TTL go in **one command**: `SET … EX` (`SET … EX GET` when the previous value is needed — Valkey 8 / Redis ≥ 7, it stays in `@string`/`@write`, so the `-@dangerous` accounts keep it), never `GETSET`/`RPUSH` + `EXPIRE` as two round trips — a crash between them leaves a key no `SCAN`-less account can find again. Where two commands are unavoidable (`RPUSH` + `EXPIRE` on a queue) wrap them in `MULTI`. Guard tests: `redisx` `TestEveryWriteHelperLeavesATTL` (reflection over the exported methods, so a new write helper must be listed) and `test/serverless-invariants.test.ts` for `reservedConcurrency`.
- Every runtime key has a TTL; tslib after 2.0.1 (to ship as 2.0.2) enforces it on the game side too (`createRedisQueue` `ttlSeconds`, `handleConnect`/`handleDisconnect`/`handleMessages` `queueTtlSeconds`, `repository-redis` `set` refuses a TTL-less write — use `setWithExpire`/`expiresInMillis`). Channel config cache 60s (never for rows with secrets); topic keys = topic TTL (≤20m); match tickets = waitTimeout+120s; OAuth state 10m; console sessions 7d.
- Prefer a Lua `eval` for compare-and-delete and multi-key atomic steps; otherwise serialize with `withLock`.
- Client options: `lazyConnect`, `connectTimeout` 2s, `commandTimeout` 3s, `maxRetriesPerRequest: 1` (unreachable host fails in ≈4s, inside the 10s Lambda timeout), `enableAutoPipelining`, an `error` listener that logs through `Logger` (otherwise ioredis spams `console.error`). Every command error becomes `AppError("unavailable")` with cause `redis <code>`. One client per container; `close()` exists for tests, Lambda just lets the container die.
- Do not store secrets in Redis except short-lived session ids; secrets stay in MySQL.
- Pub/sub is only acceptable for self-healing traffic (snapshot frames). Discrete non-idempotent events go through a list: Redis drops a slow subscriber (`client-output-buffer-limit pubsub`), turning a stall into silent input loss, whereas a list absorbs it and its depth is observable. Reasoning: `docs/realtime-gateway-design.md`.
- A key layout for a new component is settled in a TTL table before code is written (`docs/realtime-gateway-design.md`): with `KEYS`/`SCAN` removed from the ACL users an untracked key can never be found again.

## Documents (`state_docs`, migration `5_state_docs`)

- One versioned JSON blob per `(channel_id, owner_id)`, PK on the pair, `channel_id` a foreign key to `channels`. The channel is the **auth** channel: `owner_id` is a `deriveUserId` result and means nothing outside the channel that derived it.
- **Every write is conditional.** `putDoc` takes the version the caller read (`0` = "no row yet", which inserts) and `updateMany … where version = ?` decides. MariaDB counts _changed_ rows, which would normally make a no-op update look like a CAS failure — here the version always moves, so the count is a faithful verdict even when the body is byte-identical. On a miss the repository re-reads and returns the row that is actually stored, so the route can answer 409 with the current version instead of just "no".
- `owner_id` is `utf8mb4_bin`; `channel_id` keeps the database default `utf8mb4_unicode_ci` because a foreign key requires the referenced column's collation (the errno 150 trap above). The split is deliberate: an owner id is an identity compared byte-exactly by the authorization check, so a case-insensitive index would let two identities share one row — migration `4_assets_binary_paths` restated. The in-memory fake mirrors both halves so it cannot pass a test the real index would fail.
- Caps live in the repository, not only the route (`MAX_DOC_BODY_BYTES` = 64 KB, measured in **bytes** on the canonical re-serialized form), so every writer inherits them. The per-channel document cap is counted only on create — an update cannot grow the channel — and the count/insert race can overshoot by the number of concurrent creates, which is the right trade against taking a lock on the hot path.
- Documents die with their channel on **deletion**, not expiry — extending revives an expired channel, exactly the reasoning behind the `q` channel's Redis credential. Both the delete route and the daily sweep call it, and both filter by id prefix (`auth_`/`q_`) so a large delete batch does not spend its budget on statements that can only match nothing.
- **Returning early from a Prisma interactive transaction does not roll back what it already wrote.** `replaceShots` bumped the parent's `updated_at` as its first statement and then `return undefined`d on a bad key; the bump committed, so a _refused_ screenshot commit still moved the entry's "last edited" time (2026-09-01, found by review, not by the suite — the contract only asserted the success path). Do every validating read first and only then the writes, or `throw` so the transaction actually rolls back.
- **A presign quota counts reservations, not the committed set.** The show screenshot cap first counted `live` rows plus unexpired `pending` ones, which is the natural reading of "three per entry" — and it made an entry holding three permanently unable to presign a replacement, since the whole flow is presign-N → PUT-N → one commit that replaces the set. Cap what is _in flight_; the commit body caps what lands.
- **Never re-read a row to learn the version a successful CAS write produced.** The first implementation ran `updateMany … where version = ?` and then re-read the row; a writer landing between the update and the re-read handed the caller the _other_ writer's version as its `ETag`, so its next `If-Match` passed and silently overwrote it. The successful version is `ifVersion + 1` by construction; read back only on the failure path (to answer 409 with the current version).

## Key-value store (`kv_*`, migration `m0014_kvstore`, 2026-09-04)

- Three tables under a project: `kv_collections` (a named box with a read and a write scope, both `kv_scope`, plus two caps), `kv_entries` (`PK (collection_id, owner_id, k)`, one JSON value per key) and `kv_keys` (the wrapped DEK of an encrypted collection, written and read only by the state stack). Design of record: `docs/decisions.md` _Key-value store (`kv`)_.
- `owner_id` and `k` are `utf8mb4_bin`, declared **inline in the `CREATE TABLE`** rather than by a later `MODIFY` because they are primary-key columns; `collection_id` keeps the database default so its foreign key matches (errno 150). `name` stays `_ci` — it is a human-facing name, not a key. The same split as `state_docs`, and the fake mirrors both halves.
- **The enum is shared by two columns** (`read_scope`, `write_scope`) and is append-only; `test/enumOrder.test.ts` parses the `enum` body line by line, so it must be multi-line and can carry **no comment inside the block** — a comment line reads as a value.
- `(collection_id, expires_at)` is the only expiry index, and it is enough only because every purge is scoped to one collection. A global `WHERE expires_at <= now` cannot use it (leading-column rule above). The same rule bites one level deeper: `k` is the **third** PK column, so a prefix search that does not fix `owner_id` scans the whole collection — measured 45,100 rows read to return 51 on a 50k-row collection, on 10.5 and 11 alike. A shared-namespace collection must pass `ownerId: ""` to get the 20-row plan.
- **Soft-delete frees the name by parking the row on its own id**, so the guard that keeps a name from taking that shape has to fold the way the unique index compares — `utf8mb4_unicode_ci` is case-, accent- and PAD-SPACE-insensitive, so a case-sensitive regex let `KV_01H…` through and would have blocked that collection's delete for good (found by review, 2026-09-04).
- **A parent delete whose child cascades needs the drain as a precondition, not as a convention.** `deleteCollectionRow` deletes on `… AND kv_entries: { none: {} }`; without it a mis-ordered sweep issues one cascading `DELETE` over up to 100,000 rows. Measured on an idle box with 16 KiB values: 1,000 rows ≈ 0.13 s, 10,000 ≈ 1.3 s — and the statement holds row locks on all of them, against a 5 s `max_statement_time` on a shared host. The batch ceiling is 2,000 and the sweep uses 1,000.
- `deleteMany` cannot express `LIMIT`, so the batched deletes are this package's only `$executeRaw`: tagged template, every value a placeholder, and the bound alone through `Prisma.raw` **after** an integer/range check, because MariaDB takes no placeholder in `LIMIT`.
- **An expired row is absent, but only its version survives.** A write over one continues the version (`old + 1`, so a stale `If-Match` cannot land on the reborn key) and is reported as a create — which means "keep the existing ttl" must resolve to _no_ ttl there. Inheriting the lapsed `expires_at` answered 201 for an entry the next read could not see (found by all three reviews, 2026-09-04; both implementations had it, so the contract cemented it).
- **Cap what the caller sent, not what you store.** The 16 KiB value cap is on the plaintext byte count the writer passes; the stored text has its own looser bound, or an encrypted collection silently loses a third of its allowance to base64.
- **A cap counted on live rows is a cap a TTL churn walks past** (found by review, 2026-09-04). `countEntries` hides expired rows because an expired entry must not hold a slot — but a create gated on that number is one `PUT /{fresh key}?ttl=1` away from meaningless: a second later nothing the caller wrote is alive, both counts read ~0 for ever, and the table grows without bound on a host every stage shares. The create path therefore counts what the table **holds** (`includeExpired`), and only a collection whose stored rows reach a cap pays for the inline purge and the second, live count that decides the refusal. `stored < cap` implies `live < cap`, so the ordinary create got _cheaper_ as well as correct. The general shape: a quota read through a filter that the quota's own consumer controls is not a quota.

- **A daily sweep that walks a table needs a cursor, or it only ever sweeps the front of it** (found by review, 2026-09-04). `runKvStoreSweep` had a fixed statement budget and restarted at the lowest collection id every day; ids are ULIDs and an empty collection still costs a statement, so a stage with more collections than the budget would reclaim its oldest for ever and its newest never — and the comment saying "whatever it does not reach today it reaches tomorrow" was true only _within_ one collection's drain. The position lives in Redis (`kv:sweep:after`) and wraps; a lost cursor costs one restart, never a failed sweep. The general shape: a bounded walk over an ordered key space is only fair if the position outlives the run.
- **Order the phases of a shared budget by what is irrecoverable, not by what is cheap.** The same sweep purges a dead auth channel's entries, drains soft-deleted collections and reclaims expiries. Only the first has a queue that is _not_ the database: the channel ids come from that day's expiry run and nothing names those rows afterwards, so a phase skipped there is work lost rather than deferred. It goes first. And it must be fed both lifecycle lists — the expiry path _and_ the hard purge 30 days after a manual delete, which is the last moment the id exists at all.
- **A bounded walk records its position only when the item is finished.** The same sweep advanced its cursor on entering a collection, so one the budget cut short was written down as done and its rows waited for a whole wrap of the stage. And "truncated" has to mean _there was more to do_, not _the budget is spent_: a phase that finishes on its last statement is finished, and a flag that cries wolf is one nobody reads.
- **The one number a size report cannot measure must be absent, not zero.** `entriesTableBytes()` reads `kv_entries`' bytes from `information_schema`; the memory fake has no page count and a grant that cannot see the row returns none, so the answer is optional and the digest reads its absence as "unknown". **Do not bundle an O(1) read with a scan that answers a different question**: the two started as one `usage()` call, and a statement-limit timeout on the `GROUP BY` would have taken the size with it — at exactly the table size the warning exists for. A failed read is also its own warning, not just a line in `errors`, or the alarm goes blind silently.
- The state MySQL account's grant for the store is `SELECT` on `kv_collections`, `SELECT, INSERT` on `kv_keys` and `SELECT, INSERT, UPDATE, DELETE` on `kv_entries` — applied in the ops repo **after** `m0014_kvstore` has run on the stage (`GRANT` on a missing table is `ERROR 1146` and applies nothing). No `UPDATE`/`DELETE` on `kv_keys`: the state stack mints a wrapped DEK once and reads it afterwards, cascade removal is console's, and the power to overwrite a wrapped DEK is the power to make a collection unreadable for good. The migration's header comment says the account gains "DML on `kv_entries`/`kv_keys`", which over-describes `kv_keys`; the file is applied and cannot be edited, so this line is the correction.

## Teams and projects (`6_org_project` + `7_team_rename`, 2026-08-26)

- **Rename applied schema with a new migration, never by editing the applied file.** dev already ran `6_org_project` when "organization" became "team", so `7_team_rename` does the `RENAME TABLE` / `RENAME COLUMN` / `RENAME INDEX` and re-creates every foreign key under its new name (MariaDB cannot rename a foreign key). The old file keeps its name and content; the container suite applies both in order, which is what proves the pair matches `schema.prisma`.

- **Expand and contract are two commits, never one migration.** `deploy.sh` runs `migrate.sh`, which applies _every_ pending migration, and MariaDB DDL does not roll back — so a migration that both adds and drops would take the old bundle down with it. `6_org_project` only adds tables and nullable `team_id`/`project_id`; the `NOT NULL`, the team-scoped unique names and the catalog-permission drops are a later file, committed only once every stage runs a bundle that fills the columns.
- **Prove the SQL against the schema, not by eye.** `prisma migrate diff` needs a shadow database in Prisma 7: start `mariadb:11`, apply `prisma/migrations/*/migration.sql` in order (what `testDb.ts` does), then `MYSQL_* … prisma migrate diff --from-config-datasource --to-schema prisma/schema.prisma --script` must print an empty migration. The hand-written SQL and the hand-written schema drifted twice while writing them and the container suite alone would not have said so — it only exercises the columns the repositories touch.
- **A display-only actor column follows `cancelled_by`, not the `_bin` rule.** `m0013_event_force_close` (2026-09-01) adds `vote_closed_by VARCHAR(64)` on the table default `utf8mb4_unicode_ci`, with no FK and no index — `utf8mb4_bin` is for identities a unique index or an authorization check compares byte-exactly, and diverging from the column this one mirrors would have bought nothing. Three nullable columns appended in one `ALTER` is instant on MariaDB (verified with an explicit `ALGORITHM=INSTANT` against 10.5): no rebuild, no lock, and it cannot half-apply. Old code is safe against the new columns too, because the generated client emits an explicit column list rather than `SELECT *`, so a console rollback does not need a contract migration.
- **`TeamDb` is one repository on purpose.** Every write that must be recorded (`team_history`) runs in one interactive `$transaction` with the history insert; there is no transaction-sharing API between repositories, so team/member/project/version/issue/discussion writes all live in the one repository. Resource writes (channels, apps, bundles) stay in their own repositories and call `appendHistory` best-effort afterwards — say so in the route, it is the documented gap.
- **The team row is the mutex.** `SELECT id FROM teams WHERE id = ? FOR UPDATE` leads every count-then-write (last-owner protection, issue numbering, join cooldown). Inside the callback only `tx` may be used: the pool has one connection and the outer client would wait on it forever (`rules/data.md` above).
- **A unique index with a nullable column does not deduplicate.** MySQL treats `NULL`s as distinct, so `(version_id, kind, artifact_id, bundle_id, asset_version)` would have allowed the same link twice. `project_version_links.target` spells the identity out (`artifact:{id}` / `asset:{bundle}:{version}`, `utf8mb4_bin`) and is what the unique index covers; the typed columns exist for the cascades only.
- **Memory fakes must mirror foreign keys the contract exercises.** The link contract failed only on MariaDB (`P2003` for a bundle the fake never checked). `createMemoryTeamDb` takes `memberExists`/`artifactExists`/`bundleExists`, and the contract seeds the bundle through a hook so both sides see the same row. Same rule as `owner_id`: an unknown parent is `AppError("unavailable")` (a foreign-key failure), except where the repository looks the parent up itself and answers `not_found` — keep the two implementations returning the same code and let the test pin it.
- **Lock order: the team row first, in every transaction that records.** An `team_history` insert takes a _shared_ lock on the `teams` row through its foreign key. If only the count-then-write paths took the exclusive `FOR UPDATE` and the rest locked a child row first, two lock orders would exist and InnoDB would abort one side with `ER_LOCK_DEADLOCK` (a 503 for a legitimate request). So every `TeamDb` transaction that calls `record` begins with `lockTeam`, and existence is then decided by `updateMany`/`deleteMany` counts rather than `update`/`delete` (which throw `P2025` → 503 when a concurrent delete wins).
- **MariaDB collations are PAD SPACE**: `"Acme "` and `"Acme"` are one key under `utf8mb4_unicode_ci` _and_ under `utf8mb4_bin`. The fake compares `trimEnd()`-ed names; routes validate names to a grammar that has no trailing blank. `unicode_ci` also folds accents and width, which the fake does not mirror — the grammar is ASCII, which is what makes that safe.
- **Recovering a half-applied migration.** MariaDB DDL is per statement, so a failed `ADD CONSTRAINT` leaves the tables created before it. `6_org_project` orders each table's foreign keys right after its `CREATE`, so the worst case is one extra table. Repair by hand — drop what the failed file created (reverse order; for the resource tables `ALTER TABLE … DROP FOREIGN KEY …, DROP COLUMN team_id, DROP COLUMN project_id`) — then `prisma migrate resolve --rolled-back <name>` and rerun `migrate.sh`. `testDb.ts` splits the SQL on every `;` after dropping `--` lines, so a `;` inside a string literal or ENUM value would break only the test path: keep migrations free of them.
- The team/project tables (`teams`, `team_members`, `team_history`, `projects`, `project_versions`, `project_version_links`, `issues`, `issue_comments`, `discussions`, `discussion_comments`, `platform_settings`) are **console-only**, like events: auth/topic/match/state need no grant and their code never selects them. Migration directories sort lexically in both `prisma migrate deploy` and `testDb.ts` — `10_` would land before `2_`, so from the contract file on the names are `m{NNNN}_{slug}` (`docs/decisions.md`).
- **`Promise.all` over Prisma calls outside a transaction serializes on the one-connection pool; it never deadlocks, but it never parallelises either.** `GET /teams?scope=all` first did one `findTeamMember` per team that way; it is one `listTeamsForMember` now. Inside `$transaction` the rule is stricter (only `tx`, `rules/data.md` above). Reads that resolve member ids to logins still do one `listMembers()` per request (the events pattern) — fine at tens of members; a `findMembersByIds` is the fix when the table grows.
- **Resource counts that guard a delete must count soft-deleted channels.** `channels.project_id`/`team_id` are `ON DELETE RESTRICT` and a deleted channel keeps its row until the daily sweep purges it (`purgeChannels`, 30 days after the soft-delete), so a count filtered on `deleted_at IS NULL` says "empty" and the delete answers 503 (`P2003`). `deleteProject`/`deleteTeam` count every row and answer 409; the memory fake's `countResources` hook counts the same way (`services/console/test/helpers.ts`).
- **P3 (2026-08-26): resources moved under projects.** `Insert{Channel,App,Bundle}Input.teamId/projectId` are required; rows created before the mapping keep `NULL` and are invisible to `projectResource` (nobody can claim them — the safe direction) until `scripts/apply-team-project-map.mjs` assigns or deletes them. `findAppByName`/`findBundleByName` take the team; `ChannelFilter.ownerId` is gone and `teamIds` (one `IN` query for every team the caller is seated in) replaces the per-owner list. `expireChannels` returns the deleted rows with their `teamId/projectId/kind/name`, because the sweep records `resource.expire` in the team's history and revokes by kind rather than id prefix.
- **A migration map's project unit is the app, and versions are backfilled from artifact tags.** The first dev map put every dooroo app under one `apps` project with no versions; `scripts/split-projects-per-app.mjs` (idempotent, dry-run by default, `local/split-projects.<stage>.json`) now creates one project per app, writes the human name into `projects.description` **and** `catalog_apps.description` (resource names are ASCII-only), and creates one version per distinct `major.minor.patch` — the artifact's `version` tag with the `+build` suffix stripped, since the build number belongs to the artifact — linking every artifact. Run it right after `apply-team-project-map.mjs` on a stage that still has a catch-all project.
- **A contract migration is gated by `migrate.sh`, not by discipline.** A pending migration whose first line is `-- contract` is refused unless `--allow-contract` is passed and `scripts/contract-preflight.mjs` (`contractPreflight` in `@yyt/console-db`, also the verify step of `apply-team-project-map.mjs`) reports nothing — `deploy.sh` never passes the flag. The pre-flight counts soft-deleted channels as name holders, so smoke residue has to be hard-deleted first (dev 2026-08-26: 39 rows under the `org_*` smoke teams, `state_docs` checked empty first).
- **`m0008_team_project_contract` makes names unique per team.** `catalog_apps_team_name`, `asset_bundles_team_name` and `channels_team_name` are `(team_id, name)` unique indexes (the channel one has no `deleted_at` filter — decided 2026-08-26, `docs/decisions.md`: a deleted channel holds its name until `purgeChannels` hard-deletes the row 30 days after the soft-delete; the purge did not exist before P9 — the sweep only soft-deleted — so the route now checks `listChannels({ includeDeleted: true })` to answer a clear 409 instead of the bare `duplicate key`), the global `catalog_apps_name`/`asset_bundles_name` are gone, `team_id`/`project_id` are `NOT NULL` on all three tables, and the catalog permission tables/columns were dropped. The memory fakes mirror exactly that: `nameTaken(teamId, name)` in the catalog/assets fakes, and the console fake refuses a same-team name even when the holder is soft-deleted. Consequences: the generated client cannot express `team_id: null`, so `contractPreflight` counts unmapped rows with raw SQL (it runs _before_ the contract on a stage), and fixtures that need the expand-era schema use `startTestDb({ through: "7_team_rename" })` in a second container. The route-level "name used by another team" explanation (`untilContractUnique`) went with the global index; a cross-team duplicate is simply allowed and the one-release name resolver (`/catalog/apps/{name}`) answers 404 when the caller's teams hold more than one match.
- **Per-request fan-out to keep an eye on**: `crumbs()` runs one `listMembers` plus one `findProject`/`findTeam` per distinct id per page, and the `/catalog/apps/{name}` fallback runs `memberTeamIds` + `listApps({teamIds})` on every name lookup. Bounded by page size and team count today; `findMembersByIds` and dropping the fallback (P10) are the fixes when it grows.
- **Resource history is best-effort and says so** (`services/console/src/resources.ts`): channel/app/bundle writes stay in their own repositories, then call `appendHistory` in a try/catch that logs; the global audit row written by the same route is the second record. Detail carries `{ resource: { kind, id, name }, fields }` only — never config, never a hook URL.
- `resetTestDb` no longer keeps a hand-ordered `WIPE_ORDER`: it lists base tables from `information_schema` and deletes with `foreign_key_checks=0` (session-scoped; the test client has one connection). A hand-written list went stale with every migration and silently left the new tables populated between contracts.

## Expiry

- Readers of auth channels do **not** add a Redis cache (rows contain secrets); one SELECT per request is cheap. The 60s cache rule applies to topic/match config without secrets.
- `lobby`/`q` channels store `{}` as `secret_json` on purpose (`docs/decisions.md` _Realtime gateway_): the gateway verifies tokens by calling auth and neither kind has a server-to-server caller, so the whole "do not cache a secret-bearing row" problem is designed away rather than worked around. Consequences to keep in mind: `rotate-secret` must refuse them, the one-time-secret UI must stay silent for them, and adding a server-initiated route later (`POST /lobby/{id}/publish`) means reintroducing an apiKey deliberately.
- A `q` channel's Redis names are **derived from the channel id, never stored**: `game:{stage}:{id}:{event,queue,lock,awaiter}:` and `game:out:{stage}:{id}:`, with ACL patterns `~game:{stage}:{id}:*` / `&game:out:{stage}:{id}:*` (`gatewayRedis` in `services/console/src/channels.ts` is the only place that computes them). They are configuration on three sides at once — gateway, tslib, and the participant's own Lambda — and a mismatch is a silent no-op rather than an error, so nobody is allowed to type them. The `{stage}` segment is not cosmetic: one Redis instance serves both stages, so a dev-scoped grant without it also matches every prod game key — the same reason every platform key carries `{service}:{stage}:`. Derive **all four** key prefixes, not the three the gateway itself uses: `handleActor` requires `event`/`queue`/`lock`/`awaiter`, and any one left for the participant to name lands outside `aclKeyPattern` and fails `NOPERM` at actor start. Pass them to tslib's prefix options directly — a helper that appends its own segment (`…:queue:queue:`) stays inside the ACL and so fails silently instead.
- Channels: `expires_at` default +7d, extend +7d (cap now+28d); disabled on expiry; deleted (secrets wiped) 30d later by the console `expire` cron.
- `ConsoleDb` lifecycle writes (`updateChannel`, `expireChannels`) are `update … where deleted_at is null`; soft-delete wipes `secret_json` to `{}` immediately, so auth/topic/match readers must treat a missing `secret`/`apiKey` as "no channel" (they already get `undefined` via `deleted_at`).
- Console runs `migrateConsoleDb` inside a memoized `getDeps()` promise; a rejected cold start clears the memo so the next invocation retries instead of serving a poisoned container.
- Connection budget per stack (`reservedConcurrency`): the authoritative table is the "Connection budget" bullet under MySQL above (55 of 60 since 2026-08-30); update that bullet when adding a function. The realtime gateway is **not** in this budget and must not enter it: it is a long-lived process on the same box, so a pool of its own would hold connections until `wait_timeout`, and `docs/decisions.md` therefore has it read channel config through the console API (`GET /gw/channels/{id}`) instead of MariaDB. If that ever changes, the numbers here have to be cut first — the box has 2 GB and `max_connections` cannot go up.
- Events (`m0009_event_redesign`, 2026-08-29): `events` + `event_options`/`event_votes`/`event_revisions`/`event_posters`/`event_comments` are console-only; every child table cascades on event delete, and `event_votes` also cascades on option delete, so `replaceOptions` on a draft drops the votes with the options. The stored `events.status` is a **cache**: `waiting/opened/closed` are derived from `starts_at` + `duration_hours` on every read (`effectiveStatus`), the vote is decided by the first read past `vote_until` (one `updateMany … where status = 'voting'`, so two readers cannot decide twice), and `runEventSweep` persists whatever reads only derived. Never filter by the stored status for visibility — `listEvents(["voting","waiting","opened"])` is only the candidate set for the one-event-per-day check, and each row is settled before use. `commitRevision` bumps `events.revision` conditionally (`where revision = ?`) and inserts the revision row in the same transaction: a lost race is a 409, never a skipped number. `event_posters` rows with `replaced_at` set and `deleted_at` NULL are the S3 deletes that failed; the sweep retries them. Logins are still resolved with one `listMembers()` per read (fine at tens of members). The migration is destructive on purpose and deliberately **not** a `-- contract` file (nothing to preflight; both stages held test data only) — do not copy that shortcut for a table with real rows.
- Topic keys (`topic:{stage}:`): `t:{topicId}` meta JSON, `t:{topicId}:conns` set, `t:{topicId}:seq` counter, `conn:{connId}` → `{topicId,userId,at}`, `chcfg:{channelId}` 60s cache without the apiKey. Every key is set with the topic's _remaining_ TTL, so expiry needs no sweep: the next client message finds no `conn`/meta and answers `{type:"expired"}`. `nextSeq` re-applies the TTL after each `INCR` (the counter is created lazily).
- Topic apiKey lookup has no index: `findByApiKey` scans `listChannels({kind:"topic"})` and compares sha256 digests with `timingSafeEqual` for every row. Fine at hackathon scale (tens of rows); add a hashed-key column in console before it grows.
- Match keys (`match:{stage}:`): `ch:{channelId}:queue` list, `ticket:{connId}` JSON, `user:{channelId}:{userId}` → connId (compare-and-delete on removal so a stale disconnect never unbinds a newer socket), `active` set scanned by the tick, `lock:{channelId}` (30s; `enqueue` and every dispatch run under it, so a sweep can never deactivate a channel that just got a ticket and a reconnecting user cannot land in two parties), `chcfg:{channelId}` 60s cache without the apiKey, `result:{matchId}` 10m (`pending` → `matched`/`failed`, never the callback payload). `snapshot()` prunes queue entries whose ticket vanished.
- Catalog (v3 migration): deletes are **hard** — artifact rows mirror S3 objects (route deletes the object first), app/group deletion relies on FK `on delete cascade` (permissions/artifacts/uploads) and `set null` (app.group_id). Names and `pending_github_login` compare case-insensitively (utf8mb4 default collation, matches GitHub login semantics) — the memory fake mirrors this with lowercase comparison. mysql2 counts _changed_ rows, not matched rows: any "update returns boolean" repo method without an always-bumped `updated_at` column must re-check row existence after `affectedRows === 0` (see `updatePendingUpload`), and `insert … on duplicate key update` is banned on tables with several unique keys (a stray id collision silently rewrites an unrelated row — upsert = insert, catch conflict, targeted update). Presigned upload object keys are `uploads/{id}/{filename}` so the S3 event can recover the pending-upload id.
- Assets (v3 → migration `3_assets`): `asset_bundles` / `asset_files` / `asset_pending_uploads`, deliberately **not** more `catalog_*` columns. The invariant that shapes the schema is immutability — objects are served `Cache-Control: immutable`, so `(bundle_id, version, path)` carries a unique index and a second commit for the same triple must be a 409, never an update. Two consequences that are easy to miss: a bundle that holds files cannot be renamed (`name` is a live object-key segment, so the stored `url` rows would 404), and the commit's conflict-recovery path must distinguish "my own retried commit" (deterministic `af_{uploadId[0:8]}` id → heal) from "another upload won this path" (delete nothing — the object under `finalKey` is what the winner's row points at). `updateBundle` always bumps `updated_at` so the changed-rows count never lies about a no-op patch, the same rule as the catalog tables (measured 2026-08-25: the `@prisma/adapter-mariadb` driver actually reports _matched_ rows, unlike the mysql2 pool the rule was written for — the always-bumped column is now belt-and-braces, not the load-bearing part).
- **Versions and paths are `utf8mb4_bin`** (migration `4_assets_binary_paths`), bundle names are not. The tables inherited the database's `_ci` collation, which made `v1/map.json` and `V1/map.json` one row naming two S3 objects — S3 keys are case-sensitive, so the commit wrote a live public object the unique index then refused to record, in the one prefix nothing sweeps. Any column that _is_ a storage key needs the storage's own comparison semantics; a column that is a human-facing name (the bundle) is better off case-insensitive, so the two must not be collated alike. The in-memory fake has to mirror the split on both sides — equality **and** ordering (`utf8mb4_bin` sorts `MAP.json` before `map.json`; `localeCompare` does the opposite), or the contract test passes on the fake and lies about the database. Staging is `asset-uploads/{uploadId}/{path}`, disjoint from the catalog's `uploads/` so neither sweep can reach the other's objects, and **nothing sweeps `assets/`**: retention there would 404 a URL a running client has already cached.
- Quotas over a presign→commit flow must count **grants, not just commits**: a presigned URL is a reservation, and a caller that pipelines a hundred of them before committing any sees an empty bundle on every request. Count live (`pending`, unexpired) upload rows alongside the committed ones — and at commit time exclude the upload's _own_ reservation, or the last upload under the cap always refuses itself. Releasing the reservation matters as much as taking it: a commit that fails after the claim must mark its upload `failed`, otherwise the retry it just asked the caller to make is blocked by the caller's own dead grant until the grant expires.
- **Insert the row before writing the object**, not after. The row is the claim: with the copy first, two commits for the same key both copy — the loser overwrites a live `immutable` object before the unique index tells it that it lost, and its bytes are then served under someone else's row. Claim-first inverts the failure into the harmless direction (a row naming an object that does not exist yet), and the rollback is a row delete rather than an unreclaimable public object.
- A team whose only leftovers are soft-deleted channels cannot be deleted through the API until the sweep purges them (`purgeChannels`, 30 days after the soft-delete; `RESTRICT` FK, 409 `still has resources`). To retire smoke residue on dev: hard-delete those channel rows by id (`deleted_at IS NOT NULL`, scoped to the project, check `state_docs` first), then `DELETE /projects/{id}` and `DELETE /teams/{id}`. Never do this for real teams' data.
- `7_team_rename` (org → team) is ~20 non-transactional DDL statements (RENAME TABLE, DROP/ADD FOREIGN KEY, RENAME COLUMN). If it fails midway on a stage, `prisma migrate status` shows it failed and `deploy.sh` refuses to continue: run `prisma migrate resolve --rolled-back 7_team_rename` from `packages/console-db` with the stage env, finish or revert the remaining renames by hand (compare `information_schema.tables/columns` against the migration file), then `migrate.sh <stage>` again. Take the dump first; there is no automatic rollback.
- **Version link counts are derived, never stored.** `project_version_links` cascade with their artifact (retention cleanup) and bundle, so a denormalized counter would drift with no hook to fix it. `TeamDb.listVersions`/`findVersion` run one `groupBy (version_id, kind)` over the page's ids (a range scan on the `version_id` prefix of the `(version_id, target)` unique index; `kind` is read from the rows) and expose `artifactCount`/`assetCount`; the memory fake hides links whose `artifactExists`/`bundleExists` is false, for counts and `listVersionLinks` alike, to mirror the cascade. Keep the SPA/CLI reading those fields instead of opening every version's link list.
- Bumping a doc-store schema `format` (sample-morpg sheet 1 → 2): the old code treats an unknown format as "start over", so an old Lambda container writing over an upgraded row wipes it under a matching CAS version. Deploy such a bump while no long-running writer (dungeon actor) is in flight, and make the new parser read every older format forever.
- Asset bundle format bumps (sample-morpg, 2026-08-29): the parser must keep reading the previous format (format 1 still parses as format 2 with its `quests` array as kill quests) because the world bundle URL is a channel config the http Lambda fetches at request time — with a hard cut, every route (not only the sheet ones: `GET /character` and `POST /dungeon/enter` await the templates too) answers `502 upstream` while the deployed code and the published bundle disagree. Publish the new bundle version, repoint the lobby, then redeploy; the Lambda caches a bundle per container, so a repoint alone serves the old templates until containers recycle.
- The dungeon actor counts kill quests against the _world_ bundle's templates, never the field's: a zone's own bundle is a plain grid (no templates), so reading quests from the field silently drops every kill (`resolveBundles` loads both; one fetch when they coincide).
