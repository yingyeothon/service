# Data

> Storage is self-hosted MariaDB + Redis (host and account details live only in the local private ops repo `yyt-stateful` — never in this public repo). The previous sqlite-on-S3 + Upstash design was removed on 2026-08-22 (`todo/09-storage-migration.md`).

## Accounts and environments

- One MySQL database per stage (name in `yyt-stateful`), owned by console (only writer, owns migrations). auth/topic/match use `SELECT`-only accounts.
- One MySQL account and one Redis ACL user per service×stage. Redis ACL users are restricted to keys/channels `{service}:{stage}:*` (`resetkeys ~… resetchannels &…`, `+@all -@dangerous`), so a wrong prefix fails with NOPERM instead of leaking — keep the `{service}:{stage}:` prefix rule anyway for readability.
- Credentials live in `local/env/{service}.{stage}.env` (gitignored; layout in `local/env.example`, see `local/README.md`) and are pushed to SSM for Lambda. Never commit or log them. Rotate via `yyt-stateful` scripts (`ALTER USER` / `ACL SETUSER … >pw` + `ACL SAVE`) and update the `.env` in the same step.
- tslib's `naive-redis` authenticates with `AUTH <username> <password>` only when `username` is set (`REDIS_USER` via `gamebaseOptionsFromEnv`); without it the ACL user never logs in and every command fails `NOAUTH`. Its test suite uses `resetkeys ~pattern` so a wrong prefix surfaces as `NOPERM`, same as ours.
- Redis 6.2 quirk: a new ACL user starts with `allchannels`; adding `&pattern` errors unless `resetchannels` precedes it.
- Host limits (see `yyt-stateful`): Redis `maxmemory 256mb allkeys-lru` (every runtime key still needs a TTL; eviction is a safety net, not a design), MariaDB `max_connections=60` — keep Lambda pools tiny (1 connection per container) and prefer short-lived connections.

## MySQL (console-owned)

- Schema lives in `@yyt/console-db` `prisma/schema.prisma` + `prisma/migrations/*` (Prisma 7, `prisma-client` generator, `@prisma/adapter-mariadb`). Migrations run at **deploy time only**: `scripts/migrate.sh <stage>` (called by `scripts/deploy.sh console <stage>`) assembles the URL from `local/env/console.<stage>.env` inside `prisma.config.ts` and runs `prisma migrate deploy` — the URL embeds the password, never print or log it. Pre-existing databases are baselined once with `scripts/migrate.sh <stage> baseline` (`prisma migrate resolve --applied 0_init`); baseline now refuses when the live schema drifts from the baseline (learned on prod: v3 tables were missing but the baseline was marked applied, so `migrate deploy` reported "up to date" over an incomplete schema).
- Collation: every table must sit on the database default `utf8mb4_unicode_ci`. The legacy runtime DDL's `default charset=utf8mb4` pinned tables to `utf8mb4_general_ci`, and Prisma-generated DDL pins `utf8mb4_unicode_ci` — a mixed fleet makes every new FK to an old table fail with errno 150. Both stages were converged (drop FKs → `CONVERT TO CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci` → re-add FKs; `foreign_key_checks=0` alone is NOT enough, MariaDB still refuses to alter an FK-referenced column's collation). Both collations are case-insensitive, so `ci`-dependent contracts were unaffected. The legacy runtime migrator (`migrateConsoleDb`/`GET_LOCK` at console cold start) is retired; the old `schema_migrations` table remains as a modeled no-op relic. Operational discipline: migrations are forward-only and must be expand/contract-safe (the schema goes live before the new code, and old code keeps running against it until every stack is redeployed); deploy console first when a change spans services; the deploy machine needs direct DB reachability (the Lambda migrator did not).
- Prisma repositories: `updateMany/deleteMany` return matched/affected counts (the boolean contracts rely on it), `P2002` → `AppError("conflict")`, every other Prisma/driver error → `AppError("unavailable")` with only `prisma <code>` in the cause (Prisma messages can quote values — never forward them). BigInt columns come back as JS `bigint`; repositories coerce with `Number()`.
- Times are unix seconds in `bigint`; JSON configs are `mediumtext` parsed in code. MariaDB returns `bigint` as JS numbers up to 2^53 (`supportBigNumbers` + `bigNumberStrings:false`); repositories still coerce with `Number()` so a string never leaks into comparisons.
- `Db` maps driver errors: `ER_DUP_ENTRY` → `AppError("conflict")`, everything else → `AppError("unavailable")` with the driver error as `cause` (never in the message — messages reach clients). A SELECT-only account hitting an INSERT therefore surfaces as 503, not 500.
- Pool (`createPrismaClient`, mariadb adapter): `connectionLimit: 1`, `connectTimeout` 3s, `acquireTimeout` 5s, `idleTimeout` 60 (seconds), keep-alive on, `initSql: "SET SESSION max_statement_time=5"` (runs on every new connection; mariadb has no per-query timeout), built once per Lambda container. Never create a client per request. Interactive `$transaction` pins the one connection — inside the callback use only `tx`.
- Connection budget: a frozen/reaped container never closes its socket, so the server holds it until `wait_timeout`. Every function sets `reservedConcurrency` (auth: 10; budget 57 of 60 across the four stacks, see the per-stack line below) and `yyt-stateful` must set a short `wait_timeout` (≈120s) — tracked in `todo/07-infra.md`. Dev with debug hooks uses two pools per container.
- `Db.transaction` pins one connection; inside the callback use only `tx` (the outer handle would wait for the same connection and the pool rejects it). A connection whose rollback/commit failed is destroyed, never released back. `migrateConsoleDb` runs inside `transaction` because `GET_LOCK` is per-session; lock wait is 5s (< Lambda timeout).
- `upsertMember` updates only when the `github_id` matched; a colliding _id_ with another `github_id` is a no-op + `AppError("conflict")`, and the call returns the id that owns the GitHub user — use that id for foreign keys (the debug seed learned this the hard way).
- Writers that are not console (dev-only debug seeding in auth) use console's dev account through separate `DEBUG_MYSQL_*` env (`docs/decisions.md` §auth "Debug seeding"); the code path must degrade to "hooks disabled" when those vars are absent.

## Redis (ioredis, TCP)

- Every key starts with `{service}:{stage}:` — the `REDIS_KEY_PREFIX` env must equal `{service}:{stage}:` and handlers assert it at cold start. The ACL user enforces the same pattern; a mismatch shows up as `NOPERM`.
- ACL users have `-@dangerous`, which removes `INFO`: set `enableReadyCheck: false` in ioredis or every connection logs "Skipping the ready check" and waits. `KEYS`/`FLUSHALL`/`CLIENT` are also unavailable — design without them (no key scans; track membership in sets with TTLs).
- Every runtime key has a TTL. Channel config cache 60s (never for rows with secrets); topic keys = topic TTL (≤20m); match tickets = waitTimeout+120s; OAuth state 10m; console sessions 7d.
- Prefer a Lua `eval` for compare-and-delete and multi-key atomic steps; otherwise serialize with `withLock`.
- Client options: `lazyConnect`, `connectTimeout` 2s, `commandTimeout` 3s, `maxRetriesPerRequest: 1` (unreachable host fails in ≈4s, inside the 10s Lambda timeout), `enableAutoPipelining`, an `error` listener that logs through `Logger` (otherwise ioredis spams `console.error`). Every command error becomes `AppError("unavailable")` with cause `redis <code>`. One client per container; `close()` exists for tests, Lambda just lets the container die.
- Do not store secrets in Redis except short-lived session ids; secrets stay in MySQL.

## Expiry

- Readers of auth channels do **not** add a Redis cache (rows contain secrets); one SELECT per request is cheap. The 60s cache rule applies to topic/match config without secrets.
- `lobby`/`q` channels store `{}` as `secret_json` on purpose (`docs/decisions.md` _Realtime gateway_): the gateway verifies tokens by calling auth and neither kind has a server-to-server caller, so the whole "do not cache a secret-bearing row" problem is designed away rather than worked around. Consequences to keep in mind: `rotate-secret` must refuse them, the one-time-secret UI must stay silent for them, and adding a server-initiated route later (`POST /lobby/{id}/publish`) means reintroducing an apiKey deliberately.
- A `q` channel's Redis names are **derived from the channel id, never stored**: `game:{stage}:{id}:{event,queue,lock,awaiter}:` and `game:out:{stage}:{id}:`, with ACL patterns `~game:{stage}:{id}:*` / `&game:out:{stage}:{id}:*` (`gatewayRedis` in `services/console/src/channels.ts` is the only place that computes them). They are configuration on three sides at once — gateway, tslib, and the participant's own Lambda — and a mismatch is a silent no-op rather than an error, so nobody is allowed to type them. The `{stage}` segment is not cosmetic: one Redis instance serves both stages, so a dev-scoped grant without it also matches every prod game key — the same reason every platform key carries `{service}:{stage}:`. Derive **all four** key prefixes, not the three the gateway itself uses: `handleActor` requires `event`/`queue`/`lock`/`awaiter`, and any one left for the participant to name lands outside `aclKeyPattern` and fails `NOPERM` at actor start. Pass them to tslib's prefix options directly — a helper that appends its own segment (`…:queue:queue:`) stays inside the ACL and so fails silently instead.
- Channels: `expires_at` default +7d, extend +7d (cap now+28d); disabled on expiry; deleted (secrets wiped) 30d later by the console `expire` cron.
- `ConsoleDb` lifecycle writes (`updateChannel`, `expireChannels`) are `update … where deleted_at is null`; soft-delete wipes `secret_json` to `{}` immediately, so auth/topic/match readers must treat a missing `secret`/`apiKey` as "no channel" (they already get `undefined` via `deleted_at`).
- Console runs `migrateConsoleDb` inside a memoized `getDeps()` promise; a rejected cold start clears the memo so the next invocation retries instead of serving a poisoned container.
- Connection budget per stack (`reservedConcurrency`): auth 10, console 10 (`api`) + 1 (`expire`), match 10 (`ws`) + 8 (`authorizer`) + 4 (`worker`) + 1 (`tick`) + 1 (`debug`), topic 5 (`ws`) + 4 (`authorizer`) + 3 (`http`) = 57 of 60. Update this line when adding a function. The realtime gateway is **not** in this budget and must not enter it: it is a long-lived process on the same box, so a pool of its own would hold connections until `wait_timeout`, and `docs/decisions.md` therefore has it read channel config through the console API (`GET /gw/channels/{id}`) instead of MariaDB. If that ever changes, the numbers here have to be cut first — the box has 2 GB and `max_connections` cannot go up.
- Events (v2 migration): `events`/`proposals`/`votes` are console-only (no other service reads them). `votes` PK is `(event_id, member_id)` and `proposal_id` has `on delete cascade`, so deleting a proposal drops its votes; `updateEvent(id, patch, at, expectStatus)` is the only status writer and is conditional on `expectStatus` so concurrent admin clicks cannot double-advance. Proposal author logins are resolved with one `listMembers()` per read (fine at tens of members; add a join when it grows).
- Topic keys (`topic:{stage}:`): `t:{topicId}` meta JSON, `t:{topicId}:conns` set, `t:{topicId}:seq` counter, `conn:{connId}` → `{topicId,userId,at}`, `chcfg:{channelId}` 60s cache without the apiKey. Every key is set with the topic's _remaining_ TTL, so expiry needs no sweep: the next client message finds no `conn`/meta and answers `{type:"expired"}`. `nextSeq` re-applies the TTL after each `INCR` (the counter is created lazily).
- Topic apiKey lookup has no index: `findByApiKey` scans `listChannels({kind:"topic"})` and compares sha256 digests with `timingSafeEqual` for every row. Fine at hackathon scale (tens of rows); add a hashed-key column in console before it grows.
- Match keys (`match:{stage}:`): `ch:{channelId}:queue` list, `ticket:{connId}` JSON, `user:{channelId}:{userId}` → connId (compare-and-delete on removal so a stale disconnect never unbinds a newer socket), `active` set scanned by the tick, `lock:{channelId}` (30s; `enqueue` and every dispatch run under it, so a sweep can never deactivate a channel that just got a ticket and a reconnecting user cannot land in two parties), `chcfg:{channelId}` 60s cache without the apiKey, `result:{matchId}` 10m (`pending` → `matched`/`failed`, never the callback payload). `snapshot()` prunes queue entries whose ticket vanished.
- Catalog (v3 migration): deletes are **hard** — artifact rows mirror S3 objects (route deletes the object first), app/group deletion relies on FK `on delete cascade` (permissions/artifacts/uploads) and `set null` (app.group_id). Names and `pending_github_login` compare case-insensitively (utf8mb4 default collation, matches GitHub login semantics) — the memory fake mirrors this with lowercase comparison. mysql2 counts _changed_ rows, not matched rows: any "update returns boolean" repo method without an always-bumped `updated_at` column must re-check row existence after `affectedRows === 0` (see `updatePendingUpload`), and `insert … on duplicate key update` is banned on tables with several unique keys (a stray id collision silently rewrites an unrelated row — upsert = insert, catch conflict, targeted update). Presigned upload object keys are `uploads/{id}/{filename}` so the S3 event can recover the pending-upload id.
- Assets (v3 → migration `3_assets`): `asset_bundles` / `asset_files` / `asset_pending_uploads`, deliberately **not** more `catalog_*` columns. The invariant that shapes the schema is immutability — objects are served `Cache-Control: immutable`, so `(bundle_id, version, path)` carries a unique index and a second commit for the same triple must be a 409, never an update. Two consequences that are easy to miss: a bundle that holds files cannot be renamed (`name` is a live object-key segment, so the stored `url` rows would 404), and the commit's conflict-recovery path must distinguish "my own retried commit" (deterministic `af_{uploadId[0:8]}` id → heal) from "another upload won this path" (delete nothing — the object under `finalKey` is what the winner's row points at). `updateBundle` always bumps `updated_at` so the changed-rows count never lies about a no-op patch, the same rule as the catalog tables (measured 2026-08-25: the `@prisma/adapter-mariadb` driver actually reports _matched_ rows, unlike the mysql2 pool the rule was written for — the always-bumped column is now belt-and-braces, not the load-bearing part).
- **Versions and paths are `utf8mb4_bin`** (migration `4_assets_binary_paths`), bundle names are not. The tables inherited the database's `_ci` collation, which made `v1/map.json` and `V1/map.json` one row naming two S3 objects — S3 keys are case-sensitive, so the commit wrote a live public object the unique index then refused to record, in the one prefix nothing sweeps. Any column that _is_ a storage key needs the storage's own comparison semantics; a column that is a human-facing name (the bundle) is better off case-insensitive, so the two must not be collated alike. The in-memory fake has to mirror the split on both sides — equality **and** ordering (`utf8mb4_bin` sorts `MAP.json` before `map.json`; `localeCompare` does the opposite), or the contract test passes on the fake and lies about the database. Staging is `asset-uploads/{uploadId}/{path}`, disjoint from the catalog's `uploads/` so neither sweep can reach the other's objects, and **nothing sweeps `assets/`**: retention there would 404 a URL a running client has already cached.
- Quotas over a presign→commit flow must count **grants, not just commits**: a presigned URL is a reservation, and a caller that pipelines a hundred of them before committing any sees an empty bundle on every request. Count live (`pending`, unexpired) upload rows alongside the committed ones — and at commit time exclude the upload's _own_ reservation, or the last upload under the cap always refuses itself. Releasing the reservation matters as much as taking it: a commit that fails after the claim must mark its upload `failed`, otherwise the retry it just asked the caller to make is blocked by the caller's own dead grant until the grant expires.
- **Insert the row before writing the object**, not after. The row is the claim: with the copy first, two commits for the same key both copy — the loser overwrites a live `immutable` object before the unique index tells it that it lost, and its bytes are then served under someone else's row. Claim-first inverts the failure into the harmless direction (a row naming an object that does not exist yet), and the rollback is a row delete rather than an unreclaimable public object.
