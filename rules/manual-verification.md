# Manual Verification

- After tests pass, deploy the touched stack to `dev` (`scripts/deploy.sh <service> dev`) and exercise the real path: curl for httpApi, `wscat -c <wss> -s bearer -s <jwt>` for WebSocket, the match stack's dev-only `POST /debug/callback` as the matchmaker callback sink (`scripts/smoke/match.mjs`).
- `serverless-offline` is not used (poor WebSocket fidelity); `dev` on AWS is the controllable target. Cost is negligible at this traffic.
- Debug-only hooks (active only when `STAGE=dev` and `DEBUG_HOOKS=1`): seed a channel with a known secret, mint a test JWT (`POST /debug/token`), force-expire a topic, trigger `tryMatch`/`expire` on demand. They must be absent from `prod` deployments (guard at handler registration, not just at runtime).
- Record the exact commands used in the task's todo doc so the next session can repeat them.
- Stage prerequisites (per stage, once): MySQL/Redis accounts from `yyt-stateful` in `local/env/*.{stage}.env`, then `scripts/bootstrap-ssm.sh <stage>` (SSM `/yyt-service/{stage}/{service}/*`, `gateway-token` on every stage, `debug-key` and `auth/debug-mysql-*` on dev). `gateway-ws-url` is set by hand once the gateway host resolves. `serverless.yml` fails loudly on missing params by design. The S3 bucket `yyt-service-{stage}` remains for posters/backups (07).
- Opt-in integration tests hit the real dev instances: `YYT_IT=1 pnpm test` (skipped when `local/env/*.dev.env` is absent). Run them before deploying a storage change.
- auth smoke: `scripts/deploy.sh auth dev --param debugHooks=1` then `scripts/smoke/auth.mjs https://auth-dev.yyt.life "$(cat local/deploy/debug-key.dev)"`.
- console smoke: `scripts/deploy.sh console dev --param debugHooks=1` then `GATEWAY_TOKEN="$(cat local/deploy/gateway-token.dev)" scripts/smoke/console.mjs https://console-dev.yyt.life "$(cat local/deploy/debug-key.dev)" https://auth-dev.yyt.life`. Without `GATEWAY_TOKEN` the `GET /gw/channels` checks are skipped and the run still passes green — pass it, or you are not testing that route. `POST /debug/login` (dev only) mints a session for a synthetic member (`dbg_*`, negative `github_id`) so the API is testable without a GitHub OAuth app; the script cleans up its channels/tokens and demotes the synthetic member back to `pending`.
- catalog / asset smoke: with the same dev console deploy, `scripts/smoke/catalog.mjs https://console-dev.yyt.life "$(cat local/deploy/debug-key.dev)"` and `scripts/smoke/assets.mjs https://console-dev.yyt.life "$(cat local/deploy/debug-key.dev)"`. Both are self-cleaning (each run uses a timestamped app/bundle name) and both fetch the real CDN — the asset run is the only place that proves the presigned `Content-Type` is actually _signed_ (a substituted type must 403) and that CloudFront serves the committed object as `application/json` with `immutable`. Unit tests cannot see either, because both live in S3's signature and in the copy's metadata.
- Since todo/17 P3 every smoke script seats its synthetic member in a team of its own through `scripts/smoke/_team.mjs` (`ensureTeam`: find-or-create team `smoke-<script>` + project `game`; the auth seeder takes `projectId` so topic/match/dungeon channels can reference the seeded auth channel from the same project). The teams are **reused, never deleted**: a soft-deleted channel keeps its project undeletable until the daily sweep, so per-run teams would pile up. Residue per script is therefore one team, not one per run.
- Before the first deploy of a P3 bundle on a stage: `node scripts/apply-team-project-map.mjs <stage> local/team-project-map.<stage>.json` (dry run lists every unmapped app/bundle/channel), then `--execute`. The script refuses while any resource is neither assigned nor deleted; `deleteUnmappedChannels: true` deletes every unassigned channel, live or soft-deleted (the dry run prints the live count; on dev that was 300 rows of smoke residue, 1 live). Rows left unmapped are invisible to the new bundle (safe) but block the contract migration. Then `node scripts/split-projects-per-app.mjs <stage> local/split-projects.<stage>.json [--execute]` to split a catch-all project into one per app and backfill versions (`rules/data.md`).
- team smoke (teams/projects/versions/issues/discussions, todo/17 P2): with the same dev console deploy, `scripts/smoke/team.mjs https://console-dev.yyt.life "$(cat local/deploy/debug-key.dev)"`. Four synthetic members (admin/owner/mate/guest) run the whole membership state machine, the admin override, quotas and the markdown rate limit, then delete the project and team in a `finally` and demote the members back to `pending`. The rate-limit check fires four requests **concurrently**: sequential calls straddle the 500 ms slot behind Lambda latency and pass green without proving anything.
- match smoke: deploy auth, console and match on dev with `--param debugHooks=1`, then `scripts/smoke/match.mjs wss://match-dev.yyt.life "$(cat local/deploy/match-debug-http.dev)" "$(cat local/deploy/debug-key.dev)" https://auth-dev.yyt.life https://console-dev.yyt.life [--slow]` (`--slow` waits for the 1-minute tick to prove the partial timeout). The debug HTTP URL is the stack output `HttpApiUrl` (`aws cloudformation describe-stacks --stack-name yyt-match-dev`); keep it in `local/deploy/`. The script uses Node's global `WebSocket`, no `wscat` needed.
- state smoke: deploy console and auth on dev with `--param debugHooks=1`, `scripts/deploy.sh state dev`, then `scripts/smoke/state.mjs https://doc-dev.yyt.life "$(cat local/deploy/debug-key.dev)" https://auth-dev.yyt.life https://console-dev.yyt.life`. It creates its own auth channel, issues the doc key, exercises the whole CAS surface (428 / 409 with the winning version / create-over-existing / conditional delete) and both credentials' limits, then deletes the channel in a `finally` so a crashed run leaves nothing behind. It is also the only place that proves the _console→state_ wiring: the `docUrl` check fails when `doc-base-url` is missing from SSM.
- topic smoke: deploy auth and console on dev with `--param debugHooks=1`, `scripts/deploy.sh topic dev` (no debug hooks needed — `ttlSec` down to 1s makes expiry testable), then `scripts/smoke/topic.mjs https://topic-dev.yyt.life "$(cat local/deploy/debug-key.dev)" https://auth-dev.yyt.life https://console-dev.yyt.life`.
- Stage-wide SSM keys `github-client-id|secret` are required by the console stack; on dev they are placeholders until the operator registers the GitHub OAuth app (`todo/02-console.md`).
- SPA (team model, 2026-08-26): after `scripts/deploy.sh console dev --param debugHooks=1` and `scripts/deploy-web.sh dev`, open `https://console-dev.yyt.life/ui/`, mint a session with `POST /debug/login` from the browser console (role `member` is enough; `admin` to see the seatless-admin read-only view), then walk: Teams → create team → project → Channels tab → new auth channel (secret shown once) → Versions bump → Issues create/close → Members add/kick (rotation notice) → Settings delete. Check the response headers of `/ui/` carry `content-security-policy` and that the console shows no CSP violation while uploading an artifact (the presigned S3 PUT must be allowed by `connect-src`).
- SPA (dev server): `YYT_DEBUG_KEY="$(cat local/deploy/debug-key.dev)" pnpm --filter @yyt/console-web dev` (proxies to console-dev, which must be deployed with `--param debugHooks=1`), then in the browser console `fetch("/debug/login", {method:"POST", headers:{"content-type":"application/json"}, body: JSON.stringify({login:"dev-admin", githubId:-901, role:"admin"})})` and reload. Walk: channel create (secret shown once) → extend → edit → event draft → proposing → proposal → voting → vote → decided → winner → poster upload → published → sign out → public page. Clean up with the API afterwards (delete channels/tokens/poster, close the event, re-login the synthetic member with `role:"pending"`). Note: the event row itself cannot be deleted (no API); smoke leaves closed events on dev.
- CLI smoke (team model, 2026-08-26): mint a synthetic **member** session with console's `POST /debug/login` (`{login:"cli-smoke", githubId:-1101, role:"member"}`), `POST /tokens` with the cookie + `origin`, then drive the real binary with `YYT_CONFIG=<scratch> yyt login --api https://console-dev.yyt.life --token …` and walk: `team create` → `project create` (must fail: no context) → `team use` → `project create` → `project use` → `channels create --kind auth`, then `--kind match --auth-channel <auth name>` → `channels get <name>` → `catalog app create` → `asset create` + `asset push` → `project version create|bump|link` → `project issue create|close|comment add` → `team discussion create` → `team history`. Clean up in reverse; `project rm`/`team rm` answer `conflict` while the soft-deleted channels exist (until the sweep), so the `cli-smoke-*` team is the same one-team residue the smoke scripts leave. Revoke the token and re-login the member with `role:"pending"`. `yyt smoke match` needs the match stack deployed with `--param debugHooks=1` (callback sink `$(cat local/deploy/match-debug-http.dev)/debug/callback`) and JWTs from auth's `POST /debug/token`; config edits reach match only after its 60s channel cache expires. Full command log: `todo/05-cli.md`.
- dungeon (tslib integration) smoke: needs a Redis ACL user for the sample (`game`×stage, `local/env/game.<stage>.env` with only `REDIS_*`), then `scripts/smoke/dungeon.mjs setup …` (seeds auth/match/topic channels, writes `local/deploy/dungeon.dev.env` + `dungeon-channels.dev.json`) → `examples/sample-dungeon/scripts/deploy.sh ../../local/deploy/dungeon.dev.env dev` → `scripts/smoke/dungeon.mjs run … <CallbackUrl>` → `clean`. Exact commands: `todo/08-game-integration.md`. `run` rewrites the match channel's `callbackUrl` (full-config PATCH), so a channel whose config the match service cached within the last 60 s fails the first match with `failed/callback` — wait a minute and rerun.
- The match smoke's second argument is the match stack's **HTTP** API (`HttpApiUrl` output), not `https://match-dev.yyt.life` — that hostname is the WebSocket API and answers `426 Upgrade Required` to the callback POST, which surfaces as three unrelated-looking failures. Its `debug` function is capped at `reservedConcurrency: 1`, so reading back the recorded callback immediately after the match can lose the slot to the callback itself and answer a bare `{"message":"Service Unavailable"}` (API Gateway's throttle shape, not ours); `--slow` avoids it.
- match protocol gotcha for clients: a `ping` that arrives after the match already formed (ticket consumed) is answered with `{type:"failed", reason:"closed"}`. Smoke clients should not ping right after connecting; connecting alone enqueues the player.
- Console cookie sessions are CSRF fail-closed: any state-changing smoke/curl call that authenticates with the session cookie must also send `origin: <consoleBase>` or it 401s (topic/match smokes learned this after the fail-closed change).
- The match dev stack loses its HTTP API (and the `HttpApiUrl` output) whenever it is deployed without `--param debugHooks=1`; `local/deploy/match-debug-http.dev` then points at a host that no longer resolves (`ENOTFOUND`). Redeploy with the param and rewrite the file from the stack output before blaming the smoke script.
- SPA browser checks: prefer the dev server (`YYT_DEBUG_KEY=… pnpm --filter @yyt/console-web dev`) over pasting the debug key into the deployed page's console — the proxy attaches the key server-side, so the secret never enters the browser or a transcript. Verify the CSP/`x-frame-options` headers of the deployed `/ui/` separately with `curl -D -`. Use a fresh negative `githubId` per synthetic member: `POST /debug/login` upserts by `githubId`, so reusing one silently renames another script's member (`-1102` belongs to the team smoke's owner).
- Names are unique per team (`m0008_team_project_contract`): the same app/bundle/channel name in two teams is allowed, the same name twice in one team is 409 (`duplicate key`), and a soft-deleted channel keeps its name until the sweep purges it.
- console app (Flutter `apps/console-app`, published as catalog app `platform/console`): `cd apps/console-app && flutter analyze && flutter test && flutter build apk --release` (signing from gitignored `android/key.properties`), then upload with the **repo-built** CLI (`cd cli && go build -o yyt ./cmd/yyt`; a stale `~/.local/bin/yyt` predates `--team/--project`): `yyt --team platform --project console catalog artifact upload console build/app/outputs/flutter-apk/app-release.apk --platform android --version <pubspec> --tag build_type=release --tag application_id=life.yyt.console --tag title=잉여톤`, and confirm `GET /catalog/installer/downloads` lists the new version first. The app compares that route with its own `package_info_plus` version at launch (`lib/self_update_check.dart`) and shows the update banner; the only way to see the banner is a device running an older build against a stage whose newest upload is newer, so bump `pubspec.yaml` before every upload. Installing on a device and the self-update from the previous build are manual.
- CLI self-update: `go build -o <scratch>/yyt ./cmd/yyt && <scratch>/yyt self update --check && <scratch>/yyt self update` replaces the scratch copy with the newest GitHub release ; never run it on `~/.local/bin/yyt` while checking an unreleased build, or it downgrades to the release.

## Console app (Flutter) release

- Build: `cd apps/console-app && flutter test && flutter build apk --release` (signing from gitignored `android/key.properties`); publish with the `yyt … catalog artifact upload` line in `apps/console-app/README.md` (`--profile prod` for prod). Re-uploading the same `version` tag needs the old artifact deleted first.
- "배포" for the console app (2026-08-27) means exactly: patch-bump `pubspec.yaml` (both `x.y.z` and `+build`), `flutter analyze && flutter test && flutter build apk --release`, upload to **dev and prod** with the repo-built CLI, confirm `GET /catalog/installer/downloads` on both — the recipe is `apps/console-app/README.md` "Release". `android/key.properties` is gitignored and not in `local/`; if it is missing, the release build silently falls back to the debug key and devices refuse the update (signature mismatch), so check for the file before building.
- Install-flow verification cannot be unit-tested end to end: `waitForInstalledVersion` is exercised with fake `findInstalledVersionFn` + completer signals (`test/install_verification_test.dart`), the lifecycle observer is manual. Manual checklist for a release touching it: cancel at the install prompt, deny unknown-sources then return, background the app during the prompt, back out of "Installing…" on a large APK — each must end the dialog within `returnGrace` (30 s) with the right message.
- Console timestamps are unix **seconds**; a Dart model that feeds them to `fromMillisecondsSinceEpoch` renders 1970 and unit tests with made-up millisecond fixtures will not catch it — assert the decoded `DateTime`.
- The installed build finds its own update through the app list route it was built with; never remove a list route until every device has moved to a build that uses the replacement (todo/17 P10).
