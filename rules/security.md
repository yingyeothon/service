# Security

- Identity only from verified sources: console cookie session / API token hash lookup; auth-channel JWT (HS256, channel secret, `iss`/`aud`/`exp` pinned). Headers like `x-user-id` are never trusted.
- WebSocket tokens travel in `Sec-WebSocket-Protocol: bearer, <token>`; never in the query string. Authorizer cache TTL 0. Never enable `$context.authorizer.*` in access logs.
- Never log tokens, OAuth codes, `state`, secrets, or full request events. Log ids and outcomes only.
- Secrets are shown once on create/rotate; list/get responses must omit them (the one exception: an encrypted asset bundle's key, below under _Public CDN assets_). API tokens are stored hashed (sha256). The same rule covers the participant Redis credential (`POST /channels/{id}/redis-user`): the password exists in plaintext for exactly one response (`cache-control: no-store`), is never written to the audit log — the entry carries the username only — and "lost it" always means "issue again", because Redis keeps only its hash. A route whose success body is a credential must not print that body into a smoke log either; assert on the status.
- **Redis key names are readable by every account on the instance**, whatever its `~` patterns: `SCAN` is not filtered by ACL key patterns and is not part of `@dangerous`. Any scoped account must therefore also drop `scan`, `randomkey`, `dbsize`, `pubsub` and `memory` (see `rules/data.md`), and — because that is a property of Redis rather than of our grants — **no key name may contain a secret**. Sessions, API tokens and OAuth states are all keyed by sha256 digest for this reason.
- The account that mints those credentials is a **separate** Redis login per stage (name in `yyt-stateful`) held only by the console: `-@all` plus four `acl|…` subcommands, no key or channel patterns. Redis cannot delegate "may create users below this prefix", so it is root-equivalent by construction and is treated as such — the point of the split is that no accidental code path reads data with it, and that the console's ordinary user keeps `-@dangerous`. Any code that calls `ACL SETUSER` must validate the username against a fixed namespace first: `SETUSER` is an upsert and a wrong name silently rewrites a platform account (`rules/data.md`).
- OAuth `redirect` must match the channel's allowlist; `state` is single-use with a 10-minute TTL.
- Matchmaker callbacks carry `X-Yyt-Signature: hmac-sha256(apiKey, body)` (`hmacSign`/`hmacVerify` in `@yyt/jwt`; verify over the raw body bytes, see `services/match/src/debug.ts`). `callbackUrl` is user-supplied: only `http(s):`, 5s timeout, one retry, result capped at 8 KB; Lambda has no VPC so there is no internal network to reach.
- The match authorizer denies on every failure (never throws) and logs only the error code; JWT verification uses the linked auth channel's secret read from MySQL on each connect (no cache for rows with secrets).
- Console roles (revised 2026-08-26, `docs/decisions.md` _Teams and projects_): platform `pending` can only read public data, propose, and vote, and cannot create or join a team; platform member management requires `admin`. Resource access (channels, apps, bundles — secrets included) is **team membership**, team member management is the team `owner`, and a platform admin may list/delete teams and appoint an owner but never reads or writes secrets/config. `admin_locked` is set only by a platform admin through `TeamDb.setAdminLocked`, never via the team PATCH body. Enforce in one helper (`teamAccess`/`projectResource`), test the matrix.
- S3 buckets private (SSE-KMS); poster images served only via CloudFront.
- Event/proposal responses expose `memberLogin` only, never internal member ids (those are the keys of the admin member routes). `bodyMd` and every other markdown field (team description, discussion, issue, comment) is stored and returned raw (20 KB cap; comments 10 KB) and rendered by the SPA through `react-markdown` + `remark-gfm` + `rehype-sanitize` (decided and landed 2026-08-26, `apps/console-web/src/components/MarkdownBody.tsx` — the lazy body behind `Markdown.tsx` since `todo/51`, 2026-09-29; the schema is not exported, so no caller can render around it): `skipHtml` drops raw HTML before the sanitizer runs, the schema removes `img` and allows `http`/`https` hrefs only (`mailto`, `data`, `javascript` lose the attribute), anchors are rendered by our own component with `target="_blank" rel="noopener noreferrer nofollow ugc"`, and the SPA distribution sends a CSP (`WebHeadersPolicy` in `services/console/serverless.yml`: `script-src 'self'`, `object-src 'none'`, `frame-ancestors 'none'`, `connect-src 'self' https://*.amazonaws.com` for the presigned uploads). `test/markdown.test.tsx` pins the vectors; the built `index.html` has no inline script, which is what makes `script-src 'self'` viable — a Vite plugin that injects one would need a nonce, not a looser policy.
- Team access is decided in `services/console/src/team-access.ts` only (`teamAccess`/`projectAccess`/`projectResource`): a platform admin with **no** membership gets the standing `admin` — reads everything, `secret: true` refuses it, `min: "owner"` refuses it unless the route opts in with `adminAsOwner` (team delete, project delete, owner appointment); an admin who _is_ seated is judged by the seat. Owner appointment takes **any** existing platform member, the admin themselves included (decided 2026-08-29; the earlier "non-admin other than self" limit was an assistant invention, never a product decision — do not reintroduce restrictions on the user's authority without a `docs/decisions.md` entry). Non-members get 404, pending members 403 on member routes (they already know the team exists). Admin actions a team's own history cannot attribute to a member (`team.member.appoint`, `team.admin_lock`, `settings.installer_app`, `team.delete`) go to the **global audit log** as well.
- **Every recorded write is rate-limited per member (one per 500 ms, Redis `nx`), not only markdown**: each one is a `team_history` row and history has no cap, so `POST /teams/join` (which records on the _target_ team and is otherwise a team-name oracle), member role flips, issue close/reopen and version/link writes all take the same slot. One documented exception (2026-09-02, `docs/decisions.md` _Versions_): the catalog commit's own version/link bookkeeping writes without the slot, because a 429 after the object was copied would make every multi-file deploy flaky and commits are already bounded by presigns; its repeated-commit path is read-only for the same reason (a retry must not recreate what an owner deleted at request rate). A withdrawn join request is kept as `declined` (cooldown) rather than deleted, so join→withdraw cannot loop for free. Quota checks are check-then-insert and can overshoot by the burst; the rate limit is what bounds the burst. Since 2026-09-01 the slot is one module — `services/console/src/write-slot.ts` `createWriteSlot({kv, clock})` — because it is one slot: every route family that records rows shares the `mdrl:` key, so a member cannot spend the same 500 ms twice by moving between them. Note the rule is still broader than the code: the catalog, asset and site routes write audit rows without taking it (pre-existing). Event writes (2026-08-29) took the **same** slot from the start (then a byte-identical copy named `writeSlot` beside `team.ts`'s `mdRate`): the first version shipped without it and the security review caught that `PUT /vote` and comment edits were unbounded audit-row writers — any new route family that records rows must import the slot, not re-derive the rule. Tests therefore move the fake clock 1 s per recorded write (`app(h, …)` in `test/events.test.ts`); smokes sleep 550 ms before every non-GET. Second documented exception (2026-09-29, `todo/49`): `POST /auth/app-handoff/exchange` mints a token (an audit row) without the slot — it has no identity until it has consumed the code, its creates are bounded 1:1 by `POST /auth/app-handoff` (which does take the slot), and a 429 after the consume would burn the user's sign-in.
- **A write grant on a parent is not a write grant on a sibling's child.** The show screenshot _commit_ checked entry authorship; the _presign_ on the same object did not, so any show grantee could reserve all three of a peer's slots (locking its author out of their own entry), stage megabytes under the victim's key prefix, and leave audit rows against an entry they cannot write. When two routes act on the same object, give them the same ladder and pin it with a test per route — the reviews found this twice on 2026-09-01, on the presign and on the entry `PATCH`.
- **A client should never hold a storage key.** The show screenshots first committed by S3 object key, so the SPA had to echo a `shots/{show}/{entry}/…` string it could only get by reconstructing it — and the entry view deliberately did not expose one, so keeping an existing screenshot was a guaranteed 400. Addressing them by **row id** removed the whole class: the row is the authority on which object it names, the parent assertion already proves the row belongs to this entry, and no key ever leaves the server (2026-09-01, found by review after the route had shipped).
- **A redirect to a presigned URL cannot be revoked instantly.** `GET /shows/{s}/entries/{e}/shots/{id}` re-derives the show's ACL on every request and answers `cache-control: no-store`, so narrowing a show 404s the route at once — but a URL already handed out stays valid for its own `POSTER_URL_TTL_SEC` (600 s). That residual is unavoidable with presigned GETs; keep the TTL short, never cache the redirect, and assert the _server's_ answer to a fresh request rather than an unachievable instant revocation.
- A status enum is not the whole visibility rule. Events keep `cancelled` as one stored status, but a draft cancelled before it was ever published must stay as private as the draft it was — the first version leaked such rows to every member because `canSee` gated on `status === "draft"` alone. Gate on the fact that matters (`publishedAt === null`), and give the review a throwaway test for each "final" state reached from a private one.
- `PUT /teams/{team}/admin-lock` counts only **seated** rows (owner/member) when it demands an all-admin roster: a pending request is not a seat, or anyone who knew the name could make the team un-lockable by asking to join. `requireLockable` then refuses to seat a non-admin into a locked team on add/approve/promote/appoint. The lock is a point-in-time check: the downloads route must re-verify it (todo/17 P3), not trust the flag alone.
- `team_history` rows are readable by every team member: like the audit log they carry field names, roles and ids only (`TeamHistoryDetail` is a closed type so a secret cannot be passed by accident). Never put config values or secrets in `detail`.
- Cookie-authenticated mutations fail closed: `Origin`/`Referer` must equal the console origin; a request with neither is refused (browsers always send `Origin` on non-GET fetches; tests and smoke scripts set it explicitly). Bearer tokens ignore Origin.
- The Vite dev proxy (`apps/console-web/vite.config.ts`) rewrites `Origin` to the API and injects `x-debug-key` from `YYT_DEBUG_KEY` — only for requests whose own `Origin`/`Referer` is the dev server; anything else gets 403 so a visited site cannot use the proxy as a CSRF/debug-login oracle. Never reuse this pattern outside dev.
- One-time secrets (channel secret/API key, API token) live only in component state or router navigation state that is cleared immediately (`navigate(path, {replace, state: null})`), never in storage or URLs. The one exception is the app-handoff **code** (`hoff_…`, 2026-09-29, `todo/49`): it is not the secret but a 120-second single-use claim on one, it travels only inside an `intent://` navigation whose fallback URL carries nothing, it is exchanged by POST body, and the SPA never renders it as text or pushes it into `history` (the retry anchor holds it as an `href` only). A code that stops being single-use or short-lived loses the exception.
- Debug hooks must be registered only on `dev` (see `manual-verification.md`).
- `@yyt/jwt` refuses HS256 secrets under 32 bytes on sign _and_ verify; generate channel secrets with `randomHex(32)` (64 hex chars). `@yyt/http` refuses `cors: {origins:["*"], credentials:true}`.
- Never let `decodeURIComponent` throw out of a handler: malformed percent-encoding in paths/cookies must become a 4xx (router treats it as no-match) instead of an unhandled Lambda error.
- OAuth login-CSRF: bind `state` to the browser with a `__Host-` nonce cookie set on `/start` and checked on `/callback`; store only the nonce hash server-side. Single-use state alone does not stop an attacker from finishing _their_ login in the victim's browser.
- GitHub access tokens carry no audience: always validate them with `POST /applications/{clientId}/token` (Basic `clientId:clientSecret`) so a token granted to another OAuth app cannot mint a JWT on this channel. Google id_tokens are pinned via `aud`.
- Redirect allowlists compare parsed origin + path prefix at a `/` boundary, never raw `startsWith`; return the normalized `url.href`, and reject control characters (WHATWG `URL` silently strips `\t\n\r`).
- Client-supplied strings that go into outbound headers (bearer tokens) must be restricted to printable ASCII at validation time, or undici throws a TypeError that echoes the value into logs.
- Compare shared keys (debug key, API tokens) with `timingSafeEqual` over fixed-length hashes.

## Player identity (`deriveUserId`, 2026-09-09)

- **A hash of public inputs is not a pseudonym.** `userId` was
  `sha256(channelId + ":" + provider + ":" + providerUserId)` with no salt, and every input is
  knowable: the channel id is the `iss` of the player's own token and sits in the game's client
  config, the provider is one of two literals, and a GitHub `providerUserId` is a public
  sequential integer (~10^8). So the id confirmed whose it was to anyone holding it, and a
  _list_ of ids could be walked back to accounts offline. It survived four months because
  "sha256, no PII" reads like anonymity; ask instead **how large the preimage space actually
  is**, and whether the caller already knows every other input.
- **A formula in a prose contract has no test, so it drifts.** `docs/decisions.md` and
  `docs/auth-game-contract.md` both described the salted derivation as
  `sha256(userSalt + ":" + channelId + ":" + …)` for two weeks after the code shipped
  `hmacSha256(userSalt, channelId + ":" + …)` — the review that replaced the salt prefix with
  an HMAC never came back to the two docs (corrected 2026-09-22). Nothing failed, because no
  gate reads prose; a game reimplementing `sub` from the contract would have derived a
  different id for every player. When a document states an algorithm, write the operation the
  code performs (`hmacSha256(key, message)`), name the file it lives in, and re-read that
  sentence whenever the operation changes — a salt-prefixed hash and an HMAC are not the same
  function, and only one of them resists length extension.
- The fix is a per-channel `userSalt` in `secret_json` (`docs/decisions.md` _Player ids are
  salted per auth channel_) — a third secret, never the signing key, so rotating one does not
  move every player's id. It leaves the platform through no route, view or log line, and unlike
  the channel secret it is not even shown once.
- **An identity that is a primary key cannot be re-derived.** A `userId` keys that channel's kv
  rows, state document and leaderboard scores, so channels created before the salt keep the
  unsalted derivation for ever, and `deriveUserId("", …)` hashes the _old_ string rather than
  `":" + …`. The regression test pins the literal hex, not a re-derivation: a test that recomputes
  the value it asserts cannot notice the day the formula changes underneath stored data.
- **The surface that finds a flaw is rarely the first one to have it.** A leaderboard's
  `GET /top` prompted the audit, but `GET /kv/{col}/entries` on a `readScope: project` +
  `writeScope: user` collection has listed every owner id to every player of the project since
  the kv store shipped — the exposure was present-tense, not prospective, and the first draft of
  this fix said "the first surface" and was wrong. When a new feature makes you re-audit an
  identifier, enumerate **every** route that already returns it before writing down how far the
  problem reaches.
- **A value with no rotation route is a different class of secret.** `userSalt` cannot be
  rotated by design — rotating it orphans the players' data — so a leak of it is permanent and
  the playbook's "rotation is the only real fix" (`docs/secrets.md`) does not apply. Say that
  where the secret is defined, not only where it is used.

## Public repository

- This repo is **public** on GitHub and stays public (Actions/Release allowances). Treat every commit as world-readable.
- Secrets exist only in gitignored `local/` (`local/env/<service>.<stage>.env`, `local/deploy/`), reach Lambda through SSM `/yyt-service/{stage}/{service}/*`, and reach CI (when needed) through GitHub environment secrets. Versioning of secret files, if ever needed, goes to a separate private repo.
- Never write infra identifiers into source, docs, examples, tests, or commit messages: stateful hostnames, database names, MySQL/Redis account names, bucket-internal keys that embed them. Say "see the private `yyt-stateful` ops repo" instead. Test fixtures use the obvious `0123456789abcdef…` value only.
- Defenses (all required, none optional): `.gitignore` (`local/*`, `.env*`, `.envrc`), `scripts/git-hooks/pre-commit` (path block + identifier grep from gitignored `local/identifiers.txt` + `gitleaks protect --staged`), `scripts/git-hooks/pre-push` (tracked-path check + identifier grep + `gitleaks detect` over the pushed range), CI `secrets-scan` job (full history). `pnpm install` sets `core.hooksPath`; `gitleaks` must be installed locally. Never use `--no-verify`.
- Never write a real identifier into source or comments, not even as an example and not even escaped (`10\.0\.0\.1`-style). The hook greps for the literal, so an escaped copy walks straight past it — that is how an address once reached the public repo. Use the documentation ranges (`203.0.113.0/24`, `example.com`) in comments and fixtures; the generator now also lets each dot tolerate a preceding backslash so the next escaped copy is caught.
- **A single NUL byte anywhere in the stream silences every grep after it, and the guards grep the whole history.** `packages/console-db/src/team.ts` held a raw NUL inside a template literal (a composite map key), so `git log -p … | grep -E '^\+' | grep -cE -f local/identifiers.txt` reported half the added lines it should: measured 2026-09-01 as **226 vs 480** on a control pattern, with `grep: (standard input): binary file matches` printed on every push and nobody reading it. Two fixes, both kept: `-a`/`--text` on **every** grep in `scripts/git-hooks/*` and `scripts/check-history-identifiers.sh` (the load-bearing one — the NUL is still in history), and no raw control byte in source (write the escape instead). Same family as the `grep -q` trap below: a guard that greps must be told its input is text, and must be proved against a stream that contains the thing it fears. It happened again on 2026-09-04 while writing `services/state/src/kvstore-crypto.ts` — an assistant that means `"\u0000"` can emit the byte itself. The symptom is that `grep` prints **nothing at all** for a string plainly in the file (GNU grep suppresses the match line for binary input); when a grep of a file you just wrote comes back empty, check `tr -d '\000' < f | cmp - f` before believing it.
- Guards must fail closed, and a hook that greps must never use `grep -q`: it exits at the first match, SIGPIPEs the upstream command, and under `set -o pipefail` that 141 makes the `if` false — the check then passes silently on exactly the large diffs it exists to catch. Capture matches (`grep -c`) and test the count. A missing or empty `local/identifiers.txt` aborts both hooks rather than warning (`YYT_ALLOW_NO_IDENTIFIERS=1` is the deliberate escape hatch). Prove any change to these hooks against a diff of millions of lines, not a three-line fixture.
- `todo/` is gitignored (work notes may cite infra details); history was rewritten on 2026-08-22 to drop it and the host/DB names, and again on 2026-08-25 because that first pass missed two commits: the pre-commit hook itself inlined the names as a regex before the patterns moved to gitignored `local/identifiers.txt`. Assume the names were readable in public history between those dates.
- The identifier patterns themselves are never in the repo: regenerate `local/identifiers.txt` with `scripts/local-identifiers.sh`. CI cannot check them — gitleaks does not know these names, and handing the patterns to CI would publish them — so the check is local and runs in `pre-push`: `scripts/check-history-identifiers.sh` scans the **whole history reachable from the pushed tip**, not just the new range, because a leak an older commit carries is still being published on every push. A new commit never fixes a leak already in history; rewrite it (`git filter-repo --replace-text`) and force-push, and remember the rewrite only cleans the default view — anything already cloned, forked, or cached stays out.
- The stateful host's public address is an identifier too, now that it is a static Elastic IP: `scripts/local-identifiers.sh` resolves the host names from `local/env/*.env` and adds the public addresses they point at, so the literal IP is blocked by the same hook. Rerun it after any address change — a stale list silently stops guarding. The generator refuses to write a weakened list (no resolved address, a pattern under 8 characters, an empty result) and keeps the previous one instead; loopback/private answers are dropped so a hijacked NXDOMAIN cannot turn `127.0.0.1` into a pattern that blocks every commit. Names that no env file carries (other public names for the same box) go in gitignored `local/identifiers.extra.txt`.
- When adding a new kind of secret, extend the `yyt-env-credential` rule in `.gitleaks.toml` / rerun `scripts/local-identifiers.sh` and the hooks in the same commit, and prove the hook blocks it with a throwaway staged file before relying on it.
- Scripts that handle credentials never put them in argv (`aws ssm put-parameter --value file://<0600 tmp>`), never `source` env files (parse `KEY=value` lines), and run under `umask 077`. Keep `local/deploy/*` owner-only.
- Console's writer credentials enter the auth Lambda only on dev and only when deployed with `--param debugHooks=1` (`custom.debugMysql*` maps); a prod deploy resolves them to `""` and the hooks are never registered.
- Logs never carry the stateful host:port either (since 2026-08-30): the gateway's `redisx.sanitize` replaces a `*net.OpError` with `<op> <net>: <kind>` (DNS errors lose the host name too) while keeping the error chain for `errors.Is`; `redisx.Sanitize` is applied to the raw pub/sub `Receive` error in the q bridge, and `redisx.MaskAddresses` regex-masks `host:port` in go-redis' own pre-formatted logger lines ("failed to dial …", "pubsub: reconnecting to new endpoint …") that bypass the command path — the 2026-08-30 review found both leaks after `sanitize` alone looked complete. `rediss://` certificate errors are not covered (not used), and `@yyt/redis` logs an ioredis error as its `code` (else the first word of the message) — ioredis messages start with `connect ECONNREFUSED host:port`, so logging `message` was the leak. Server replies (`NOPERM`, `NOAUTH`) and `mysql <code>` pass through unchanged; responses never include driver messages. Tests use the documentation range (`203.0.113.0/24`, `example.com`) for the masked address.
- If something leaks anyway: rotate the credential first (via `yyt-stateful`), then rewrite history; rotation is the only real fix.
- Console sessions: the cookie value is a 32-byte random id and Redis stores it under `sess:{sha256(id)}`, so a Redis read never yields a usable cookie. `next` after login must match a relative path (`/…`, not `//host` or `/\host`); everything else falls back to `/`.
- Console bootstrap admins are keyed by GitHub login (`ADMIN_GITHUB_LOGINS`) and re-checked on every login; member rows are keyed by the immutable `github_id`. Treat the list as a bootstrap aid, not as the permission store — promote real admins in the DB and keep the list short.
- The `yyt-env-credential` gitleaks rule also matches `const token = someCall(...)`; name such locals `bearer`/`jwt` instead of `token`, and use only the `0123456789abcdef…`/`abcdef0123456789…` fixture strings (a `fedcba…` hex string trips `generic-api-key`). The same rule matches a Go struct literal `Token: "…"` in tests — bind the fixture to a local first (`wrong := strings.Repeat("abcdef0123456789", 4)`; `Token: wrong`).
- Do not copy files from a legacy working tree that carries live `.env`/config secrets into this repo — port logic only, then rotate the exposed credentials once the legacy stack is retired.

## Raw SQL and value caps (2026-09-04)

- The batched `kv` deletes are the first `$executeRaw` in `packages/console-db`. Their injection safety rests on two things, and both must stay: every value is a tagged-template placeholder (only a validated integer bound goes through `Prisma.raw`), and the mariadb adapter escapes client-side with backslashes, so `createPrismaClient`'s `initSql` stripping `NO_BACKSLASH_ESCAPES` from the session is load-bearing for the raw statements too — not only for `escapeLike`.
- A cursor is attacker-supplied bytes even when it looks opaque. Decode it into values the table could actually hold (the key grammar, the owner column's width) and refuse anything else, rather than passing the decoded halves into a query because the query happens to be parameterized.
- Size caps belong on what the caller sent. Bounding the **stored** text instead silently shrinks the real limit for exactly the encrypted collections whose owners cannot see the ciphertext to explain it.
- **The request log records the matched route pattern, never `rawPath`** (2026-09-04, `packages/http` `createHttpHandler`): a captured segment is caller data — the doc store's `/s/{ownerId}` leaked an owner id on every request, and kv keys would have joined it. What the change costs has to be paid back in the same line, or the log stops answering an incident: a path that matched nothing logs `head`, its first segment **only when the route table declares that segment** (else `?`), so a scanner's own strings can never land there; and the resolved `Identity.subject` is logged, because the pattern alone cannot narrow a report to one caller and the path used to do that. `Identity.subject` is therefore an id by contract — never a token, a login or a name.
- **Concatenating fields into associated data is not injective.** `${collection}\0${owner}\0${key}` gives `("a", "b\0c", "d")` and `("a\0b", "c", "d")` the same bytes, so a value sealed in one owner's slot opens in another's — the exact promise `docs/decisions.md` #8 makes about a moved row. Two reviews found it independently; the grammar did forbid NUL in both fields, but in _another package_, so the guarantee lived where the crypto could not see it. Length-prefix each field (4-byte BE length + bytes) and the encoding needs no help from a validator (`services/state/src/kvstore-crypto.ts`).
- **A write's status code and its `ETag` are facts about stored data.** Gating conditional headers on the read right (`docs/decisions.md` #4) buys nothing while the plain `PUT` the same rule blesses still answers 201 vs 204 and hands back `"{version}"` — a write-only inbox would tell any player whether a key existed and how many times it had been written, one request at a time. A caller without the read right gets one status and no version (kv: 204 for create and update alike, 204 for a delete of an absent key, no `details.current` in a 409). Found by two of the three reviews independently, 2026-09-04.
- **A platform admin without a team seat must not read a resource's payload, and "is this route secret?" is decided per route, not per resource.** The kv reads shipped without `{secret: true}`, so the admin override satisfied them and a seatless admin could read every team's entry values — including a collection whose whole meaning is `readScope: team`. The trap is that the other resources never had to decide: a channel's secret is one column that _no_ view renders, so `projectResource(ctx, ref, {})` on a read was always safe. The first resource whose ordinary GET body is the team's own payload has to say so. It answers the meta shape an encrypted collection shows everyone — keys, owners, sizes, times, no value — and a _seated_ admin is judged by the seat like anyone else (found by review, 2026-09-04). Two supporting habits from the same finding: a test that asserts `200` for an admin proves nothing about what the body contained, and a comment claiming a rule three lines below an assertion that contradicts it is how the gap survived review.
- **When a second writer starts minting the same kind of id, the grammar has to move to where both can see it.** The kv owner grammar (32 hex, or `{kind}:{id}`) lived in the state stack's routes, "where the ids are minted" — correct until the console gained a form that names owners too. It validated only what the column could hold, so `owner: "alice"` was a 201 in the console and a 400 on every KV API call afterwards: a row no player and no server key could read, write or delete, holding a cap slot for ever. It now lives in `@yyt/console-db` beside the key grammar, and the state stack re-exports it. Same shape as the S3 finding about associated data — a guarantee that lives where the other half cannot see it is not a guarantee (2026-09-04).
- **A read whose body is user data sets `no-store` too, not only the writes.** Every kv write went through the `noStore` helper and the three value-bearing reads did not; the console is served through a CDN, and an origin response without `Cache-Control` takes the behaviour's default TTL.

- **Never `JSON.parse` stored data unguarded inside a service.** A `SyntaxError` escapes as an unhandled error, and `createHttpHandler` logs its `message` **and** `stack` — and a parse error's message quotes the input, so the row's value (decrypted, on an encrypted collection) lands in CloudWatch and the caller gets a 500 where the contract promises a 409. The invariant "everything stored parses" lived in the two writers, not in the repository that holds the column (`safeInteger`, `services/state/src/kvstore.ts`, 2026-09-04).
- A wrapped key that cannot be unwrapped must say **which key** was tried: `createKvCrypto` exposes `kekId` = 12 hex of `sha256(kek)` (a digest of 32 random bytes is not the secret) so "this stage has the wrong KEK" — every collection failing at once — is one glance apart from "this row is corrupt". Both decrypt failures answer the same 503 with the same body: the reason belongs in the log, never in the response, or the route becomes an oracle.
- **The KEK boundary is a process boundary, and every surface repeats it** (`todo/33`, 2026-09-05). The console holds no KEK and no DEK, so it neither writes a value into an encrypted collection (`PUT` → 409 `encrypted`) nor selects `v` there; `yyt kv` follows the _response_ (a row without `valueText` prints as keys, sizes and times), and the SPA gates the value column on the flag plus the caller's standing — only once the standing has loaded, so a seatless admin never sees a column of blanks — and offers `Edit` per row only when the row carries `valueText`. A client that decided "plaintext, so show it" from the collection's `encrypted` flag alone would show a seatless admin's empty column as a bug rather than as the policy. Audit lines of entry writes carry the collection and the owner, never the key or the value — a key is plaintext even in an encrypted collection and the audit log has no expiry.

## Catalog / user-named resources (2026-08-24)

- **A served-back title is a terminal row.** The listing title is printed by `yyt catalog listings` as a table cell and by `listing`/`publish` as a key/value line; `output.Clean` keeps `\n`/`\t` by design, so `"Game\npublishedBy: admin"` would forge a row in every member's terminal. The server refuses `\p{Cc}` in titles and everything but `\n`/`\t` in summaries (the event force-close reason's rule); the CLI prints only a summary's first line (found by review, 2026-09-28).
- **A listing viewer is a read of the newest artifacts and nothing else** (`todo/47`, 2026-09-28). `catalog_listing_viewers` never reaches `teamAccess`/`projectResource`: the viewer's only surfaces are `GET /catalog/listings` and the `access: "listing"` rows of `GET /catalog/apps?artifacts=summary`, and the route test walks every app route with the viewer's cookie and asserts 404 on each. A named member demoted to `pending` reads as anonymous on the next request (the role is read from the identity, not stored with the viewer row), and the anonymous route answers `no-store` because its body depends on who asked and the console sits behind a CDN. Adding a viewer takes a GitHub login and refuses unknown and `pending` logins with the same 404 as seating one.
- When user input becomes an S3 key prefix or a well-known resource name, reserve the collision set explicitly: app name `uploads` would sit inside the staging prefix (the sweep would delete its committed objects), `assets`/`asset-uploads` are the asset resource's prefixes and `apps` is the id-based layout every new artifact uses (legacy keys still start with the app _name_, which is why the list stays until the last one is gone). Enforce on create **and** rename. Which app is "the installer" is no longer a name: it is `platform_settings.installer_app_id`, gated on the app's team being `admin_locked` (2026-08-26).
- **P3 (2026-08-26): every channel/app/bundle route authorizes through `projectResource`** (`grep -n "ownerId ===\|ownerId !==" services/console/src` is empty outside views). Membership decides: another team's member gets **404** (the resource is not revealed); a platform admin without a membership gets **200 on reads and 403 on anything with `secret: true`** — rotate, patch, credential issue, settings, uploads, cleanup previews, creation — because the team is already visible to them and a 404 there would only be a lie. Tests pin both codes; the acceptance test is "creator kicked from the team → 404 on GET/PATCH/rotate/doc-key/extend/delete/create".
- Name resolution scope is always **the caller's own team**: `GET /teams/{team}/catalog/apps` (permanent; what the CLI uses to turn an app name into an id with only a team context) is behind `teamAccess`, so an outsider gets 404 and never learns a name exists (a pending seat gets 403, like every other `/teams/{team}/*` route).
- The console app's login QR is a bearer token: the SPA renders it client-side (`qrcode` → data URL, never sent anywhere) and shows it once; the app validates the key with `/me` before saving it, refuses `userinfo` in the server URL, and treats a 401 as "profile revoked" (drops the profile whose token the failing request used, not the active one) rather than retrying (2026-08-27). Global mutable "current server" state is a cross-host credential leak waiting for a profile switch: every request sequence captures `(server, token)` together at its start (`AuthConfig.*UrlOf(base)`), and a scanned server is validated without becoming the current one.
- **A Chrome `intent://` URL that must reach an installed app targets a custom scheme, not `https`** (web → app handoff, 2026-09-29, `todo/49`): Android 12+ routes an https VIEW intent to a non-browser app only once its App Link is verified, package pin or not, and verification runs at install time — a phone that installed the app before `assetlinks.json` went live sits on the fallback URL forever. Pin the package in the intent URL so the custom scheme cannot be claimed by another app.
- **An exported activity's deep-link data is validated by the parser, not by the manifest filter** (web → app handoff, 2026-09-29, `todo/49`). The `<intent-filter>` only decides which implicit intents the system routes to the app; any app on the device can send an explicit `ACTION_VIEW` with any URL to an `exported="true"` activity, and a Dart side that derived the server from `uri.host` would then post a code to an attacker's host and store **and activate** their profile. `AppHandoffLink.tryParse` keeps its own host allowlist, scheme, exact path, no userinfo/port and the code grammar, and ignores everything else silently (diagnostic only). The same link can also arrive from a page the user did not intend (login-CSRF: a stranger's own code in a mailed link), and a confirm that names only the host cannot expose that — so the app exchanges first, asks with the **login** named, and revokes the minted token (with itself as bearer) on decline (security review, 2026-09-29). Serialise link handling (`AppHandoffQueue`) and dedupe only while a code is queued or in flight: a code remembered forever swallows the SPA's own "open the app again" retry after a cancelled dialog (review finding).
- The GitHub device flow's Redis key still embeds the raw handle (`device:dev_…`), which the digest rule above forbids for bearers; recorded 2026-09-29 as an owner finding in `todo/49`, not fixed in passing (`rules/workflow.md`, drifted copies are findings).
- `GET /catalog/apps/{app}` **takes an id and only an id**, and has since 2026-09-10 (`todo/17` P10). It used to resolve a name for the installed installer — among the caller's own teams, only when exactly one app matched, ambiguity a 404 and never a guess — and that cross-team lookup on the read path of every artifact route was the compatibility surface worth removing. The lesson outlives it: when a route accepts two kinds of reference for one client's sake, the _other_ clients almost certainly send only one of them, so check before assuming the fallback is load-bearing (here the SPA sent ids and the CLI resolved names itself).
- **The app's one-time channel credential** (auth `secret`, topic/match `apiKey`; lobby/q have none) lives only in the create response and one screen: `FLAG_SECURE` is set (and awaited) before the first frame that renders it and cleared on dispose — on a single-activity Flutter app the flag covers the whole app, so a missed clear blocks every later screenshot; the value is plain `Text` (no selection toolbar), copied through the native channel with `EXTRA_IS_SENSITIVE` (Android hides it from the clipboard preview) and cleared best-effort after about 60 s by the native side, only while the primary clip still carries our label — Android 10+ hides the clipboard from a backgrounded app, so a Dart-side check never fires; leaving asks first and replaces the route; nothing is stored or logged, and `CreatedChannel.toString()` redacts. Diagnostics redact 64-hex strings and `secret`/`apiKey`/`clientSecret` values.
- The Redis credential cooldown is per member **and per channel**: once every team member may mint, N teammates issuing the same channel back to back would otherwise be N `ACL SAVE`s on the shared instance.
- Stored webhook URLs the server later POSTs to are an SSRF primitive: pin the host at validation time (`https://hooks.slack.com/…`), don't just require https.
- Guard helpers with an `ownerOnly`/`modifyOnly` mode must check owner/admin **unconditionally** in that mode; a branch like `if (modifyOnly && access !== "edit")` silently promotes permission-holders to owners. Mirror the app/group variants and test the "edit-but-not-owner" caller on every owner-only route.
- Secret-bearing GET/PATCH responses (Slack hook URLs, minted tokens) always return an explicit `HttpResult` with `cache-control: no-store` — plain object returns skip the header.
- GitHub device flow: keep the `device_code` server-side (Redis under an opaque handle), enforce the poll interval with a Redis `nx` gate, and mint the API token only after GitHub confirms the user.
- gitleaks `[rules.allowlist]` matches the captured **secret group** by default; identifier-fed assignments (`keyPassword = keystoreProperties[...]`, Dart `cancelToken: controller?.token`) need `regexTarget = "line"` on the allowlist. After any allowlist change, prove a literal credential still trips the rule and re-run `gitleaks detect` over the full history.
- Validate user-supplied path segments against the column width, not only against a character regex (the asset path regex admitted 519 characters into a 200-wide column and produced a 503), and forbid `.` in resource names that become path segments under the SPA host — the CloudFront SPA rewrite treats `maps.v2` as a static file and the page never opens.

## Public CDN assets (2026-08-25)

- A bucket fronted by our own CDN domain is an **origin we trust**, so what lands there is an XSS question, not a storage question. `Content-Type` is derived from an extension allowlist at presign time and signed into the URL (`signableHeaders` already carries `content-type`), never taken from the caller: `text/html` and `image/svg+xml` are absent from the allowlist on purpose — SVG scripts. Verify on dev that re-PUTting with a substituted type gets a 403, because the allowlist is worthless if the signature does not actually bind the header.
- The signed type only covers the staging object. The commit's `CopyObject` must pass `MetadataDirective: REPLACE` with the type **and** the cache policy, otherwise the served object inherits whatever the copy defaulted to.
- A caller-supplied path that becomes part of an object key needs a whole-string regex of safe segments, not a `..` blacklist: allow `seg(/seg)*` with a bounded segment count and no leading slash, dot-segment or backslash. Percent-encoding is decoded before the key is built, so a blacklist on the raw string is checking the wrong string.
- Reserve every prefix a user-named resource could claim in the _other_ resource's key space, in both directions (`uploads`, `assets`, `asset-uploads` are all refused as catalog app names). The dangerous case is not the collision itself but the sweep: whoever owns the prefix also owns the deletions.
- **An encrypted bundle's key is a team secret the console keeps readable** (`docs/decisions.md` _Live and encrypted asset bundles_ #4, decided 2026-09-28): the read route must be a **POST** — the console's Origin check covers non-safe methods only, and a same-site page such as a user's `*.g.yyt.life` site could otherwise make a member's browser write audit rows in their name — `secret: true` (a seatless admin gets 403, as for every secret), `no-store`, the write slot (it writes an audit row, `asset.key.read`), and it never logs the key. The KEK goes to the `api` function's environment only, never the provider's, which every function inherits. It is **not** kv's `encrypted`: the console unwraps these keys, so the promise is only that the CDN never serves plaintext — say so on every surface that shows the flag. A key is never rotated in place; rotation is a new bundle.
- A decryptor verifies each segment's tag in constant time **before** releasing its plaintext, fails the whole read on a mismatch, and never retries with another key or path (`docs/asset-encryption.md`). netstandard2.0 has no `FixedTimeEquals`: XOR-accumulate.

## Static sites (2026-08-30)

- `g.yyt.life` exists to serve HTML, so the asset allowlist argument (no scriptable types on a trusted origin) does not apply there; what replaces it is **one shared origin for every team**, accepted with a standing rule the console, `yyt site` and the SPA repeat verbatim (`SITE_SHARED_ORIGIN_WARNING`): no credential in web storage on that host. A game page keeps its JWT in memory and mints per session.
- The zip entry name is the only thing between one team's deploy and another's prefix. `zip.ts` `sitePath` is an **allowlist** (ASCII, segment charset, no `.`/`..`/empty segments, no backslash, ≤16 segments), non-ASCII is refused rather than normalised (NFC/NFD twins would be two objects the prune cannot tell apart), symlinks and dot-files are dropped, and the worker still asserts `key.startsWith(slug + "/")` and `SLUG.test(slug)` before any S3 call — an empty or malformed slug would otherwise turn "prune the prefix" into "wipe the bucket".
- Every cap on an archive is enforced **while** inflating (`inflateRawSync({ maxOutputLength })`, running total), never from the central directory's declared sizes; zip64, encryption and multi-disk are refused, and entries are read from the central directory (Go's writer leaves local headers at 0).
- Staging uploads never go to the site bucket: every object there is served by the CDN (world-readable), so the zip is presigned into the private poster bucket and deleted after the worker read it.

## Per-site hosts (`{slug}.g.yyt.life`, 2026-09-26)

- **The edge authorizes nothing, so S3 is the access list.** The function maps a Host label to the same-named prefix with no lookup; whatever objects sit under a grammar-valid label are served on that label's origin. Every path that gives a prefix up must empty it (move cleanup, failed-move cleanup, delete, the name sweep), and a claim refuses a prefix still waiting for its purge. Decide what to delete from the **site row**, never from the deploy row: a switch whose commit reply was lost did switch.
- **Fail closed at the edge.** The function returns its own 404 for anything outside the name grammar and the zip path grammar (no `%` at all, no dot segments, no `//`, a lower-cased Host that must be exactly `label + "." + suffix`) — it never passes an unchecked request through. The origin gets no viewer headers, cookies or query strings: a forwarded Host would make S3 look for a bucket named after it, and a query string reaches S3 sub-resources — and, on a request signed through origin access control, the `response-content-type`/`response-content-disposition` overrides, which would serve any upload as HTML. The path host's and artifact CDN's functions drop the query string too (2026-09-27).
- **A served origin never changes hands.** A name (or random slug) whose prefix served files stays with its team forever, a deleted team's with nobody; only a platform admin's audited release frees one. The browser is the reason: storage, cookies, service workers and permission grants outlive any hold.
- **Same-site cookie hygiene.** Sibling hosts can toss cookies at `Domain=yyt.life`. `parseCookies` trims ASCII whitespace only (JS `trim()` would turn an NBSP-prefixed ` __Host-x` into the real name) and drops a `__Host-`/`__Secure-` name seen twice; keep it that way, and keep the console's exact-Origin check.

## Documents (state service, 2026-08-26)

- The state service has **two** credentials and one 401. A doc apiKey (`yds.{channelId}.{random}`) is the server, may touch any owner's document; a player's channel JWT may read the single document its own `sub` names. Everything that does not verify — wrong key, wrong signing secret, wrong audience, an expired/disabled/deleted channel — returns the same `unauthorized`, so nothing distinguishes "no such channel" from "wrong password".
- The apiKey **names its own channel** because the routes carry no channel segment, and that is a lookup key, not a claim: the id selects which row to compare against, and a constant-time digest comparison over `sha256` decides. The same shape covers the JWT — `unverifiedChannelId` reads `iss` _without verifying_, purely to pick the secret, and `verifyChannelToken` immediately rejects the token unless it was really signed with it. Never let a value read that way become identity.
- It is a **second** secret on the auth channel, beside the signing key, because the two have different holders: the signing key never leaves the platform, the apiKey is pasted into a participant's own Lambda. Rotating either must leave the other alone — `rotate-secret` merges rather than replaces `secret_json`, and so does the doc-key route.
- A player reading another owner is **403, not 404**: the caller is authenticated, the rule is worth stating, and it reveals nothing they did not already know (their own id). Absence is 404 only for the row they are entitled to see.
- Revoking the key does **not** delete the documents. Revocation is how an owner stops a leaked credential, and taking a channel's character sheets as a side effect of that would be unrecoverable; deleting the channel is the action that takes both.
- There is no list route. Enumerating a channel's owners is a server capability, and a route a client could reach with its own token would hand it one.
- **`secret_json` is a read-modify-write blob with four writers now** — `buildChannel`, `patchChannel`, `rotateSecret` and the doc-key routes — and none of them uses compare-and-set. Two concurrent edits lose one: a doc-key issue racing a `rotate-secret` writes back the pre-rotation signing secret, resurrecting a key the operator believes revoked. Pre-existing, and the reason every one of those functions must **spread the stored object** rather than rebuild it from the fields it knows. `patchChannel` did rebuild it, so an ordinary config edit silently dropped the doc apiKey and the owner's only symptom was their game server going 401 (found in review, fixed, regression-tested). When you add a field to a secret blob, grep every function that writes it back.
- The doc apiKey is stored **plaintext**, like the topic/match apiKeys and unlike `api_tokens.token_hash`. It is only ever compared, so it could be a digest; it is not, for consistency with its three siblings, and hashing one of four is worth less than the inconsistency costs. Revisit all four together or none.
- The state service resolves **any** bearer with one MySQL `SELECT`, before a body limit or an authorization check applies, so unauthenticated junk is what competes for `reservedConcurrency` and through it for the shared box's connections. That is why the stack sets `httpApi.defaultRouteSettings` throttling rather than relying on the reservation alone. One exception since 2026-09-08: `GET /time` (and `/time/`) is skipped by the resolver, because it authorizes nothing and a client that attaches its bearer to every request would otherwise pay that `SELECT` for the clock. **A route excused from identity resolution has to be excused from it at every spelling the router accepts** — `compilePath` matches a trailing slash, so the skip normalises one off; a skip that is narrower than the route silently reinstates the cost it was written to avoid.

## Realtime gateway (`gateway/`, 2026-08-27)

- Order the handshake by cost: shape checks (channel id regex, `bearer` subprotocol present, JWT-shaped token with an unexpired `exp`) and the per-address handshake bucket run **before** the console read and the auth verify, so an unauthenticated flood costs the gateway a regex, not a Lambda invocation per request. Both remote calls are also bounded: the config cache is capped (1024, evict soonest-expiring) and negative-cached only for well-formed ids; verifies run under a semaphore (8 < auth's reserved 10) and fail fast with 503 rather than throttling every other auth consumer.
- A shared in-flight fetch (singleflight) must run on its **own** context with a timeout, never the first caller's request context — one client aborting its handshake would otherwise fail the seven teammates waiting on the same key.
- `/metrics` is on the public host: the process-wide numbers are public, the per-channel slice (channel ids are half of what an attacker needs to target a lobby) is served only with the operator token, and `/healthz` caches its console probe so a poller cannot turn it into an amplifier. `/livez` exists so a restart policy never keys on the console's health.
- In the `q` bridge `connectionId` is the only field an actor may trust: the gateway overwrites it and **strips** a client-supplied `memberId`, because the envelope shape is identical to the `enter` the actor does trust and a participant's actor may read it too casually.
- Every refusal after the upgrade is a typed `error` frame and repeated abuse closes the socket; a Redis outage is surfaced to the client (`error unavailable`, then `4001` after three failed pushes) — silence is never the answer, and neither is a log line per failed push (throttle per op).

- History rewrite recipe (used 2026-08-28 for a Redis account name): back up `.git`, `git filter-repo --replace-text <file> --force` (it drops `origin`; re-add it), `git push --force origin main` and `--tags` (moved tags are fine — GHCR images are keyed by digest), add the identifier to `local/identifiers.txt`, run `scripts/check-history-identifiers.sh`. The pre-push hook scans the whole pushed tip when the old remote sha no longer exists locally, so a rewrite does not need `--no-verify`. Used again 2026-09-27 for two bucket names, run from the session after the owner's explicit approval. A `.git/filter-repo/already_ran` left by an earlier run makes filter-repo treat the new run as a continuation of that one. It does so silently when that run is less than a day old. When the run is older it asks first, and without a terminal the question is an `EOFError`. Move `.git/filter-repo/` aside before a new rewrite; its `commit-map` records the earlier run, so keep it in `local/`. `echo n | git filter-repo …` also starts fresh when the old run is older than a day. A fresh `git clone --mirror` shows only that no remote ref still reaches the old text. The pre-rewrite commits stay public: the force-push entry in the repository's activity view and the events API point at them, they resolve by sha, and every fork and clone keeps them. That lasts until GitHub support purges them (`docs/secrets.md`), and forks and clones keep them even after that. Treat a rewritten name as published. For the bucket names the protection is that the buckets are private (`docs/decisions.md` _CDN cost guard_ §11), not the rewrite.
- **A stored reason that is served back is a different thing from one that only reaches the audit log.** Show moderation reasons go to `audit_log` and nowhere else; the event force-close reason (2026-09-01) is on the event page for anonymous visitors, so it needed three things the moderation ones do not: a note in the SPA control and the CLI flag help that the text **is published and cannot be edited afterwards** (the same `ConfirmWithReason` widget otherwise implies an admin-only note), rendering as a text node rather than through `Markdown`, and a `\p{Cc}` refusal — `output.Clean` keeps `\n`/`\t` on purpose, so a newline in a reason forges a row in the CLI's `key: value` table. Ask where a new free-text field is _read_ before copying an existing field's validation.
- **An admin action that overrides a member decision has to record what it overrode.** `close-vote` moves `voteUntil` to now, which destroys the only trace of how much of the vote was cut off, and naming an option destroys the fact that the tally said otherwise. Both go into the audit detail (`previousVoteUntil`, `tallyStartsAt`), and the page carries a derived `voteOverridden` so it can say "the tally decided" and "an admin picked this" differently — a page that claims the stronger one either way is as misleading as one that hides the override (2026-09-01).
- Order every HTTP route as route match → bearer verification → body/param validation. Parsing the body first answers `400` to anonymous callers, which both leaks validation detail and makes tests assert the wrong code (sample-morpg phase 3, 2026-08-28).
- CSP applies to redirect targets: `GET /events/{id}/poster` answers a 302 to a presigned S3 URL, and `img-src 'self'` alone blanked every poster in the SPA (fixed 2026-08-29: `img-src` lists the exact virtual-hosted poster bucket host the presigner emits, `https://yyt-console-posters-{stage}.s3.ap-northeast-2.amazonaws.com` — the bucket name is already public in `serverless.yml`, so a wildcard bought nothing; `services/console/test/csp.test.ts` pins both). When a same-origin route redirects to another host, that host needs to be in the directive of the consumer (`img-src`, `connect-src`, `media-src`), not just the origin the tag names.

## Social graph (`/social/*`, 2026-09-10)

- **A display name is user text on a surface the platform does not control.** 1–32 characters, trimmed, refusing `\p{Cc}`, `\p{Cf}` and U+2028/2029 and a run of combining marks: a newline forges a row in an operator's table (the leaderboard `meta` lesson), a bidi override reorders one, and a zero-width joiner makes two different names look identical. Refusing at the boundary is not enough on its own — names are **not unique**, so every renderer (SPA, CLI, and the client libraries' docs) puts the owner id beside the name wherever a mistake matters.
- **An "opaque string" a client will render is still a syntax decision.** `avatar` is an id or a path (`^[A-Za-z0-9][A-Za-z0-9._-]{0,31}(?:/…){0,3}$`, ≤ 64): no `:`, no leading `/`, no bare `..` segment. Opaque means the platform never resolves it, not that it must store anything — a value with a scheme or a protocol-relative prefix is a tracking pixel in every viewer's friend list the moment a client puts it in an `<img src>`. Whole-string grammar of safe segments, never a `..` blacklist, the same shape as `sitePath` and the kv key.
- **A cooldown must live where the party that pays for it cannot delete it.** Deleting a declined request hands the sender their slot back and makes request → decline → request free and infinite (the console's join→withdraw lesson restated). The row stays on the **sender's** side as `dropped`, out of the recipient's inbox and their cap but still inside the sender's, and expires with the request TTL. The one observable difference — withdraw refuses it — is the price, and it is written down rather than papered over.
- **A hiding rule is only as strong as the answer it shares with something innocent.** "A block answers 404" is a proof of the block while every other target answers 200. What repairs it is a second, ordinary cause for the same code: a target with no profile. Say plainly in the docs how far the hiding goes (a caller who already knows the target has a profile can still infer it) rather than claiming anonymity a route cannot deliver — and do not add a second hiding rule that is a stronger oracle: omitting a blocker from a profile batch would be passive, batchable and re-checkable, which is worse than the thing being hidden.
- **A protection that spans two stacks is only as strong as the one that cannot see the other.** A block lives in MariaDB on the state stack; presence lives in Redis on the gateway, which has no MariaDB by design — so `GET /presence` is **not** block-aware and a blocked player keeps a working presence feed on whoever blocked them. Nothing in either service is wrong; what would be wrong is a document saying "a block bounds harassment" without that sentence next to it. When a feature's guarantee has to hold across a boundary the architecture forbids crossing, write the hole down in both READMEs and in the client recipe, where the person building the UI will read it.
- **A cooldown, a block and a profile delete are three writes on the same row, so decide who owns each fact.** Three separate loops were found in one review pass (2026-09-10) and all three were the same mistake — a row whose state one party owns carrying a fact that protects the _other_ party: block-then-unblock deleted the decline cooldown that lived in the blocker's own row (fixed with a `cooldown_until` the block preserves and the unblock restores), and deleting a profile deleted every row pointing at that owner, including other players' blocks (fixed by excluding `state = 'blocked'` from that half of the purge). Ask, for every column a transition overwrites: whose fact is this, and can the party it constrains reach it?
- **Enumerate what already lists the identifier before claiming a route is not enumerable.** Profiles are fetched 50 ids at a time and never listed, but `GET /kv/{col}/entries` on a `readScope: project` collection and `GET /lb/{board}/top` already hand out owner ids in bulk — so the batch route completes a directory for anyone who wants one. What bounds it is the per-channel salt, and a channel created before 2026-09-09 has none.
- **A public-read S3 origin is also readable around the CDN.** Its name is enough to download past every CloudFront-side control (a cost guard, a switch, a WAF).
  - The fix is a private bucket read through origin access control (`scripts/origin-oac.sh`, 2026-09-27). Access control needs the REST endpoint, so whatever the website endpoint did that clients rely on (index documents, the directory redirect, a literal `+`) moves into a CloudFront Function.
  - A secret `Referer` origin header with a bucket-policy condition, the stopgap used earlier the same day, also works on website endpoints. But it is a shared secret sent over HTTP, and every server access log line would record it.
  - A policy does not override an object ACL grant. Pair it with `IgnorePublicAcls`, and turn `BlockPublicAcls` on only where no uploader still sends `public-read`: find the writers first (Lambda environments naming the bucket, their `Invocations`).
  - A name already in public history is harmless once the bucket is private.

- **A Go transport error prints the request URL, query string included** (2026-09-28, review of `todo/46` P2). `http.Client.Do` wraps failures in `*url.Error`, whose `Error()` is `Put "<full URL>": …`; Go masks only a password in the userinfo, so a presigned PUT's `X-Amz-Credential`, `X-Amz-Security-Token` and signature land in whatever prints the error — and `yyt asset sync` collects per-file errors and prints them, in CI logs too. `putPresigned` rewrites `ue.URL` in place (keeping the `net.Error` type the retry classifier needs), and a test with a failing transport asserts no `X-Amz-` or `?` survives. Any new code that sends a bearer URL must do the same.
- **A batch route authorizes every resource it names before it answers about any of them** (same review). The first batch commit checked "one bundle only" (400) and "nothing found" (200) before `projectResource`, so the mix of answers told a caller whether another team's upload id existed. Now every distinct bundle is authorized first, an id of a bundle the caller cannot write is a per-id `not_found`, and only then are the rest judged.
- **"The other services' grants are table-scoped" was true of state only** (2026-09-28, `todo/46` P4 acceptance check). `SHOW GRANTS` on both stages: the state account names its tables, but auth, topic and match hold a database-level `SELECT`, so a new table such as `asset_bundle_keys` is readable by three stacks the design said could not see it. The rows are wrapped under a KEK only the console `api` function holds, so the exposure is one layer of defence, not the key — but a sentence like that in `docs/decisions.md` has to come from `SHOW GRANTS`, not from the ownership rule. Narrowing the three grants is an owner item (`local/owner-checklist.md`); until then say "console is the only reader" and not "the only account that can".
- **A test-vector file carries one secret-shaped value, and it is the allowlisted one** (same task). The `yak1.` bundle-key rule in `.gitleaks.toml` is allowlisted by the vector key's text form only; the "wrong key" case therefore keeps the vector key and carries bytes made under another one, so `docs/asset-encryption-vectors.json` never holds a second key text. Design negative vectors that way before generating them — a second literal would need a second allowlist entry, and every entry is a hole.
- **A refusal to read a secret answers one body, whatever the cause** (P4 review): `POST /assets/bundles/{b}/key` first answered `asset_key_other_kek` and `asset_key_unreadable` as two bodies, which told a member that the stage KEK had been replaced. Both are `asset_key_unreadable` now, and the cause (which `kekId` the row and the stage carry, or the unwrap failure) travels only in the error's `cause` to the log line — the same rule as the kv 503s above.
- **Handler-wide CORS is gated by `allow-headers`, not by route lists** (auth stack, 2026-10-01, `todo/55`): `createHttpHandler({ cors })` marks every route including dev `/debug/*`, and that is fine only because `x-debug-key` is not an allowed request header — a browser preflight refuses it. Never add a debug or admin key header to `cors.headers`; `services/auth/test/app.test.ts` pins this. `*` is safe exactly when every credential is an explicit header or body field (never a cookie) and `credentials` stays off; a navigation-only cookie (`/start` → `/callback` nonce) is out of a cross-origin script's reach without credentials.

## Push (`/push/*`, device tokens and Firebase keys, 2026-10-06)

- **A device token is never logged, returned or audited.** It addresses one device of one player, and whoever holds it and any key of the same Firebase project can message that device. So: no response of any route carries one (a send answers per **user id**, a token `PUT` answers 204 with no body), `checkPushToken`'s message never quotes its input, the rows are keyed by the channel and the token's sha256 so a delete names a digest, and `@yyt/push` results carry enum codes and HTTP statuses only — Google's free-text `message` is dropped, because it can echo the token it refuses. The same goes for FCM message ids and access tokens. `PushDb.listTokensForUsers` exists for the platform's own sender and for nothing a team can reach.
- **"Platform-internal" holds for the state account only.** Its grant is table-scoped; auth, topic and match hold a database-level `SELECT` (the 2026-09-28 `SHOW GRANTS` finding above), so all three can read `push_tokens` in clear, and nothing wraps a token. Until those grants are narrowed in the ops repo, a sentence saying "only state and console read tokens" is false. The state account's `SELECT` on `channels` likewise covers `secret_json` of every push channel, the team's service-account key included.
- **A team's service-account key is stored like an auth channel's provider secrets.** It lives in `secret_json` beside the apiKey, is accepted on create and on `PUT /channels/{id}/sender-key`, and is never returned, logged or audited: the audit row says `rotated` and nothing else, and the view shows `teamProject` only. Every write **merges** the blob under the row lock (`ConsoleDb.editChannel`) — the apiKey and the key share it, so a rebuild on rotate or on a key change, or a merge over a row read before another writer landed, would silently drop the other. A refused key names the field (`details: {reason: "service_account", field}`), never `JSON.parse`'s message, which quotes its input. In memory the key is a `KeyObject`, which serialises to `{}` wherever it lands by accident.
- **`token_uri` is pinned to Google's endpoint.** A service-account file is team-supplied input that says where to POST a signed assertion; honouring it would make the platform an HTTP client of the team's choosing that hands over a credential. Absent or exactly `https://oauth2.googleapis.com/token`, else 400. `project_id` is held to Google's grammar for the same reason: it becomes a URL path segment.
- **Adopt only what the platform registered.** A pool project also holds apps added by hand (the console app). Every app the platform registers carries the display-name marker `yyt-push:{stage}:` followed by the channel id — no member text reaches the Firebase console — and only an app carrying **this stage's** whole marker is adopted on `ALREADY_EXISTS`, filled in by the reconciliation, removed on a channel delete, or removed by the reconciliation when no claim names it. Without the marker a team naming a hand-registered package would be handed that app's config and, on deleting its channel, would remove the app. An unmarked match is refused as `package_taken`; the reconciliation counts it (`orphans`, `foreign`) and never touches it. The marker is therefore also a delete permission: never give a hand-made app a display name that starts with `yyt-push:`.
- **The marker names the stage, because claims are per stage and a project need not be** (review 2026-10-06). With a bare `yyt-push:` one Firebase project in both stages' pools — or a key put under the wrong stage's SSM path — had each stage's sweep find the other's apps marked and unclaimed, and delete them at once. `isPlatformApp(app, stage)` compares the whole prefix; another stage's app, or one with the bare prefix, is foreign here like a hand-made one. The stage is injected from the handler's config (`PushDeps.stage`), never read from `process.env` in the module.
- **The reconciliation deletes on fresh evidence only.** An unclaimed marked app is removed after the claim is read again by package name _after_ Firebase's list came back — never from the claims read before it. A create writes its claim before it calls Firebase, so "listed, marked, and no claim of this slot names the package now" can only be what a rolled-back or timed-out create left; the pre-list snapshot would also match a registration that started in between.
- **A check followed by an irreversible call is not atomic; make the first step reversible** (review 2026-10-06, reproduced). That re-read and an immediate remove still left a window: a retry of the same package claimed and adopted the orphan in between, and a live channel pointed at a purged app. The reconciliation now removes **softly** first (state `DELETED`, which no create adopts — it purges and registers anew), reads the claim once more (by package, and any claim of the slot naming the app id), and only then purges with `immediate`; an app a claim names by then is restored with `:undelete`, and a claim that cannot be read counts as claimed. Every order ends with the channel bound to a live app: adopted before the soft removal → restored; create after it → new app id, and the sweep's purge or restore of the old id finds nothing. A restore that fails is logged as an error and reported as `missing`.
- **A sender that costs nothing must not hold a scarce name** (review 2026-10-06). A `team`-sender channel takes a self-made key, calls no Firebase API and counts against no cap, and its claim used to hold the package name stage-wide: eight creates squatted eight names of somebody else's app. Stage-wide uniqueness is the `platform` claims' alone now (`rules/data.md`).
- **Every route that spends a shared third-party quota takes the write slot, reads included.** `GET /channels/{id}/google-services.json` is one Firebase Management call per request against the pool project every team shares; it takes the member's write slot like the create does, so a loop gets 429s.
- **Known gaps, accepted for now (owner, 2026-10-06):** no per-channel ceiling on token rows (5 per user, any number of users), the token length cap stays 4096, the console's functions share one IAM role, and `POST /push/{id}/send` tells an existing channel (401) from a missing one (404) before it checks the key.
- **A pool project id is an infra identifier, not a secret.** It is in no source file, doc, log line, audit row or error: a slot is named by its label (`p1`) everywhere, `push_project_refused` does not list the ids a channel accepts, and each id goes into gitignored `local/identifiers.extra.txt` — not `local/identifiers.txt`, which `scripts/local-identifiers.sh` regenerates from the env files and that list — so the commit hooks refuse it. It is still public to every team in the slot — `google-services.json` carries it and ships in their APK — so nothing may treat knowing it as authorization. `teamProject` is the team's own id and is shown to that team.
- **Log the SDK error's name, not its message.** `createPushPool` logs `e.name` when the SSM read fails: the message of an access-denied error carries the parameter ARN and the role.
- The send route compares the apiKey as fixed-length sha256 digests with `timingSafeEqual`, and refuses a request without a bearer before its first `SELECT`.
- **Deferred match (2026-10-06).** The ticket routes verify the bearer through the same function as the WebSocket authorizer (`verifyPlayer` in `services/match/src/channels.ts`): one implementation, so the two surfaces cannot drift. Order: id shape (400) → bearer shaped like a JWT (401, before any lookup) → channel exists (404; an unknown id is cached 10 s on the ticket path) → auth channel active (410) → token (401) → channel active (410) → mode (400 `wrong_mode` with `details.mode`). An HTTP error body, unlike the authorizer's uniform Deny, is an oracle: the channel's state and mode come after the token, and only what no token can be verified without (existence, the auth channel) is answered before it. The player is the verified `sub` and nothing in the path, query or body; a `sub` that is not 1–128 printable ASCII characters is a 403, because it becomes a Redis key segment and a hash field. A `confirmed` record names a match and the stored result names its members; the read checks both, so a forged or stale record cannot open someone else's result.
- **A deferred result is the one place the match stack stores a callback's answer** (`dr:{channelId}:{matchId}`, at most `resultTtlSec` ≤ 1 h; live mode's `result:{matchId}` never holds it). It may carry a game token: it is returned only to members, with `no-store`, and never logged.
- **Deferred abuse bound = two Redis TTL keys** (owner decision 2026-10-06, _Match: deferred mode_ #7): `dcd:` (cooldown, `acceptTimeoutSec`, set on decline / delete-in-proposal / unanswered window) and `dpn:` (10 s between `proposed`/`expired` pushes per user and channel). Without them one player could submit → be proposed → decline in a loop and push every other member's device each time. Code constants, not registry limits.
- **The match push hook sends ids, not content**: `{channelId, matchId, state}`, data-only. It logs counts, the slot label and error codes — no token, user id or Firebase project id (`services/match/test/push.test.ts` pins this). `pushChannelId` is checked by console at write time (active, same project, same auth channel) and again at send time, since the push channel can expire or be repointed afterwards; a mismatch skips the push.
- **CORS on the ticket API is `*` without credentials**, the state stack's rule: the credential is an explicit `Authorization` header. The dev `/debug/*` routes are a different function with no CORS at all.

## Push campaigns (2026-10-06)

- **A second credential on the console API gets its own path family, and the first one does not count there.** `/push-api/{channelId}/…` takes the push channel's apiKey as a bearer — sha256 of both sides, `timingSafeEqual` — and never looks at the identity the request may also carry: a member's cookie on those paths is a 401, and the apiKey on a member path is a 401. No CORS header, so no browser origin can use a leaked key against it. The routes are declared without `auth`, which is safe only because every handler starts with the key check; the test matrix walks every route with no key, a wrong key, another channel's key, a prefix, a longer key and a cookie. **An unknown channel id answers the same 401 as a wrong key** (a 404 there was an oracle for which ids exist); 410 is kept for a known channel with the right key.
- **A shared key is rate-limited by what it opens, not by who holds it**: the write slot of the apiKey family is keyed by channel (`mdrl:pushkey:{channelId}`), so two servers with one key share one slot.
- **Recipients are user ids, never device tokens.** A CSV header that reads like a token column (`token`, `device_token`, `fcmToken`, `registration_id`, …) refuses the whole file; no response, report, audit row or log line carries a device token or a Firebase project id, and no log line carries a user id (the test greps all of them after a full job).
- **A file a team will open in a spreadsheet is output to escape.** The report is CSV built from the team's own upload: a cell starting with `=`, `+`, `-`, `@`, tab or CR gets a leading `'`, control characters are dropped, quotes are doubled, and a value is cut at 128 characters. Only an `invalid-user` row can carry such a value (a valid user id cannot start with one), which is exactly the row an attacker controls.
- **A parser of an uploaded file is strict and bounded before it is helpful.** The CSV reader works on bytes with caps per record (1,024), per field (512) and on columns (32), refuses invalid UTF-8, NUL, a bare CR and any quote that is not RFC 4180, and fails the whole job at the line — before anything is sent, because the worker reads the file once in full first. No dependency was added for it.
- **A template is checked with the send route's validator, not a copy of it** (`@yyt/push` `pushDataFailure`, `pushPayloadBytes`): reserved FCM data keys and the 4096-byte payload are one rule for the targeted send, a template and a broadcast. The state route uses the same two functions and re-exports the constants; its messages are its own.
- **A placeholder is substituted in one pass and its value is never re-read**, so a CSV value holding `{{other}}` or `$&` cannot pull another column or a replacement pattern into a message.
- **An FCM topic is public to everyone who holds the app, and to every other app of the same pooled Firebase project.** Subscribing needs only the app's Firebase config (public by design) and the topic name (`yyt.push.{channelId}`), and a topic belongs to the project, not to an app. A broadcast therefore carries no secret, no personal data and no `data` that grants anything; private content goes through a campaign or the targeted send (device tokens). The app must not treat a topic message as authenticated. What does hold is integrity: only the API holding the project's key can send to the topic. `docs/push.md` _Broadcast_ says this to teams.
- **The platform's own topic message says no more than a public page does** (`todo/56` P3, 2026-10-06). `yyt.catalog.{stage}.{appId}` announces a catalog upload to the console app. Any holder of the console app's Firebase config (it is inside the APK) and every team app in the same pool project can subscribe to any name, so the notice names the app only while a `public` listing without a takedown shows it; otherwise the title is fixed and the payload is the app id + version tag. Accepted residual: whoever knows a private app's id learns that a build landed and its version. The client never builds a topic name (the server hands out `topic`), drops a message whose topic its current profile's server did not name for that app, and opens screens from its own authorised list, never from the message.
- **A client's Firebase config is public but still not committed.** It is extractable from any APK, so it protects nothing — yet the project id, sender id and app id are infra identifiers of a pool project, which this repo never carries (`docs/secrets.md`). The console app takes them from `--dart-define-from-file=<gitignored json>`; the tracked `firebase.example.json` holds placeholders, `apps/console-app/.gitignore` refuses any other `firebase*.json`, and there is no `google-services.json` or Google Services plugin to tempt a commit. Do not print the values in a log line either: the app's push error sink records the error's type, not its text.
- **A value substituted into a checked template is checked again.** A template refuses control characters, but a CSV field may hold any byte, so the rendered row is held to the same rule (title: none; body and data values: `\n` and `\t` only) and a row that breaks it is `skipped` / `invalid-value` — otherwise a quoted CSV field carries ESC or CR into a notification past the template check.
- **A worker's own progress note stays out of the job view.** A running broadcast keeps the projects it sent to in `error_detail` as 12-hex hashes of the project ids; the view answers `errorDetails` only for a `failed` job, and both ways of ending a job (the worker's finish, the sweep's `expired`) clear the note first.
- **A report names a channel's players: a member's read.** `GET …/report` takes the member-write access level (a seatless platform admin gets 403) although it writes nothing; job counts stay readable like every project read.
